# Client-side storage, key protection, PWA platform constraints and code integrity for a browser-only encrypted messenger (GitHub Pages PWA), state as of 2026-11-01

Scope note: the app is a static site on GitHub Pages (no custom response headers), installed as a PWA. The native app uses SQLCipher plus OS-bound key protection; the notes below give the browser equivalents and, where none exists, the honest substitute. Every finding has a URL; claims from vendor blogs, forum threads or search snippets are labelled "secondary" or "unverified".

## Key question 1: Storage engines — OPFS + SQLite WASM vs IndexedDB, encryption at rest, quotas, Safari's 7-day eviction, `navigator.storage.persist()`

### Takeaway
The workable browser equivalent of "SQLCipher file on disk" is SQLite compiled to WASM writing to the Origin Private File System (OPFS) from a dedicated Worker, using a VFS that does not need SharedArrayBuffer (SQLite's official `opfs-sahpool`, or wa-sqlite's `AccessHandlePoolVFS` / `OPFSCoopSyncVFS`); at-rest encryption comes either from the SQLite3MultipleCiphers WASM build (ChaCha20-Poly1305 default, SQLCipher-compatible scheme available) or from application-level encryption of rows before they reach a plain SQLite file. Quotas are generous on every 2026 browser (about 60% of disk per origin on Chrome and Safari), but Safari deletes all script-writable storage of a site after 7 days of Safari use without interaction; an installed Home Screen web app has its own day counter and WebKit treats deletion there as a bug, yet bug reports of exactly that exist, so the local database must be treated as re-creatable from the relay/backup, and `persist()` requested (it is auto-decided, no prompt, on Chrome and Safari).

### Cited Findings

Storage engines and VFS options
- SQLite's official WASM build offers these persistence back-ends: `kvvfs` (localStorage/sessionStorage, main thread only, "typically 5MB"); the `opfs` VFS, which "requires" COOP/COEP headers because it needs SharedArrayBuffer and must be loaded in a Worker; `opfs-sahpool` (added in SQLite 3.43), which "does not require COOP/COEP headers", is "easily" the fastest OPFS option, but "does not support multiple simultaneous connections to the same database" and fails to initialize in a second tab using the same directory; and `opfs-wl` (3.53.0), which uses Web Locks and needs `Atomics.waitAsync()`. — [sqlite.org/wasm persistence](https://sqlite.org/wasm/doc/trunk/persistence.md)
- Same source: OPFS "is not available on the main thread"; "Safari versions less than version 17 are incompatible with the current OPFS VFS implementation"; opening an OPFS file takes an exclusive lock, so "no two database handles can have the same OPFS-hosted database open at one time"; clients must handle `SQLITE_BUSY`; `opfs-sahpool` versions before 3.54 "had a locking bug that could corrupt data" with multiple same-thread connections; by default a failed `opfs-sahpool` init "wipes the storage" (`preserveOnInitFailure` false as of 3.54); `pauseVfs()`/`unpauseVfs()` (3.50+) let another instance take over the handles. WAL on OPFS requires `locking_mode=exclusive` and "provides no concurrency benefit". Storage limits "differ per environment" and databases "can disappear for reasons outside the library's control". — [sqlite.org/wasm persistence](https://sqlite.org/wasm/doc/trunk/persistence.md)
- Unverified (search-engine summary, not read from the page): the npm package `@sqlite.org/sqlite-wasm` README reportedly carries a notice dated 2026-04-15 marking the Worker1/Promiser1 APIs deprecated in favour of calling `sqlite3InitModule` inside a worker. — [sqlite/sqlite-wasm on GitHub](https://github.com/sqlite/sqlite-wasm)
- wa-sqlite (MIT since 2023-02-10) ships synchronous and asynchronous (Asyncify or JSPI) builds and VFS classes `IDBBatchAtomicVFS`, `IDBMirrorVFS`, `AccessHandlePoolVFS`, `OPFSAdaptiveVFS`, `OPFSAnyContextVFS`, `OPFSCoopSyncVFS`, `OPFSWriteAheadVFS`. — [wa-sqlite README](https://github.com/rhashimoto/wa-sqlite)
- wa-sqlite's comparison table marks "No COOP/COEP requirements" for every VFS; `AccessHandlePoolVFS` is synchronous, Worker-only, single connection, and with `locking_mode=exclusive` allows WAL, which can "significantly reduce write transaction overhead"; `OPFSCoopSyncVFS` is synchronous, Worker-only and supports multiple connections via a "retry hack" that "may expose race conditions"; `IDBBatchAtomicVFS` works in all contexts (including main thread) but is async only; `IDBMirrorVFS` keeps files in memory and "can only use databases that fit in available memory"; `OPFSAnyContextVFS` writes are "very bad and will be increasingly worse as the file grows"; `OPFSWriteAheadVFS` needs the proposed `readwrite-unsafe` locking mode, "only on Chromium browsers as of June 2024". — [wa-sqlite src/examples](https://github.com/rhashimoto/wa-sqlite/tree/master/src/examples)
- Browser support (MDN browser-compat-data, main branch, read 2026-11-01): `FileSystemFileHandle.createSyncAccessHandle` Chrome 102, Chrome Android 109, Firefox 111, Safari 15.2; `Atomics.waitAsync` Chrome 90, Firefox 145, Safari 16.4; `LockManager` (Web Locks) Chrome 69, Firefox 96, Safari 15.4; `StorageManager.persist` Chrome 55, Firefox 57, Safari 15.2. — [mdn/browser-compat-data](https://github.com/mdn/browser-compat-data) (files `api/FileSystemFileHandle.json`, `javascript/builtins/Atomics.json`, `api/LockManager.json`, `api/StorageManager.json`)
- SQLite's own page states OPFS support as "Chromium-derived browsers since about mid-2022, Firefox 111 and later, Safari 16.4 and later" (July 2023 statement), which is later than BCD's Safari 15.2 for the raw API. — [sqlite.org/wasm persistence](https://sqlite.org/wasm/doc/trunk/persistence.md)

Encryption at rest
- SQLite3MultipleCiphers (SQLite3MC) changelog: "Added WebAssembly target support (issues #88, #89)" in the release immediately preceding 1.4.8 (2022-07-26); "Applied several modifications to improve support for SQLite3 WASM" in the release based on SQLite 3.44.2; 2.5.x "Fixed issue #252 - precompiled WASM fails due to compact import encoding"; 2.6.0 (2026-10-12) "Fix WASM entropy source when HEAPU8 is not exported"; 2.6.1 "Fixed build failure with older Emscripten versions". The project therefore publishes a precompiled WASM. — [SQLite3MultipleCiphers CHANGELOG](https://github.com/utelle/SQLite3MultipleCiphers/blob/main/CHANGELOG.md)
- SQLite3MC latest version shown is 2.6.1 (October 2026) based on SQLite 3.54.0. — [SQLite3MultipleCiphers README](https://github.com/utelle/SQLite3MultipleCiphers)
- SQLite3MC cipher schemes: wxSQLite3 AES-128/256-CBC, "sqleet: ChaCha20-Poly1305 HMAC" (the "recommended default cipher scheme"), "SQLCipher: AES 256 Bit CBC, with SHA1/SHA256/SHA512 HMAC", RC4, Ascon-128, AEGIS. Limitations: "TEMP tables are not encrypted", in-memory databases are not encrypted, "Bytes 16 through 23 of the database file contain header information that is usually not encrypted". — [SQLite3MultipleCiphers docs](https://utelle.github.io/SQLite3MultipleCiphers/)
- A SQLite Forum post notes SQLite3MC "supports WASM, with a precompiled WASM binary in its latest release". — [SQLite Forum](https://sqlite.org/forum/forumpost/20b2639ec5?t=c) (secondary, from search snippet)
- The Rust crate `sqlite-wasm-rs` can build with SQLite3MultipleCiphers via a `sqlite3mc` feature and has an OPFS `sahpool` VFS ("available only in a Dedicated Worker"); the docs list them as separate options and no example combines them. — [sqlite-wasm-rs](https://github.com/nyurik/sqlite-wasm-rs) (secondary, from search snippet)
- No official SQLCipher (Zetetic) WASM build was found. A third-party "Fork of SQLCipher v4.16.0 (SQLite 3.53.1) patched for LibreSSL and WASM" exists, runs in a Web Worker, "Auto-detects the best persistence backend — OPFS or IndexedDB page cache", lists OPFS as "Chrome 108+, Safari 16.4+, Firefox 111+" with Firefox/Safari OPFS marked untested, is BSD-3-Clause, and makes no claim of affiliation with Zetetic; it warns that stock SQLCipher opening its files is "Not tested, by decision" and non-default cipher settings "can risk corruption after a crash". — [wmacevoy/sqlcipher-libressl](https://github.com/wmacevoy/sqlcipher-libressl)
- Aztec's kv-store added SQLite-wasm over OPFS as an experimental backend and deferred encryption to "either the sqlite3mc level or the OPFS-VFS page-encryption level". — [aztec-packages PR 22658](https://github.com/AztecProtocol/aztec-packages/pull/22658) (secondary, from search snippet)

Quotas and eviction
- MDN: in Chrome/Chromium "an origin can store up to 60% of the total disk size in both persistent and best-effort modes" and "Chrome currently uses at most 80% of the total disk size"; Firefox best-effort is the smaller of 10% of disk or the 10 GiB group limit, persistent up to 50% of disk capped at 8 TiB; Safari browser apps: "each origin can store up to around 60% of total disk", other WebKit-embedding apps "around 15%", a Home Screen/Dock web app "uses the same origin quota as the browser app", cross-origin frames get "roughly 1/10 of their parents", overall cap 80% (browser apps) / 20% (non-browser apps). Eviction is LRU, whole-origin, skipping persistent origins. Exceeding quota throws `QuotaExceededError`. Data stored via IndexedDB, Cache and "File System API (which defines the Origin Private File System)" is all managed by the same per-origin storage system. — [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- WebKit (2023-08-10, Safari 17 / iOS 17): origin quota "up to 60% of the total disk space" for browser apps, 15% for other apps, 10% of the parent for cross-origin frames; overall 80%/20%; a Home Screen Web App "gets the same origin and overall quotas as the browser app"; Safari 17 "no longer prompts users when a site wants more space" (earlier Safari gave 1 GiB then prompted); eviction is triggered by overall quota, system pressure, or "a period of no user interaction (Intelligent Tracking Prevention)", and `persist()` "exempts an origin from best-effort eviction", granted by heuristics "such as whether the site is opened as a Home Screen Web App". — [WebKit: Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/)
- Safari's "legacy" behaviour: "an origin is given an initial 1 GiB quota" then Safari prompts. iOS 17.4+ alternative engines in the EU may apply their own policies. — [MDN Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

Safari's 7-day cap and Home Screen apps
- WebKit (2020-03-24): ITP deletes "all of a website's script-writable storage after seven days of Safari use without user interaction on the site"; covered types are IndexedDB, LocalStorage, media keys, SessionStorage, "Service Worker registrations and cache". Home Screen web apps "are not part of Safari" and "have their own counter of days of use"; WebKit "does not expect first-party website data in such apps to be deleted" and deleting it "would be a serious bug". — [WebKit: Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)
- MDN restates it: "If an origin has no user interaction, such as click or tap, in the last seven days of browser use, its data created from script will be deleted. Cookies set by server are exempt." — [MDN Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- A 2020 WebKit bug reports cookies and localStorage deleted in a Home Screen web app after about nine days without launching it. — [WebKit bug 211775](https://bugs.webkit.org/show_bug.cgi?id=211775)
- A 2022 WebKit bug (237350) discusses which cookies are capped for Home Screen web apps ("Only JavaScript-created cookies and cookies from third-party CNAME-cloaked responses should be capped at 7 days ... Server-set cookies and HTML storage should not be deleted"). — [WebKit bug 237350](https://bugs.webkit.org/show_bug.cgi?id=237350) (search snippet)
- Apple Developer Forums thread "Safari iOS PWA Data Persistence Beyond 7 Days": developers note the exemption is in ITP docs but "the counter has to be reset each time the app is opened". — [Apple Developer Forums 710157](https://developer.apple.com/forums/thread/710157) (secondary)

`navigator.storage.persist()`
- MDN: "Safari and most Chromium-based browsers, such as Chrome or Edge, automatically approve or deny the request based on the user's history of interaction with the site and do not show any prompts"; Firefox "is notified with a UI popup". — [MDN Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- web.dev (last updated 2020-05-12): Chrome's heuristics are site engagement, "Has the site been installed or bookmarked?", "Has the site been granted permission to show notifications?"; a denial can be re-requested later; persistent data "is only deleted if the user chooses to remove it using their site settings". — [web.dev Persistent storage](https://web.dev/articles/persistent-storage)
- Anecdote: a 2023 test saw Chrome/Edge deny immediately without a prompt while Firefox prompted. — [Raymond Camden 2023](https://raymondcamden.com/2023/08/25/working-with-the-storage-api) (secondary)

### Inferences
- The closest analogue to the native "SQLCipher file" is SQLite3MultipleCiphers compiled with SQLite's official WASM toolchain on top of `opfs-sahpool` (no COOP/COEP, fastest, Safari 16.4+/17+). Because `opfs-sahpool` is single-tab, the app needs a tab-leader election (Web Locks, available everywhere since Safari 15.4) and `pauseVfs()` hand-over, or wa-sqlite's `OPFSCoopSyncVFS` if multi-tab writes are a hard requirement.
- IndexedDB-backed VFSs remain the fallback for contexts where OPFS sync handles are unavailable (very old browsers, some private modes); they are slower and async-only, but work on the main thread.
- Application-level encryption (encrypt message bodies and attachment blobs under a per-database key before insert, keep only opaque IDs and timestamps in plaintext columns) is the "honest substitute" if the SQLite3MC WASM build cannot be reproduced/verified; it loses full-text search over plaintext and leaks table structure and row counts, which SQLite3MC does not.
- Treat local storage as a cache: Safari's ITP, LRU eviction, and user "clear site data" can all destroy the database without warning. The identity key must be recoverable (export/backup or re-provision via the relay), and message history must be re-fetchable from the relay or a backup, or its loss accepted explicitly in the UI.
- Call `navigator.storage.persist()` after installation and after notification permission, since those are exactly Chrome's and WebKit's grant heuristics.

### Gaps
- No primary benchmark comparing `opfs-sahpool` vs `IDBBatchAtomicVFS` on 2026 phones was found; only SQLite's qualitative "easily the fastest" claim.
- No documented end-to-end example of SQLite3MultipleCiphers WASM running on `opfs-sahpool` was found; the combination is implied by the changelog and the Rust crate but not demonstrated.
- Whether the 2020 Home Screen deletion bug (211775) is fixed in current iOS was not verified; the WebKit statement of intent stands but reports of deletion exist.
- Safari's exact `persist()` heuristics beyond "opened as a Home Screen Web App" are not published.
- Whether Safari's 7-day ITP counter also covers OPFS by name is not stated explicitly; MDN's phrase "data created from script" and WebKit's list ("all script-writable storage") imply it does.

## Key question 2: Key protection — non-extractable WebCrypto keys, WebAuthn PRF / hmac-secret support in 2026, passkey unlock UX, Argon2 in WASM on phones

### Takeaway
Browsers have no equivalent of OS-bound key storage for web content: the WebCrypto spec allows key material to be "persisted to disk, possibly unencrypted", and `extractable=false` only stops page JavaScript from exporting bytes, not from using the key (so XSS can still decrypt). The best 2026 substitute is to derive the vault key from a passkey via the WebAuthn `prf` extension (Safari/iOS 18+, Chrome 116+ with Google Password Manager or security keys, Firefox 139+/149 Android), with Argon2id over a user password as the universal fallback; third-party passkey managers' PRF support is uneven and Chrome's built-in profile passkeys have none.

### Cited Findings

What non-extractable WebCrypto keys protect
- Web Cryptography spec, Security Considerations: the spec "places no normative requirements on implementations as to how the underlying cryptographic key material is stored"; it does "not guarantee that the underlying cryptographic key material will not be persisted to disk, possibly unencrypted"; "Any application or user that has access to the device storage may be able to recover the key material"; "conforming user agents are not required to zeroize key material"; "issues such as script injection are the equivalent to remote code execution" and injected script "may allow for the exfiltration of keys or data"; any origin sharing scheme/host/port shares the storage partition; once a key is shared via structured clone "the source origin can not later restrict or revoke access". — [W3C Web Cryptography API, Security Considerations](https://w3c.github.io/webcrypto/#security-considerations)
- W3C WebCrypto WG (Ryan Sleevi, 2012): a key with `extractable=false` "can be stored in IndexedDB without exposing the raw key material. What is stored in IndexedDB is effectively a reference"; "'Extractable' only gives you assurances between the UA and the JS. It does not give you any assurances about the UA and below." — [public-webcrypto Dec 2012](https://lists.w3.org/Archives/Public/public-webcrypto/2012Dec/0027.html)
- 1Password (2024-07-18): "in the browser it's currently not possible to store these keys in a secure manner". — [1Password blog](https://1password.com/blog/encrypt-data-saved-passkeys)

WebAuthn PRF extension (spec)
- WebAuthn Level 3 became a W3C Recommendation on 25 August 2026; §10.1.4 defines the `prf` extension. — [W3C WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/)
- Spec text: the extension "allows a Relying Party to evaluate outputs from a pseudo-random function (PRF) associated with a credential. The PRFs provided by this extension map from BufferSources of any length to 32-byte BufferSources"; "PRF outputs could be used as symmetric keys to encrypt user data"; evaluating at two inputs in one assertion lets "the encryption key ... be periodically rotated"; it "is modeled on top of the [FIDO-CTAP] hmac-secret extension, but can also be implemented by other means"; inputs are hashed as `SHA-256(UTF8Encode("WebAuthn PRF") || 0x00 || input)` before reaching hmac-secret; the PRF used "MUST be the one used for when user verification is performed"; "Not all authenticators support evaluating the PRFs during credential creation so outputs may, or may not, be provided. If not, then an assertion is needed"; `evalByCredential` maps base64url credential IDs to inputs and is "Only applicable during assertions when allowCredentials is not empty"; at registration `enabled` is set from the authenticator's hmac-secret output; "Authenticator extension outputs MUST NOT contain cleartext PRF outputs"; non-CTAP implementations use a PRF "whose outputs are exactly 32 bytes long, selected uniformly at random from a set of at least 2^256 such functions". — [WebAuthn editor's draft §10.1.4](https://w3c.github.io/webauthn/#prf-extension)
- Yubico: older hmac-secret derives the secret during an assertion; the newer `hmac-secret-mc` derives it at registration and "needs firmware 5.8 or later"; both surface through the WebAuthn PRF extension. — [Yubico PRF support](https://developers.yubico.com/Passkeys/Passkey_concepts/Security_key_capabilities/Pseudo-Random_Function_PRF_Support.html) (search snippet)

- Chrome: "Intent to Ship: WebAuthn PRF extension" (Adam Langley, April 2023) covering all Blink platforms; chromestatus entry 5138422207348736 reads "Enabled by default" (API read 2026-11-01; the milestone field is empty); a GitHub commenter believed it landed in M116 (unverified). — [blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/iTNOgLwD2bI/m/Oz1C7oEYAgAJ), [chromestatus](https://chromestatus.com/feature/5138422207348736)
- Corbado's matrix (lastModified 2026-09-29, snapshot August 2026; vendor blog, secondary): "macOS 15 enabled PRF via iCloud Keychain across Safari 18+, Chrome 132+ and Firefox 139"; security-key PRF on Safari "since Safari 26.4" (March 2026) and on iOS/iPadOS 26.4; "Android has the broadest PRF support", "Every passkey stored in GPM supports PRF"; Firefox 149 shipped PRF on Android (March 2026); "Windows Hello returns PRF values since the February 2026 update for Windows 11 24H2 and 25H2" (KB5077181); "Chrome 147 has committed support for PRF on create" on Windows; "the Chrome profile authenticator does not support PRF at all"; iOS 18.0–18.3 had cross-device data-loss bugs, "iOS 18.4+ fixed earlier data-loss bugs"; open WebKit bugs 311099 and 314934 affect USB/NFC security keys in Safari. Argon2 in WASM
- OWASP Password Storage Cheat Sheet minimum Argon2id configurations: "m=47104 (46 MiB), t=1, p=1", "m=19456 (19 MiB), t=2, p=1", "m=12288 (12 MiB), t=3, p=1", "m=9216 (9 MiB), t=4, p=1", "m=7168 (7 MiB), t=5, p=1"; "increasing parallelism is not a guarantee of slower password guessing"; benchmark on the target system. — [OWASP cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
- Bitwarden defaults: "By default, Bitwarden is set to allocate 32 MiB of memory, iterate over it 6 times, and do so across 4 threads"; "Argon2id users with a KDF memory value higher than 64 MiB will receive a warning dialogue every time iOS autofill is initiated"; PBKDF2 default 600,000 iterations. — [Bitwarden KDF algorithms](https://bitwarden.com/help/kdf-algorithms/)
- argon2-browser benchmark (argon2d, 100 iterations, 1 MiB, p=1, 2020 MacBook Pro i7): Chrome WASM 225 ms, Chrome WASM+SIMD 119 ms, Firefox WASM 195 ms, Safari WASM 174 ms, native -O3 SSE 15 ms; no mobile figures. — [antelle/argon2-browser](https://github.com/antelle/argon2-browser)
- openpgpjs/argon2id falls back to a non-SIMD binary in Safari. — [openpgpjs/argon2id](https://github.com/openpgpjs/argon2id) (search snippet, secondary)
- Tuta chose Argon2 for its web client via WebAssembly; "WebAssembly ... is still not available in some situations, for example, on Lockdown Mode in iOS"; mobile apps use native implementations. — [Tuta blog 2023-08-23](https://tuta.com/blog/best-encryption-with-kdf)
- Anecdotes only: a Bitwarden user on iOS 16.3.1 with 110 MB / 10 iterations / p=8 reported "no noticeable effect"; an Android user with 256 MB / 10 / p=16 reported "3 to 5 seconds to login depending on the device". — [Bitwarden community](https://community.bitwarden.com/t/recommended-settings-for-argon2/50901?page=3) (secondary)

### Inferences
- Vault-key design that is honest about the browser: a random 256-bit database key (for SQLite3MC or app-level AES-GCM) wrapped twice: once under a PRF-derived key (`prf.eval.first` = app-specific constant salt, output HKDF'd into the wrapping key) and once under an Argon2id(password) key; unwrap into a non-extractable WebCrypto `CryptoKey` kept only in Worker memory, never persisted. This mirrors Bitwarden's "PRF symmetric key" design and the spec's stated motivating use.
- PRF availability must be feature-detected at registration (`enabled` output) and the UX must fall back to the password path when `enabled` is false, when the authenticator only supports evaluation at assertion time, or when the user's manager (Dashlane, NordPass, Chrome profile) returns nothing. Expect 100% on Apple Passwords and Google Password Manager, variable elsewhere (Corbado's figures).
- Requiring a passkey assertion to unlock means a biometric prompt at every cold start; keep the unwrapped key in memory for the session and rely on the OS screen lock, as the native app does. Rotation via the spec's two-input trick is cheap to add later.
- For Argon2id on phones, OWASP's 19 MiB/t=2 or 12 MiB/t=3 profiles plus a Worker are the safe default; Bitwarden's 32 MiB/6/4 and its iOS >64 MiB warning show 64 MiB is the practical ceiling in iOS extension contexts. Nothing better than anecdotes exists for timings, so the parameters must be benchmarked on the owner's target devices.
- Because XSS equals key compromise, code-integrity controls (question 5) are part of key protection, not a separate concern.

### Gaps
- No measured Argon2id-in-WASM timings on 2025–2026 iPhones/Android phones at 19–64 MiB were found; the numbers above are desktop (1 MiB) or anecdotal.
- No official Google/Android document on PRF in Credential Manager or on third-party providers' ability to advertise PRF was found; sources conflict.
- The exact Chrome milestone that enabled PRF by default is not exposed by chromestatus; "Chrome 116" is a community belief.
- Chromium's on-disk handling of non-extractable keys stored in IndexedDB (plaintext vs OS-encrypted) was not verified from source; the spec only says plaintext is permitted.

## Key question 3: PWA runtime on iOS (Safari and Home Screen apps) and Android Chrome in 2026 — background execution, WebSocket/WebTransport/WebRTC survival, Web Push, background sync, service worker lifetime

### Takeaway
Neither platform lets a web app keep code or sockets alive once it is backgrounded or the screen locks: iOS suspends the process (WebSockets die, often without `onclose`), Chrome freezes/throttles hidden pages and terminates idle service workers after 30 s (WebKit after 10 s). The only wake-up path is Web Push with a user-visible notification (iOS 16.4+ for Home Screen apps only; WebKit revokes the subscription after three silent pushes; Declarative Web Push without a service worker since iOS 18.4), so message delivery while the app is closed must be the relay's job, with push as the wake signal. Background Sync, Periodic Sync and Background Fetch are Chromium-only.

### Cited Findings

iOS / WebKit

### Inferences
- A browser messenger cannot be its own always-on transport. The architecture must be relay-centric: the relay (or the owner's existing relay/agent) holds encrypted messages, sends a Web Push to wake the installed PWA, and the PWA's push handler must always show a notification (or use Declarative Web Push on iOS 18.4+ with the real content fetched when the app opens). On WebKit three silent pushes kill the subscription, so "silent sync" pushes are not an option.
- Push handlers get at most about 5 minutes per event in Chromium and are torn down about 10 s after going idle in WebKit, so decrypting and persisting a message inside the push event must be fast and must not depend on the OPFS single-connection VFS being free (the foreground tab may hold the lock; `pauseVfs()` or a message to the tab is required).
- WebSocket/WebTransport/WebRTC to the relay should be treated as foreground-only: reconnect on `visibilitychange`/`resume`, heartbeat, never trust `readyState` after the page was hidden. WebTransport is now cross-browser (Safari 26.4) but gains nothing for background survival.
- Because iOS requires installation for push, the first-run UX must guide "Add to Home Screen"; iOS 26 makes the result open as a web app by default, which removes one failure mode.
- Android installed PWAs (WebAPK) get the full Chromium feature set including Background Sync, but the single reliable wake path is still push.

### Gaps
- No Apple documentation states the service worker time budget for push events on iOS; only WebKit source constants were found.
- Whether the 3-silent-push quota is unchanged in 2026 WebKit was not verified beyond the 2022 commit.
- No official Chrome for Android documentation on tab-freeze timing beyond the Page Lifecycle text and the 5-minute throttling rule was found.
- iOS push subscription loss "without cause" rests on a vendor blog and is unverified.
- Whether third-party iOS browsers (Chrome on iOS) can install push-capable Home Screen apps in 2026 was not researched.

## Key question 4: WebAssembly threads need cross-origin isolation; GitHub Pages cannot set COOP/COEP — the service-worker injection workaround and its behaviour on iOS

### Takeaway
GitHub Pages serves a fixed header set, so `SharedArrayBuffer` (needed by wasm threads and by SQLite's `opfs` VFS) is only reachable through the `coi-serviceworker` trick: a service worker that re-serves every response with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy` headers and reloads the page once. It works on Chromium and Firefox; on Safari/iOS the default `credentialless` mode is not supported at all (through Safari 27.2), so only `require-corp` mode can work and there is no WebKit documentation confirming that service-worker-synthesised COOP/COEP yield `crossOriginIsolated` on iOS. The robust design avoids the need: single-threaded wasm plus `opfs-sahpool`/wa-sqlite, which need no isolation.

### Cited Findings
- GitHub Pages: a community feature request (2025/2026) states "GitHub Pages serves every file with a fixed set of default headers and offers no way to add custom HTTP response headers", linking the older request for custom CSP headers (#54257). No official GitHub doc stating header support was found. — [GitHub community discussion 199121](https://github.com/orgs/community/discussions/199121) (secondary)
- Wasmer's docs describe the service-worker emulation for hosts like Pages: "This script reloads the page on the first user visit, registering a service worker that emulates COOP and COEP headers." — [Wasmer: COOP/COEP headers](https://docs.wasmer.io/sdk/wasmer-js/how-to/coop-coep-headers)
- coi-serviceworker README: provides "cross-origin isolation (COOP and COEP) through a service worker for situations in which you can't control the headers"; it "will reload the page on the user's first load"; must be a separate file served from your own origin (not bundled, not CDN), over HTTPS or localhost; `coepCredentialless` defaults to true (uses `Cross-Origin-Embedder-Policy: credentialless`), `coepDegrade` retries with `require-corp`; `doReload` can be overridden to ask the user first; the README has no Safari/iOS notes. — [gzuidhof/coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker)
- Issue tracker: users on GitHub Pages reported reload loops where the page never became isolated; a suggested cause was the script not being served from the top-level directory; the maintainer says "serious" projects should set headers on the backend. — [coi-serviceworker issue 5](https://github.com/gzuidhof/coi-serviceworker/issues/5)
- `COEP: credentialless` support: Chrome 96, Firefox 119, Safari false (MDN BCD main); caniuse lists Safari 3.1–27.2 and iOS Safari as "Not supported". — [mdn/browser-compat-data Cross-Origin-Embedder-Policy.json](https://github.com/mdn/browser-compat-data), [caniuse credentialless](https://caniuse.com/mdn-http_headers_cross-origin-embedder-policy_credentialless)
- Contradicted claim: a widely copied `coi-serviceworker.js` comment says "iOS Safari only learned credentialless in 17.5 (May 2024)"; this is a code comment, not WebKit documentation, and conflicts with BCD/caniuse. Treat as unverified/false. — [mirrored coi-serviceworker.js](https://caterwauling-jumper.m.preview.paperboy.com/coi-serviceworker.js)
- `SharedArrayBuffer` support: Chrome 68, Chrome Android 89, Firefox 79, Safari 15.2 (BCD); caniuse: Safari on iOS "Supported from 15.2", "Disabled by default" 10.3–15.1. — [mdn/browser-compat-data SharedArrayBuffer.json](https://github.com/mdn/browser-compat-data), [caniuse SharedArrayBuffer](https://caniuse.com/sharedarraybuffer)
- Zoom's Video SDK team hit SharedArrayBuffer failures on an iPhone X with iOS 16.7 and worked around it by "skipping the coi-serviceworker.js setup only on iOS". — [Zoom dev forum](https://devforum.zoom.us/t/session-failing-when-using-sharedarraybuffer-on-ios/122170) (secondary)
- WebKit bug 261734 (NEW, 2023): a Worker module load is blocked by COEP in Safari 16.6 despite valid CORP headers. — [WebKit 261734](https://bugs.webkit.org/show_bug.cgi?id=261734)
- SQLite's `opfs` VFS "requires" COOP/COEP (SharedArrayBuffer); `opfs-sahpool` "does not require COOP/COEP headers"; OPFS-over-WASMFS also requires them "for the whole library". — [sqlite.org/wasm persistence](https://sqlite.org/wasm/doc/trunk/persistence.md)
- wa-sqlite: every VFS in the comparison table has "No COOP/COEP requirements". — [wa-sqlite src/examples](https://github.com/rhashimoto/wa-sqlite/tree/master/src/examples)
- MDN: workers "are in general not governed by the content security policy of the document ... set a Content-Security-Policy response header for the request which requested the worker script itself", except blob/data-URL workers, which inherit the document's policy. — [MDN Content-Security-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)

### Inferences
- On GitHub Pages, cross-origin isolation is achievable on Chromium and Firefox with coi-serviceworker in `require-corp` mode (set `coepCredentialless: false` so Safari gets a header it understands); `credentialless` mode is a no-op on WebKit. Whether iOS honours SW-injected COOP/COEP is undocumented and has field reports of failure, so the app must not depend on `SharedArrayBuffer` for correctness.
- A first-load reload plus a service worker that rewrites every response is a bad fit for a security app: it adds a second service worker in the integrity story (question 5) and a visible reload on first visit. Prefer builds without wasm threads (Rust `wasm32-unknown-unknown` single-threaded, crypto in a dedicated Worker) and `opfs-sahpool`.
- If a threaded wasm build is ever needed (e.g. an embedded I2P router), gate it on `self.crossOriginIsolated === true` at runtime and keep a single-threaded fallback; that is what Zoom effectively did for iOS.
- The same "no headers" limitation means workers cannot get a header-delivered CSP; blob-URL workers inheriting the document's `<meta>` CSP are the available substitute.

### Gaps
- No WebKit/Apple statement was found on whether COOP/COEP headers synthesised by a service worker make a page `crossOriginIsolated` on iOS; only anecdotal failures and the contradicted "17.5" claim.
- No 2026 test matrix of coi-serviceworker on iOS 18/26 was found.
- GitHub's official docs were not located stating header limitations; the limitation is inferred from the open feature request and third-party docs.

## Key question 5: Code integrity and supply chain for a static-hosted crypto app — SRI, CSP, reproducible builds, Sigstore/transparency logs, Isolated Web Apps and Web Bundles, Code Verify, the service-worker update cycle

### Takeaway
No 2026 browser verifies a web app's code against a signature out of the box: Isolated Web Apps are ChromeOS-enterprise-only, Web Bundles subresource loading is Chromium-only with a neutral Mozilla position, and Source Code Transparency is an unimplemented proposal. What exists for a GitHub Pages app is layered: SRI on every script/wasm fetch, a `<meta>` CSP (headers are unavailable), reproducible builds whose hashes are attested via GitHub Actions + Sigstore (public transparency log), a published hash manifest, and an optional out-of-band verifier in the spirit of Meta's Code Verify or FPF's WEBCAT (Firefox-only alpha since March 2026, which also requires a header-delivered CSP). The service worker script itself cannot be SRI-protected; the browser re-fetches it byte-for-byte on navigation (at most every 24 h for push/sync), so the SW should be minimal and should itself verify fetched assets against the signed manifest.

### Cited Findings

Subresource Integrity and CSP
- SRI applies to `<script>` and `<link rel="stylesheet|preload|modulepreload">`; allowed prefixes `sha256`, `sha384`, `sha512`; browsers pick the strongest algorithm present; cross-origin resources must use CORS (`crossorigin`), and `no-cors` requests with integrity "will always fail"; the `Integrity-Policy` header can block scripts/stylesheets lacking integrity. — [MDN Subresource Integrity](https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity)
- `fetch()` accepts an `integrity` option: "This will be checked when the resource is fetched, just as it would be when the integrity attribute is set on a <script> element ... if the result does not match ... the browser will reject the fetch request with a network error." — [MDN RequestInit](https://developer.mozilla.org/en-US/docs/Web/API/RequestInit#integrity)
- CSP via `<meta http-equiv>` is "a useful option for some use cases, such as a client-side-rendered single page app which has only static resources ... However, this option does not support all CSP features"; "a report-only policy cannot be delivered in a <meta> element". — [MDN CSP guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP)
- Workers do not inherit the document CSP unless loaded from blob/data URLs (see question 4). — [MDN Content-Security-Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy)

Reproducible builds, Sigstore, attestations
- GitHub artifact attestations: signed with Sigstore; for public repositories "the Sigstore Public Good Instance" is used and a copy "is also written to an immutable transparency log that is publicly readable on the internet"; private repos use GitHub's instance which "does not have a transparency log"; verification via `gh attestation verify`; "Artifact attestations by itself provides SLSA v1.0 Build Level 2", Level 3 with reusable workflows; "Generating attestations alone doesn't provide any security benefit" and they "are not a guarantee that an artifact is secure"; GitHub Pages deployments are not mentioned. — [GitHub Docs: artifact attestations](https://docs.github.com/en/actions/concepts/security/artifact-attestations)
- WEBCAT's manifest approach to reproducibility: `app` and `version` "point to a Git repository and tag, so auditors can rebuild the release and compare the manifest"; GitHub attestations are "mentioned only as a possible future addition". — [SecureDrop: WEBCAT](https://securedrop.org/news/webcat-towards-auditable-web-application-runtimes/)

Code Verify (Meta)
- Code Verify is "an open source web browser extension that confirms that your Facebook, Messenger, Instagram, and WhatsApp Web code hasn't been tampered with"; a manifest lists "the hashes of all the JavaScript/CSS files in a given release" and the extension verifies "that only that code executes, or else display a warning"; installable from Chrome, Firefox, Edge or Safari stores. — [facebookincubator/meta-code-verify](https://github.com/facebookincubator/meta-code-verify)
- Meta (2022-03-10, updated for Messenger 2022-08-11 and Instagram 2023-06-16): "We've given Cloudflare a cryptographic hash source of truth for WhatsApp Web's JavaScript code"; Cloudflare provides "independent, third-party, transparent verification"; unlike SRI "Code Verify checks the resources on the entire webpage"; "If there are any inconsistencies, Code Verify will notify the user"; listed for Chrome, Edge, Firefox. — [Meta Engineering: Code Verify](https://engineering.fb.com/2022/03/10/security/code-verify/)
- The IWA explainer compares itself to "Meta and Cloudflare's Code Verify, which is described as similar to Binary Transparency". — [WICG isolated-web-apps README](https://github.com/WICG/isolated-web-apps/blob/main/README.md)

WEBCAT (Freedom of the Press Foundation)
- "a code integrity mechanism for single-page browser applications", introduced 2025-03-19; verification failure shows an error in the WEBCAT browser extension. — [FPF: Introducing WEBCAT](https://freedom.press/tech/news/introducing-webcat-web-based-code-assurance-and-transparency/)
- Design (2025-12-18): enrolled origins are checked "against the domain list shipped with the WEBCAT browser extension"; the manifest (`app`, `version`, `default_csp`, `files` path→SHA-256, `default_index`, `default_fallback`, `wasm` hashes, `extra_csp`) "is the only object that needs to be signed and transparency-logged"; `unsafe-inline` is disallowed in `script-src`; WebAssembly is checked by hooking compile/instantiate against the manifest; "Only a single CSP header is supported"; server redirects must be relative same-origin; unlisted assets stream through unverified; runtime-generated service worker blobs break reproducibility; opaque third-party scripts (reCaptcha, Turnstile) are impractical. — [SecureDrop: WEBCAT](https://securedrop.org/news/webcat-towards-auditable-web-application-runtimes/)
- Alpha (2026-03-03): "has just entered alpha testing"; users are invited "to try out our Firefox browser extension" and developers "to experiment with our new decentralized web domain enrollment system". — [FPF: Help SecureDrop test WEBCAT alpha](https://freedom.press/tech/news/help-securedrop-test-webcat-alpha/)
- Repository description: "WEBCAT is an architectural framework for providing blocking code signing and verification, integrity and transparency checks for browser-based applications"; last push 2026-10-31. — [freedomofpress/webcat](https://github.com/freedomofpress/webcat)
- Research paper (2025): the mechanism "prevents the execution of unverified code, unlike previous approaches premised on user-visible error indicators". — [IACR ePrint 2025/797](https://eprint.iacr.org/2025/797)
- Funding: the Ethereum Foundation's 1TS initiative announced a grant to FPF for WEBCAT on 2026-08-05. — [Ethereum Foundation blog](https://blog.ethereum.org/2026/08/05/1ts-grant)
- Talk at Transparency.dev Summit 2025. — [transparency.dev](https://transparency.dev/summit2025/talks/webcat.html)

Isolated Web Apps and Web Bundles
- Explainer: IWAs "are packaged into Web Bundles, signed by their developer", served from `isolated-app://` where "the authority section of the URL is based on the public key used to sign the Web Bundle"; updates replace the bundle "with a new version signed by the same key"; the signing key "can be kept securely offline". — [WICG isolated-web-apps README](https://github.com/WICG/isolated-web-apps/blob/main/README.md)

- A W3C TPAC 2025 session noted IWAs "have been launched in ChromeOS since 2024"; Google positions IWAs as the Chrome Apps successor (Chrome Apps removed from ChromeOS kiosk July 2026, entirely February 2028). — [W3C TPAC 2025 meeting](https://www.w3.org/events/meetings/5c9ab1dc-8be0-47ff-8012-c925b553d243), [chromeunboxed](https://chromeunboxed.com/make-way-for-the-iwaisolated-web-app/) (secondary)

- Web Bundles: Mozilla's standards position was closed "non-harmful" on 2020-05-28 and relabelled "position: neutral" on 2024-09-13. — [mozilla/standards-positions#264](https://github.com/mozilla/standards-positions/issues/264)
- Subresource loading with Web Bundles: the old (`urn:uuid`) APIs "were removed in M102"; a newer declarative API shipped in Chrome 104 (2022); Brave disabled it. — [Chromium commit b3f32ae](https://chromium.googlesource.com/chromium/src/+/b3f32ae50f14cda992944604f4ef33c8dbaeca77), [jefftk blog](https://www.jefftk.com/p/built-in-bundling-for-faster-loading) (secondary)
- Source Code Transparency (Daniel Huigens, Proton; WICG proposal #124, 2023): publish "the hash of a Web Bundle of the web app to a transparency log, similar to Certificate Transparency logs, such as sigstore or a future log based on the IETF's SCITT work", signalled via an X.509 extension; no browser implementation found. — [WICG proposals #124](https://github.com/WICG/proposals/issues/124), [W3C workshop talk](https://www.w3.org/2023/03/secure-the-web-forward/talks/source-code-transparency.html)

Service worker update cycle
- The browser checks for a new service worker on navigation to an in-scope page and on `push`/`sync` events "unless there's been an update check within the previous 24 hours"; a worker is updated if it is "byte-different to the one the browser already has"; Chrome 68+ ignores HTTP caching headers for the registered script by default (`updateViaCache` overrides; imported scripts still respect caching headers); new workers install alongside the old and wait until the old controls zero clients; `skipWaiting()` activates sooner but "pages loaded under the old version may have some fetches handled by the old worker"; `reg.update()` can be called manually (e.g. hourly). — [web.dev Service worker lifecycle](https://web.dev/articles/service-worker-lifecycle)
- Safari deletes "Service Worker registrations and cache" under the 7-day ITP rule (question 1); Declarative Web Push exists partly because "a service worker is removed, for example by ITP". — [WebKit 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/), [WebKit Declarative Web Push](https://webkit.org/blog/16535/meet-declarative-web-push/)

### Inferences
- Practical 2026 stack for a Pages-hosted messenger: (1) reproducible build in GitHub Actions with `actions/attest-build-provenance` on the exact bundle that is deployed, so the Sigstore public log carries the hash set; (2) a `manifest.json` of SHA-256 hashes for every JS/CSS/wasm asset, signed and committed with the release tag; (3) `index.html` with a strict `<meta>` CSP (`script-src 'self'` plus hashes, `wasm-unsafe-eval` only if needed, no inline), SRI on every `<script>`/`<link>`, and `fetch(..., {integrity})` for `.wasm`; (4) a tiny service worker that only caches assets whose hash matches the manifest and refuses anything else; (5) in-app "About" showing the build hash and a link to the Rekor entry so a user can compare with what `gh attestation verify` reports. None of this stops a malicious release signed by the repository owner; it makes such a release publicly logged and byte-comparable, which is the Code Verify / WEBCAT threat model.
- WEBCAT is the closest thing to "the user can trust the JS" with blocking enforcement, but it is Firefox-only alpha and it checks a CSP header; on GitHub Pages only a `<meta>` CSP exists, so enrolment is likely impossible without a header-capable host (Cloudflare Pages/Netlify in front) — needs to be confirmed with the WEBCAT spec.
- Isolated Web Apps are not an option for consumers in 2026 (ChromeOS managed devices only), and their 2026 CVE stream shows the model is still maturing; Web Bundles outside IWAs give no integrity guarantee by themselves.
- The service worker is the weak link: it is fetched without SRI and silently replaced on byte change; keep it trivial, ship its hash in the attested manifest, and have the page compare `navigator.serviceWorker.controller.scriptURL`'s fetched bytes against the manifest at startup (hash the response of `fetch(scriptURL)`) to surface tampering in the UI.
- Because the index HTML itself cannot be SRI-protected by anything inside the page, the only out-of-band roots of trust available today are a browser extension (Code Verify / WEBCAT model), the Sigstore log plus manual verification, or a native wrapper; the notes should say this plainly to the owner.
