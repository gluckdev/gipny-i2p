# Threat model and anonymity of a browser-hosted, outbound-only I2P router + E2EE messenger; precedents among privacy messengers

State as of 2026-11-01. All geti2p.net URLs now 301-redirect to i2p.net; the i2p.net URLs below are the ones actually fetched. "Design A" = byte-level TCP forwarder on the user's own native node relaying NTCP2 to arbitrary routers; "Design B" = NTCP2-over-WebSocket first hop terminated on a project-run node (vocabulary from `docs/plans/2026-10-31-web-local-mode.md`). Quotes are verbatim from the cited page unless marked "paraphrase".

## KQ1. Anonymity of an outbound-only ("hidden"/firewalled) I2P router, and whether a small browser population changes the academic picture

### Takeaway
I2P's own documentation defines hidden mode as "no RouterInfo in netDb, no participating tunnels", and frames that as a trade: harder to harvest, but zero cover traffic and "not widely used". A browser router is structurally a hidden/unreachable client that can never relay, and its messenger destination must still publish a LeaseSet naming its inbound gateway (a project node in Design B); the published attacks (2011 peer-selection DoS, 2013 floodfill/Sybil + storage verification, 2026 RouterInfo live-behaviour alignment) all target the netDb/floodfill layer and exploratory-tunnel behaviour that every client, hidden or not, still performs — so a browser router inherits them, while a small, identifiable population entering through a handful of project nodes makes harvesting and intersection trivially easier for the operator and any observer of those nodes.

### Cited Findings
- Hidden mode is defined by three behaviour changes: a hidden router "will no longer publish a routerInfo to the NetDB, it will no longer accept participating tunnels, and it will reject direct connections to routers in the same country that it is in"; routers geolocated to the "Strict" list (42 countries, "as of 2024", incl. China, Iran, Turkey; Russia is not on the list) are placed in hidden mode automatically — [I2P: Restrictive countries](https://i2p.net/en/docs/overview/restrictive-countries) (page undated; strict list labelled 2024).
- The I2P threat-model page describes hidden mode as the defence against harvesting: "“Hidden mode”, which prevents a router from publishing its information to the netDb" ... "but also prevents it from relaying data" and notes it is "not widely used now"; "“Harvesting” means compiling a list of users running I2P." and "I2P itself is not designed with effective defenses against this attack" — [I2P threat model](https://i2p.net/en/docs/overview/threat-model) (page undated; banner references release 2.14.0 of 2026-10-20).
- Same page on the other attack classes: intersection — "if an attacker is at both ends of your tunnel at the same time, he may be successful"; Sybil — "We currently have not implemented any particular technique to address Sybil"; timing — "Without protocol scrubbing or higher latency, global active adversaries can gain substantial information"; predecessor — "The predecessor attack is passively gathering statistics"; restricted routes "are not currently implemented"; DoS section: "over 95% of I2P users relay traffic for others" — [I2P threat model](https://i2p.net/en/docs/overview/threat-model).
- Firewalled (not hidden) Java routers still "remain firewalled" and rely on SSU introducers to be reached; the troubleshooting page says (paraphrase) a firewalled router cannot take direct inbound connections, performance drops noticeably and it "contributes little to the network"; hidden mode is enabled via the router console and "uses SSU introducers exclusively" — [I2P troubleshooting](https://i2p.net/en/docs/troubleshooting/).
- RouterInfo capability flags: "U" means the router is not directly reachable on any transport address and a router should publish R or U; "H" is listed only as "Hidden". Floodfill is automatic only for routers with manually set high bandwidth (min share "128 KBytes/sec"); roughly 6% of routers (~1,700) are floodfills. Threat analysis lists Sybil (full and partial keyspace, an attacker clustering 8–15 floodfills near a target key), bootstrap/reseed attacks, query capture and information leaks (floodfills can observe queries); daily keyspace rotation is a defence that recent research suggests is not especially effective (all paraphrase) — [I2P network database](https://i2p.net/en/docs/overview/network-database).
- Peer-selection restrictions ("as of 2010"): "Two peers from the same /16 IP space may not be in the same tunnel", "A peer may participate in a maximum of 33% of all tunnels created by the router", "Peers with extremely low bandwidth are not used", "Peers for which a recent connection attempt failed are not used" — [I2P peer selection](https://i2p.net/en/docs/overview/peer-selection).
- Tunnel defaults: exploratory tunnels default to 2 hops, client tunnels 2–3 via I2CP; "The maximum number of hops in a tunnel is 7"; 3+ hops recommended for highest protection; tunnel testing "mandatory as of 2026-02" (paraphrase) — [I2P tunnel routing](https://i2p.net/en/docs/overview/tunnel-routing).
- i2pd has the equivalent knobs: `notransit` = "Router will not accept transit tunnels" (publishes the G cap), `nat` = "If true, assume we are behind NAT" (default true), `trust.hidden` = "Should we hide our router from other routers?" (default false) — [i2pd configuration](https://docs.i2pd.website/en/latest/user-guide/configuration/).
- Network size (IMC 2018): "around 32K active I2P peers in the network on a daily basis", "Of these peers, 14K are located behind NAT or firewalls"; reachable and unreachable peers each occupy "roughly half of the network"; ~2.7K floodfills/day; a censor "can block more than 95% of peer IP addresses known to a stable I2P client by operating only 10 routers" (paraphrase) — Hoang, Kintis, Antonakakis, Polychronakis, [An Empirical Study of the I2P Anonymity Network and its Censorship Resistance, IMC 2018](https://ar5iv.labs.arxiv.org/html/1809.09086).
- Herrmann & Grothoff (PETS 2011, tested "in early 2011 using I2P version 0.8.3"): attack "primarily based on exploiting I2P's performance-based selection of peers for tunnel construction, I2P's usage of unidirectional tunnels and the fact that Eepsites are located at a static location"; "Our attack requires a modest amount of resources; the only special requirement, to run I2P peers in several different /16" — [PDF](https://www.net.in.tum.de/fileadmin/bibtex/publications/papers/herrmann2011pet.pdf); venue per [TUM author page](https://net.cit.tum.de/members/grothoff/).
- Egger, Schlumberger, Kruegel, Vigna (RAID 2013, LNCS, DOI 10.1007/978-3-642-41284-4_22 per [FAU CRIS](https://www.cris.fau.de/publications/107714684/)): "an attacker, with relatively limited resources, is able to deanonymize a I2P user that accesses a resource of interest with high probability"; attack group of "20 conspiring nodes"; floodfill takeover needs "only 2 % of total nodes in the network"; "there are currently only 320 floodfill nodes active"; deanonymisation exploits that "Storage of peer information is done without a tunnel. That is, it is done in the clear" while "Storage verification, on the other hand, is done through an exploratory tunnel", giving "a probabilistic mapping between exploratory tunnel endpoints and the peers owning the tunnel"; detection ">80% probability when she accesses the site with p = 0.05", false positives "about 2.4%" — [PDF](https://sites.cs.ucsb.edu/~chris/research/doc/raid13_i2p.pdf).
- Wang, Ling, Xu, Pan, Liu, Luo, Fu, "Time will Tell: Large-scale De-anonymization of Hidden I2P Services via Live Behavior Alignment" (arXiv 2512.15510, submitted 17 Dec 2025; "Accepted to appear at ... NDSS 2026"): I2PERCEPTION uses attacker-run floodfills to collect RouterInfo passively and infer each router's join/leave ("on-off") pattern, then aligns it with a target hidden service's probed on-off pattern; "Through the deployment of only 15 floodfill routers over the course of eight months" it "successfully de-anonymizes all controlled hidden services" — [arXiv abstract](https://arxiv.org/abs/2512.15510). The test set was 10 controlled routers (5 Java, 5 C++), of which 2 Java and 2 C++ "are firewalled"; Appendix D "Firewalled Java Router Handler" states a firewalled router "must rely on introducers to accept incoming connections"; the paper notes the method lets "strong adversaries to focus active attacks (e.g., DoS, watermarking, fingerprinting) on a much smaller candidate pool" — [arXiv PDF](https://arxiv.org/pdf/2512.15510).
- LeaseSet structure: a LeaseSet holds the destination's keys and a group of leases, and each lease names the tunnel gateway router, a 4-byte tunnel ID and the tunnel's expiration; it is stored under a key derived from the destination's SHA256 hash by sending a store to "the floodfill that is closest to the current routing key"; whoever wants to contact a destination requests its LeaseSet from floodfills near that key; LeaseSets live at most 10 minutes (paraphrase except the quoted phrase) — [I2P network database](https://i2p.net/en/docs/overview/network-database). The Lease's first field is the "SHA256 Hash of the RouterIdentity of the gateway router"; for LeaseSet and LeaseSet2 (since 0.9.38) the lease data is not encrypted and is readable by netDb participants; EncryptedLeaseSet (working since 0.9.39) leaves only a blinded signing key, published time, expiration and flags in cleartext (paraphrase) — [I2P common structures spec](https://i2p.net/en/docs/specs/common-structures). For encrypted LeaseSets "The Destination is hidden, and only a blinded public key and an expiration are visible to the floodfill." and only holders of the full Destination can decrypt it (paraphrase) — [I2P network database](https://i2p.net/en/docs/overview/network-database).

### Inferences
- A browser router is, by construction, the "hidden"/"U" case: it cannot listen, cannot be introduced (no UDP), so it publishes no reachable address and cannot be a transit hop. By the I2P docs' own framing it therefore has the harvesting benefit of hidden mode only if it also does not publish a RouterInfo; it gets none of the cover-traffic benefit that the threat-model page attributes to the "over 95%" of users who relay.
- The 2013 and 2026 attacks do not need the victim to relay or to be reachable: Egger et al. exploit the client's own netDb store + exploratory-tunnel verification; Wang et al. explicitly include firewalled routers in the evaluated set. Hidden mode (no RouterInfo publication) removes the input of the 2026 attack (its traces are built from RouterInfo), but Egger-style lookups through exploratory tunnels and LeaseSet publication for the messenger's own destination remain. A browser router should be assumed to be at least as exposed as a native firewalled client.
- Population effect: if every browser router has the same distinctive RouterInfo shape (no addresses, same version/caps) and all enter via a few project nodes, the operator of those nodes (Design B) or any observer of their IPs can enumerate the entire browser population — "harvesting" becomes a list the project itself holds. The I2P docs' /16 and 33%-per-peer restrictions do not help when the client has exactly one possible first hop.
- Hidden mode hides the RouterInfo, not the LeaseSet. A messenger destination must publish a LeaseSet at least every 10 minutes, and each Lease names the inbound gateway router by hash. In Design B the gateway is always a project node, so every browser user's LeaseSet carries a project-node router hash: with plain LeaseSet2 it is readable by the closest floodfills (and by a Wang-style floodfill collector), and in every case by any correspondent who fetches it in order to send. The browser population is therefore enumerable at the LeaseSet layer regardless of RouterInfo hiding; EncryptedLeaseSet blinds this from floodfills but not from contacts.
- The "small candidate pool" point in Wang et al. applies directly: a population of a few hundred browser routers is a small candidate set for intersection/on-off alignment, and browser tab lifecycle (KQ3) makes on-off behaviour unusually crisp.

### Gaps
- Whether Java I2P or i2pd excludes "U"/"H" routers from tunnel-peer selection as an explicit rule could not be sourced; the peer-selection page only lists /16, 33%, low-bandwidth and recent-failure exclusions. The practical exclusion follows from unreachability (nobody can build through a router it cannot connect to), not from a documented rule.
- The current I2P `router.isHidden` / hidden-mode config key naming was only seen in an old Launchpad release note (secondary); not verified on current docs.
- Wang et al. do not, in the parts read, state whether hidden-mode routers (no RouterInfo) are fully outside the attack; this is inferred from the method's data source.
- Web search found no i2pd Emscripten/WebAssembly build and no in-browser I2P router (results were native i2pd, Docker images and Firefox proxy set-ups only); this is a null search result, not a sourced claim that none exists.
- No 2020–2024 peer-reviewed I2P deanonymisation paper was found besides the Dec 2025/NDSS 2026 one; the 2014–2018 literature found was surveys/measurement, not new attacks.

## KQ2. What the entry node learns: Design A (own-node TCP forwarder) vs Design B (NTCP2-over-WebSocket on a project node), compared with Tor guards, bridges and pluggable transports

### Takeaway
In Design B the project node is the NTCP2 responder, so by spec it receives the browser router's full RouterInfo and static key in handshake message 3 and, being the only reachable peer, is necessarily the first outbound hop and inbound gateway of every tunnel: it learns IP, router identity, session on/off times, and volume/timing of all traffic — strictly more than a Tor guard or bridge, which learn "this IP address is using Tor" and encrypted cells but no client identity. In Design A the user's own node forwards opaque NTCP2 bytes and the remote I2P routers see what they see from any native firewalled router (the user's IP), with no third party in the path. In Design B the LeaseSet additionally names the project node as inbound gateway, so contacts (and, without EncryptedLeaseSet, floodfills) learn the user's entry node.

### Cited Findings
- NTCP2 handshake: Alice's static key is sent in message 3 part 1 and Bob must check it "matches the static key in the Router Info"; message 3 part 2 payload is "Alice's RouterInfo and random padding", encrypted with "strong forward secrecy"; routers "must not rotate the static public key or IV while the router is up"; message 1 "can also be replayed, since there's no ephemeral contribution from the recipient" and the AES layer is "for DPI resistance only"; data-phase frame length "is obfuscated by XORing a mask derived from SipHash"; the data-phase padding scheme "is an area of future work" — [NTCP2 specification](https://i2p.net/en/docs/specs/ntcp2) (supported since 0.9.36; page undated).
- Tor's first hop: "A bad first of three servers can see encrypted Tor traffic coming from your computer." "It merely sees "This IP address is using Tor"." "It still doesn't know who you are and what you are doing over Tor." — [Tor: How is Tor different from other proxies?](https://support.torproject.org/about/how-is-tor-different-from-other-proxies/).
- Why Tor pins a guard (blog, 16 Oct 2013): without guards "an attacker who runs some relays would very quickly find himself as the first hop of one of the user's circuits"; simulation with an adversary holding 10% of guard capacity: three guards reach ~25% compromise quickly and over 80% by six months, one never-rotated guard stays under 25% at six months; recommendation to move to fewer guards and rotation of "a year or more" (paraphrase of numbers) — [Improving Tor's anonymity by changing guard parameters](https://blog.torproject.org/improving-tors-anonymity-changing-guard-parameters/).
- Bridges are "non-public Tor relays that aren't listed in the public directory" — [Tor support: censorship-7](https://support.torproject.org/censorship/censorship-7/); "relays in the network that are not listed in the public Tor directory", pluggable transports are "a special kind of bridge" adding "an extra layer of obfuscation" (paraphrase) — [Tor: Types of relays](https://community.torproject.org/relay/types-of-relays/).
- Pluggable Transports spec abstract: PTs are "a generic mechanism for the rapid development and deployment of censorship circumvention, based around the idea of modular sub-processes that transform traffic to defeat censors" — [pt-spec v1](https://spec.torproject.org/pt-spec/index.html).
- Snowflake (USENIX Security 2024; Bocovich, Breault, Fifield, Serene, Wang): proxies "are simple enough to be implemented in JavaScript, in a web page or browser extension"; "The main value of a Snowflake proxy is its IP address"; "an end-to-end secure channel between the client and the bridge, using keys unknown to the proxy. ... the DTLS of the data channel is only hop-by-hop, not end-to-end"; "not even the Snowflake bridge is trusted to know the contents or destinations of client streams"; "Proxies are trusted to deliver the client's traffic to the bridge, but do not themselves connect to the destination, or even know what it is." — [abstract page](https://www.usenix.org/conference/usenixsecurity24/presentation/bocovich), [PDF](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf).
- I2P's intersection/timing threat: "if an attacker is at both ends of your tunnel at the same time, he may be successful" — [I2P threat model](https://i2p.net/en/docs/overview/threat-model).
- Egger et al.: storing one's own RouterInfo/LeaseSet is "done without a tunnel ... in the clear, as the client is exposed by the content of the database entry anyways" — [RAID 2013 PDF](https://sites.cs.ucsb.edu/~chris/research/doc/raid13_i2p.pdf).
- The project's own plan already records that the Pages origin "https://gluckdev.github.io" covers all project sites on that origin, that hosting must never receive correspondence "even ciphertext", and that any local process can reach loopback and forge headers — [docs/plans/2026-10-31-web-local-mode.md](../../docs/plans/2026-10-31-web-local-mode.md) (local file).

### Inferences
- Design B entry node learns (by NTCP2 spec, not by choice): the client's IP; the router's identity (RouterInfo + static key) which is stable for the whole session and, if router keys persist in browser storage, across sessions and IP changes; every tunnel-build message as first hop/inbound gateway (layered-encrypted, so no destinations), hence exact tunnel count, lifetimes and per-tunnel byte/timing profiles; connection on/off times at sub-second precision. This is more than a Tor guard (no client identity in Tor) and far more than a Snowflake proxy (which carries only end-to-end ciphertext and never terminates the client's protocol). The right analogue is a Tor guard that the user did not pick at random and cannot rotate away from.
- If both correspondents of a chat use the same project node (likely with "a handful" of nodes), that operator is "at both ends" in the sense of the I2P threat model's intersection/timing attack — it can correlate the two users' send/receive timing without touching any encryption. Mitigations are only partial: several independent operators, randomised assignment, padding/cover traffic from the browser side.
- Design A entry node (the user's own forwarder) learns peer IPs, byte counts and timing — the same as the OS already knows for a native router; the NTCP2 keys never leave the browser, so the forwarder cannot read RouterInfos or tunnel messages. Remote I2P routers see the user's IP, as they do for any native firewalled router; there is no project-run third party in the path. The anonymity properties then collapse to those of a native hidden/firewalled i2pd (KQ1), plus the browser-specific risks (KQ3).
- Network-observer view: in Design A, traffic to many I2P peer IPs looks like ordinary I2P (NTCP2 has DPI-resistance padding but "area of future work" for data-phase padding); in Design B, all traffic goes over one WSS connection to a fixed project hostname/IP — the TLS SNI/IP is a usage fingerprint comparable to an unobfuscated bridge (Tor's own docs motivate PTs precisely because a fixed, known endpoint is blockable). GitHub Pages cannot host a WebSocket endpoint, so the project node is a separate, enumerable host.
- Third parties beyond the entry node: in Design B your correspondent learns which project node you use (the gateway hash in your LeaseSet), and with plain LeaseSets the floodfills nearest your destination key learn it too; in Design A the gateway is a randomly chosen I2P router, so the LeaseSet reveals nothing project-specific. EncryptedLeaseSet removes the floodfill leak in both designs but cannot hide the gateway from a contact.
- NTCP2 message 1 replayability and the stable static key mean a Design B node (or anyone observing it) can link a returning browser router even if IP changes, unless the router identity is regenerated per session.

### Gaps
- No Tor Project page fetched states in one sentence "the bridge operator learns your IP"; the support page's "this IP address is using Tor" is the closest primary text. Tor's client-anonymous TLS handshake (no client identity to the guard) is well known but was not separately sourced here.
- No source quantifies I2P tunnel-level traffic-confirmation success for a first-hop adversary; the claim is qualitative (threat-model page).
- The exact set of tunnel metadata visible to an I2P first hop (hop count? no; tunnel ID and next hop: yes) is standard I2P design but was not re-verified against the tunnel-creation spec in this pass.

## KQ3. Browser-specific side channels, fingerprinting and trust in the hosting origin and browser profile

### Takeaway
Browsers coarsen timers to 100 µs (5 µs only with COOP/COEP cross-origin isolation), throttle hidden tabs to 1 Hz and then one wake-up per minute, and freeze or discard them "at their discretion"; GitHub Pages cannot set any custom HTTP header, so a Pages-hosted router cannot be cross-origin isolated (no SharedArrayBuffer/wasm threads, meta-only CSP, no COOP/COEP) and its liveness is dictated by tab visibility — a clean on/off signal to its NTCP2 peer. Extensions with host permission on the origin can read the DOM and inject main-world scripts, WebRTC local-IP leaks are mitigated by mDNS since Chrome 76 but STUN-reflexive public IPs remain, and WebCrypto's own spec equates script injection with remote code execution and promises no protection of key material on disk.

### Cited Findings
- `performance.now()` "is coarsened based on whether or not the document is cross-origin isolated": "Resolution in isolated contexts: 5 microseconds", "Resolution in non-isolated contexts: 100 microseconds" — [MDN Performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now). Chromium's "Intent to Ship: Align performance API timer resolution to cross-origin isolated capability" (17 Mar 2021) moved desktop "from 5 microseconds to 100 microseconds in non-isolated contexts" and states "Reducing timer granularity in non-isolated contexts increases security" — [blink-dev thread](https://groups.google.com/a/chromium.org/g/blink-dev/c/k6M3HJiqmkE/m/zgaVyKfnAwAJ). Firefox reduced `performance.now()` to 20 µs in Firefox 57 and disabled SharedArrayBuffer by default in response to "Meltdown and Spectre" (3 Jan 2018) — [Mozilla Security Blog](https://blog.mozilla.org/security/2018/01/03/mitigations-landing-new-class-timing-attack/).
- Cross-origin isolation requires `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Opener-Policy: same-origin` on the main document; "Some web APIs increase the risk of side-channel attacks like Spectre"; SharedArrayBuffer ("Required for WebAssembly threads") is disabled on Chrome desktop without isolation from Chrome 92; high-resolution timers "can be 5 microseconds or higher" only with isolation — [web.dev: COOP and COEP](https://web.dev/articles/coop-coep) (published 13 Apr 2020, updated 21 Jun 2022).
- GitHub Pages headers: in reply to a request for CSP and other headers on Pages, user yoannchaudet wrote on 2 May 2023: "We don't support this feature today so a `meta` tag unfortunately is the only way." — [GitHub Community discussion #54257](https://github.com/orgs/community/discussions/54257) (role not shown on the page; GitHub-staff status unverified). A separate request to allow COOP/COEP on Pages remains open without ETA (paraphrase) — [discussion #13309](https://github.com/orgs/community/discussions/13309).
- Chrome 88 timer throttling (page last updated 18 Jan 2021): intensive throttling (timers checked "once per minute") applies when the page has been hidden > 5 minutes, chain count ≥ 5, silent ≥ 30 s and "WebRTC is not in use"; otherwise hidden pages get 1 Hz; an open `RTCDataChannel` or live `MediaStreamTrack` exempts from intensive (not standard) throttling; WebSocket treatment is not documented beyond a test flag — [Chrome Developers blog](https://developer.chrome.com/blog/timer-throttling-in-chrome-88).
- Page Lifecycle (last updated 16 Oct 2026): browsers "already occasionally freeze and discard hidden tabs (at their discretion)"; when frozen, "things like JavaScript timers and fetch callbacks don't run"; when discarded, "No tasks, event callbacks, or JavaScript of any kind can run"; Chrome is conservative about discarding pages that use WebRTC, play audio or show alerts — [Chrome Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api).
- WebRTC local-IP leak mitigation: Chrome PSA (14 Aug 2019) — private IPs in ICE host candidates replaced by mDNS `.local` names, full rollout in Chrome 76; sites granted getUserMedia permission still receive real IPs (paraphrase) — [discuss-webrtc PSA](https://groups.google.com/g/discuss-webrtc/c/6stQXi72BEU/m/2FwZd24UAQAJ). The IETF draft behind it ("Using Multicast DNS to protect privacy when exposing ICE candidates", last rev 2021-12-06) is expired/Informational; it conceals local addresses only: "these addresses are typically private and, as such, their disclosure has privacy implications" — [draft-ietf-mmusic-mdns-ice-candidates](https://datatracker.ietf.org/doc/draft-ietf-mmusic-mdns-ice-candidates/).
- Extensions: "Content scripts can access and modify the page's DOM, just like normal page scripts can."; "content scripts can only access page content when host permissions for the web page's origin are granted."; they get a "clean" DOM view and "cannot see JavaScript variables defined by page scripts" but can bridge via `window.postMessage` and, in Firefox, `cloneInto()`/`exportFunction()` — [MDN Content scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Content_scripts). Chrome: "Content scripts live in an isolated world"; the `world` option "Defaults to `ISOLATED`" and "When a content script is injected into the main world, the CSP of the page applies" — [Chrome content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts).
- WebCrypto (W3C Recommendation 26 January 2017): "issues such as script injection are the equivalent to remote code execution in other operating environments" and "allowing hostile script to be injected may allow for the exfiltration of keys or data"; the API "does not guarantee that the underlying cryptographic key material will not be persisted to disk, possibly unencrypted" — [W3C WebCryptoAPI REC](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/). `CryptoKey.extractable` only controls `exportKey()`/`wrapKey()` — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey/extractable).
- WebCrypto algorithm coverage: the current draft (First Public Working Draft 22 April 2025) lists RSA, ECDSA/ECDH, Ed25519, X25519, AES-CTR/CBC/GCM/KW, HMAC, SHA, HKDF, PBKDF2; ChaCha20-Poly1305 does not appear in the portion read — [W3C WebCryptoAPI draft](https://www.w3.org/TR/WebCryptoAPI/). Secure-curve shipping: Ed25519 in Chrome 137 (May 2025) per [IPFS blog](https://blog.ipfs.tech/2025-08-ed25519/); Firefox 130 shipped Ed25519+X25519 by default and WebKit enabled X25519 Dec 2024 per [Igalia blog](https://blogs.igalia.com/jfernandez/?p=1913) (one secondary source says Firefox 129; conflict unresolved).
- Spectre vs wasm: "Swivel: Hardening WebAssembly against Spectre" (USENIX Security 2021) states Spectre attacks can bypass Wasm's isolation guarantees and proposes compiler hardening with 3.3%–240% overhead for deterministic variants (paraphrase of abstract) — [USENIX page](https://www.usenix.org/conference/usenixsecurity21/presentation/narayan). "CT-Wasm" (Watt, Renner, Popescu, Cauligi, Stefan; DOI 10.1145/3290390, i.e. POPL 2019) proposes a typed Wasm extension precisely because ordinary JS/Wasm crypto is not verifiably "resistant to timing side channel attacks" (paraphrase) — [arXiv 1808.01348](https://arxiv.org/abs/1808.01348).
- The project plan already states the Pages origin covers all project sites, fragments with tokens land in browser history/sync, and "a compromised browser profile/extension sees plaintext" (translated) — [docs/plans/2026-10-31-web-local-mode.md](../../docs/plans/2026-10-31-web-local-mode.md).

### Inferences
- Tab lifecycle is the browser-specific timing signal that matters most for an I2P router, not high-resolution timers: after 5 minutes hidden the router's timers tick once a minute (unless it holds a WebRTC data channel, which would be a hack with its own fingerprint), and a freeze/discard stops it entirely. Its NTCP2 peer (the project node in Design B, arbitrary routers in Design A) observes a crisp on/off pattern correlated with the user's foreground activity — the same kind of "live behaviour" Wang et al. exploit, but at tab-switch granularity. Tunnels and LeaseSets expire on ~10-minute timescales (Egger et al. note "service information expires after ten minutes"), so they lapse during freezes and reconnection bursts are visible.
- A Pages-hosted page cannot be cross-origin isolated (no COOP/COEP headers), so: no SharedArrayBuffer/wasm threads (single-threaded router), only 100 µs timers (irrelevant to the router itself; it also denies a co-located attacker page nothing, since an attacker can isolate its own origin), and CSP only via `<meta>` (no `frame-ancestors`/`report-uri`). The coi-serviceworker header-injection shim exists but is a workaround with known breakage (secondary, see discussion #54257).
- Any extension with host permission for `*.github.io` (ad blockers, password managers, "AI assistants") can read every rendered message and inject main-world code that holds references to the wasm instance and its linear memory; "extractable: false" WebCrypto keys would not help for NTCP2/I2P crypto anyway because ChaCha20-Poly1305 and I2P's AES/ElGamal/EdDSA formats mean most keys must live in wasm memory, not in WebCrypto. The browser profile is the trust boundary; WebCrypto's spec says as much.
- WebRTC is not needed by the router; the mDNS mitigation only matters if the page (or a co-hosted script) opens an RTCPeerConnection — the project should simply not use WebRTC, which also keeps the Chrome-88 exemption fingerprint away.
- Trust in the hosting origin is not reducible by SRI/CSP (KQ4): all code is first-party from Pages; a push to the repo or a GitHub-side compromise changes the client for everyone, or for targeted users if served conditionally (GitHub Pages is static, which limits per-user targeting to what the attacker can do client-side).

### Gaps
- Firefox's current default timer precision (100 µs vs 1 ms) and its cross-origin-isolated value (20 µs per the Chromium thread) were only seen in secondary/localised MDN text and a test file; not confirmed from a current primary page.
- Chrome Site Isolation / Firefox Fission process-per-site details (which bound in-process Spectre reads from a hostile site to the router's memory) were not fetched in this pass.
- Whether `github.io` is on the Public Suffix List (which decides whether cookies/storage are isolated between different users' Pages sites) was not verified.
- Safari/WebKit background-tab policies and iOS Safari tab suspension were not researched.

## KQ4. The "JavaScript cryptography considered harmful" debate in 2026: original objections, what WebCrypto/SRI/CSP/wasm changed, and how current web E2EE apps justify their trust model

### Takeaway
The 2011 Matasano and 2013 Arcieri objections reduce to one that is still unsolved in 2026: the server that serves the code can serve different code, and nothing in the browser pins or signs a web app. WebCrypto (REC 2017) and SRI (REC 2016) address runtime quality and third-party resource tampering respectively, not first-party code delivery; the projects that ship web E2EE today (Proton, CryptPad, Element, WhatsApp Web) say so in their own threat models, and only WhatsApp's Code Verify extension (2022) attempts out-of-band verification. Signal never shipped a web page client (Chrome App 2015 → standalone 2017).

### Cited Findings
- "Javascript Cryptography Considered Harmful" (Matasano, originally at matasano.com/articles/javascript-cryptography/) was posted to Hacker News on 28 Aug 2011; the author (tptacek) summarised in the thread that when the server supplies the crypto code, "the server can read the plaintext no matter what", and that "not every good programming environment is going to be suitable for cryptography" — [HN thread](https://news.ycombinator.com/item?id=2935220). The NCC Group mirror URL cited by third parties returned 404 on nccgroup.com in this pass. Paragonie (Oct 2019) wrote: "It's been more than eight years since Javascript Cryptography Considered Harmful was published. It's just as true today ... that JavaScript cryptography in a web browser is dangerous." — [Paragonie blog](https://paragonie.com/blog/2019/10/improving-cryptography-javascript-ecosystem/source).
- Tony Arcieri, "What's wrong with in-browser cryptography?" (30 Dec 2013): browsers run whatever JavaScript the server sends, with no signature check, so a compromised server, insider, government order or targeted injection can change the code at any time; audits give little protection because the code can change after the audit; WebCrypto "does not address this"; recommends browser extensions (signed updates) or reproducible native binaries (paraphrase) — [tonyarcieri.com](https://tonyarcieri.com/whats-wrong-with-webcrypto).
- W3C Web Cryptography API became a Recommendation on 26 January 2017; its Security Considerations equate script injection with remote code execution and warn that injected script "may allow for the exfiltration of keys or data" — [W3C REC](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/).
- Subresource Integrity became a Recommendation on 23 June 2016; integrity metadata "only protects an origin against a compromise of the server where an external resources is hosted" — [W3C SRI REC](https://www.w3.org/TR/2016/REC-SRI-20160623/); a new SRI Working Draft is dated 20 March 2026 — [W3C SRI WD](https://www.w3.org/TR/SRI/).
- WhatsApp Code Verify (Meta Engineering, 10 Mar 2022; extended to Messenger 11 Aug 2022 and Instagram Web 16 Jun 2023): a browser extension that compares the JavaScript served to the browser against a hash reference WhatsApp gave Cloudflare; green/orange/red states; extension "doesn't log data, doesn't read your messages, and never sends chats to Cloudflare"; open source at facebookincubator/meta-code-verify (paraphrase) — [engineering.fb.com](https://engineering.fb.com/2022/03/10/security/code-verify/).
- CryptPad threat model (Theo von Arx, 16-03-2023): the server is assumed "honest-but-curious", i.e., "the server behaves according to the protocol"; "The users must consequently trust the server to provide the correct application" and "no security guarantees can be established otherwise" — [CryptPad Blueprints: Threat Model](https://blueprints.cryptpad.org/document/threatmodel/). CryptPad blog (14 Mar 2024): "If you receive bogus code from this server, you cannot establish any security" and "you must trust the server to not run any active attacks" — [Most Secure CryptPad Usage](https://blog.cryptpad.org/2024/03/14/Most-Secure-CryptPad-Usage/). CryptPad signed its JS with a manifest in 2018 and admitted the root HTML can still subvert the chain (secondary summary of [Signing CryptPad, 15 Jun 2018](https://blog.cryptpad.org/2018/06/15/Signing-CryptPad/)); its "Reduce trust on server" blueprint proposes TOFU warnings when client code changes — [blueprint](https://blueprints.cryptpad.org/document/recommendations/reduce_trust_on_server/) (not fetched; from search summary).
- Proton (20 Jan 2019): the web-app-swap concern "applies to any web app in existence today", naming WhatsApp, Wire, Tresorit and Threema; Proton says the weaker guarantees of web apps are discussed in its published threat model, that it offers native apps on every platform, and that it is "following web standards work on code signing for web apps" (paraphrase) — [Proton blog](https://proton.me/blog/cryptographic-architecture-response). A Proton engineer's FOSDEM 2020 talk "Building a Web App that Doesn't Trust the Server" argues open-source clients are necessary but not sufficient and describes Source Code Transparency and Key Transparency projects (secondary summary) — [FOSDEM 2020](https://archive.fosdem.org/2020/schedule/event/dip_securing_protonmail/).
- Element Web README "Important Security Notes": "We do not recommend running Element from the same domain name as your Matrix homeserver." (XSS from user-generated content gaining the app's origin); recommends `X-Frame-Options: SAMEORIGIN`, CSP `frame-ancestors 'self'`, `X-Content-Type-Options: nosniff` — [apps/web/README.md](https://github.com/element-hq/element-web/blob/develop/apps/web/README.md); the section was added in 2021 by PR #16367 (mirror of the commit: [riot-web #16367](https://eugit.opencloud.lu/OpenCloud/riot-web/commit/4acdb7c715db3882ab467c02df59971e092749de)). Install docs: serve over HTTPS; releases are GPG-signed — [docs/install.md](https://github.com/element-hq/element-web/blob/develop/docs/install.md).
- Signal Desktop launched as "a Chrome app which links with your phone" on 2 Dec 2015 — [signal.org](https://signal.org/blog/signal-desktop/) — and became a standalone desktop app on 31 Oct 2017 because "the Chrome App has been deprecated"; no security rationale is given in either post — [signal.org](https://signal.org/blog/standalone-signal-desktop/). A widely quoted Signal explanation ("there's no way to version, sign and securely distribute a web page ... reduces the security of your end-to-end encrypted communication to that of your SSL connection to the server") appears only in forum posts (e.g. [Opera forums](https://forums.opera.com/post/252035)); no primary Signal page containing it was found.
- The project's own plan concedes the point: not sending correspondence to the host "is a property of current routes/code, not a defence against substitution of trusted JS", and recommends a locally served UI for minimal hosting trust (translated) — [docs/plans/2026-10-31-web-local-mode.md](../../docs/plans/2026-10-31-web-local-mode.md).

### Inferences
- What changed since 2011: the runtime objections (no CSPRNG, no constant-time primitives, no key isolation) are largely answered by WebCrypto + wasm; the delivery objection is not. SRI and CSP protect against compromised third-party hosts and injection, respectively; neither helps when the first party (the Pages repo/GitHub) is the adversary or is coerced. Code Verify is the only deployed answer and it requires (a) a second party holding the hash and (b) an extension the user installs — i.e., a native, signed component after all.
- Reproducible builds help only if someone compares the served bytes to the reproducible output; on a static host that means publishing per-release hashes out of band (release notes, signed tags) and, ideally, a verifier extension or a service-worker that refuses unknown bundle hashes (TOFU), as CryptPad proposes. GitHub Pages' static nature makes per-user targeting harder than on a dynamic server but does not prevent a repo-level swap.
- For an I2P router specifically, the stakes are higher than for mail: a swapped bundle can leak not only plaintext but router identity, peer lists and tunnel keys — i.e., de-anonymise, not just decrypt.

### Gaps
- The full original text of the Matasano essay could not be fetched (NCC Group URL 404; web.archive.org blocked for this tool); arguments are cited via the author's HN comments and Arcieri's independent post.
- Proton's referenced threat-model page and Source Code Transparency status in 2026 were not fetched.
- No primary Signal statement explaining the absence of a web client was found.

## KQ5. Precedents: did Tor-, I2P- and mixnet-based privacy messengers ship web/PWA clients, with what architecture, and what did they say?

### Takeaway
No Tor- or I2P-based privacy messenger (Session, SimpleX, Cwtch, Briar, Quiet, Ricochet, I2P-Bote) ships a hosted web/PWA client as of 2026; the only browser efforts are an abandoned unofficial Session Web (archived Sep 2025, needed a CORS/TLS proxy and lacked onion routing), Quiet's post-1.0 roadmap item "Browser Support via Arti-in-WASM", Delta Chat Desktop running its React UI in Firefox/Safari against a local process (2025), and Matrix's 2020 Dendrite-in-wasm demo. The overlay projects that do run in browsers — Nym (wasm client in a Web Worker over WebSocket to an entry gateway) and Veilid (veilid-wasm, WebSocket-only, needs an inbound relay) — are exactly Design B: a wasm node whose only transport is a WebSocket to an operator-run entry.

### Cited Findings
- Session: official docs list only "Android, iOS, Windows, Mac, Linux" (paraphrase) — [docs.getsession.org](https://docs.getsession.org/). Unofficial "session-web" (VityaSchel): repository "was archived by the owner on Sep 14, 2025"; README calls it experimental, "not maintained for security vulnerabilities found in code or dependencies", notes MITM is not prevented, backend requests "aren't onion routed", no certificate pinning; a proxy is required because nodes use self-signed certificates and "Nodes do not send CORS headers, which prevent reading responses"; PWA is on the feature list — [github.com/VityaSchel/session-web](https://github.com/VityaSchel/session-web).
- SimpleX Chat: no web client found; users request one in community threads (e.g. [Disroot/Lemmy thread](https://scribe.disroot.org/post/10284183)); the SimpleX FAQ URL fetched returned 404 and no official statement on a browser client was located.
- Cwtch: peer-to-peer over Tor; offline/group delivery uses "untrusted Cwtch servers which can host messages for a group"; messages are encrypted with the group key and fetched via ephemeral onions so the server cannot tell which groups or who; server hosting is Desktop-only (paraphrase) — [docs.cwtch.im: Servers](https://docs.cwtch.im/docs/servers/introduction). No web client found.
- Briar: offline delivery via Briar Mailbox, "a helper app for Briar messenger" installed on "a spare Android device" the user owns, linked by QR code (paraphrase) — [briarproject.org](https://briarproject.org/download-briar-mailbox/); on F-Droid since 2024-04-12, v1.0.9 added 12 Aug 2024 — [F-Droid](https://f-droid.org/en/packages/org.briarproject.mailbox/). Briar Desktop exists as beta; no web client found (FAQ page 404 in this pass).
- Quiet: "Encrypted p2p team chat with no servers, just Tor."; peers connect via Tor onion services; Electron desktop (Mac/Windows/Linux), Android, iOS (TestFlight); under "Post-1.0 Features" it lists "Browser Support" for joining "with any modern browser, via Arti-in-WASM" and "Tor Browser Support" (paraphrase) — [github.com/TryQuiet/quiet](https://github.com/TryQuiet/quiet) (read 2026-11-01; no release date visible).
- Delta Chat: the desktop monorepo has a `target-browser` package (Express server + WebSocket) described as mainly for development/testing (secondary: [DeepWiki architecture](https://deepwiki.com/deltachat/deltachat-desktop/2-architecture)); May 2025 reports that Delta Chat Desktop "can now run on Firefox and Safari, entirely avoiding Electron and Chromium" via the Tauri effort, with a blog post (delta.chat, 2025-05-22) on what is missing "for a full Web version" (secondary: [AlternativeTo news](https://alternativeto.net/news/2025/5/delta-chat-desktop-now-runs-in-firefox-and-no-longer-depends-on-electron-or-chromium)); NLnet's DeltaTauri grant page calls Tauri "an important stepping stone towards a potential Delta Chat Web client" — [nlnet.nl](https://nlnet.nl/project/DeltaTauri/). No hosted web client shipped as of the sources found.
- I2P-Bote: "a serverless, encrypted e-mail application" delivered as an I2P plugin with a "Themeable webmail interface" (router-console-hosted or standalone WAR under Tomcat) and IMAP/SMTP; repository "was archived by the owner on Jan 10, 2026" — [github.com/i2p/i2p.i2p-bote](https://github.com/i2p/i2p.i2p-bote). Its web UI is served by the local router, not a remote host.
- Matrix P2P demo (2 Jun 2020): Dendrite compiled to WebAssembly running "embedded in Riot Web as a Service Worker"; transport HTTP over libp2p's websocket transport via a websocket rendezvous server (WebRTC future work); storage in IndexedDB; no "store and forward" for offline devices; demo at p2p.riot.im, explicitly "very likely **not** what the final version of P2P Matrix will look like" — [matrix.org blog](https://matrix.org/blog/2020/06/02/introducing-p2p-matrix/).
- Nym (docs last updated 27 Oct 2026): browsers/WebViews "offer only WebSockets and `fetch`, under mixed-content rules", so the SDK runs a WASM client inside a Web Worker; "The mixnet behaviour is identical in both modes, only the integration shape differs"; the dVPN client "has no WebAssembly build"; "The mixnet anonymises the sender; protecting the payload (TLS, Noise) is your application's job" — [nym.com/docs/developers/browsers](https://nym.com/docs/developers/browsers). mixFetch tunnels requests through the WASM client over a WebSocket to an entry gateway (secondary summary) — [nym.com/docs/developers/mix-fetch](https://nym.com/docs/developers/mix-fetch).
- Veilid: `veilid-wasm` generates WebAssembly bindings for `veilid-core::VeilidAPI`; in the browser the only transport is WebSockets (no TCP/UDP), `wss://` only on HTTPS pages; browser nodes cannot open ports, so a WASM node selects another node as its Inbound Relay; no DNS, so bootstrap must be a direct WebSocket URL (e.g. `ws://bootstrap-v1.veilid.net:5150/ws`); planned Outbound Relays not implemented (paraphrase) — [veilid-wasm README](https://gitlab.com/veilid/veilid/-/raw/main/veilid-wasm/README.md). Veilid was released 11 Aug 2023 at DEF CON 31 (secondary: [Wikipedia](https://www.wikipedia.org/wiki/Veilid)).
- Snowflake is the precedent for a browser-resident *relay* (volunteer proxies in JS/WebExtension) rather than a browser-resident client; see KQ2 — [USENIX Security 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/bocovich).
- No wasm/Emscripten build of i2pd or Java I2P, and no in-browser I2P router, was found (KQ1).

### Inferences
- The consistent pattern among Tor-based messengers is: native app + optional user-owned or untrusted offline relay (Briar Mailbox on the user's own device; Cwtch servers that store only group-key ciphertext). None has accepted a hosted web client; the one that plans it (Quiet) ties it to a wasm Tor client (Arti) — the same bet this project is making with I2P.
- The Session Web post-mortem is the most instructive: a browser cannot speak directly to overlay nodes (self-signed TLS, no CORS), so an operator proxy appears, onion routing is dropped, and the unmaintained result is archived — every one of those steps is a Design B consequence.
- Nym and Veilid demonstrate that a wasm client with WebSocket-only transport is technically routine, and both documentation sets quietly accept an operator-run entry (gateway / inbound relay) as the price — they are honest that the browser node is a client of a relay, not a peer.

### Gaps
- Ricochet Refresh was not fetched; it is desktop-only to my knowledge but this is unverified here.
- No primary statement from SimpleX, Cwtch or Briar maintainers explicitly refusing a web client was found; absence is inferred from platform lists.
- Delta Chat's 2025-05-22 blog post could not be fetched (URL unknown/404); its content is cited via secondary reports.
- Nym's gateway-side knowledge of browser clients (IP, credential linkage) is not described on the pages fetched.

## KQ6. Recommendations: what such a project can honestly promise and must not, and which mitigations are standard

### Takeaway
The honest promise is "end-to-end encrypted messaging whose client runs in your browser; your IP and router identity are known to the project's entry node (Design B) or to the I2P routers you contact (Design A); the hosting never receives message content, but you are trusting the hosting to serve honest code every time you load the page". The project must not claim Tor/I2P-grade anonymity, protection from a malicious host, or protection from browser extensions/profile compromise. Standard mitigations exist for each gap and each has a precedent.

### Cited Findings
- Hidden-mode trade-off and harvesting weakness as documented by I2P — [threat model](https://i2p.net/en/docs/overview/threat-model), [restrictive countries](https://i2p.net/en/docs/overview/restrictive-countries) (KQ1).
- NTCP2 responder learns the initiator's RouterInfo; static key stable while up — [NTCP2 spec](https://i2p.net/en/docs/specs/ntcp2) (KQ2).
- Tor pins one guard deliberately and documents what the first hop learns — [guard blog 2013](https://blog.torproject.org/improving-tors-anonymity-changing-guard-parameters/), [Tor FAQ](https://support.torproject.org/about/how-is-tor-different-from-other-proxies/) (KQ2).
- Snowflake keeps the proxy untrusted via an end-to-end layer "using keys unknown to the proxy" — [USENIX 2024 PDF](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf) (KQ2).
- Hosting cannot set headers on GitHub Pages — [discussion #54257](https://github.com/orgs/community/discussions/54257) (KQ3).
- Code delivery is the unsolved problem; CryptPad and Proton say so in their threat models; Code Verify is the deployed out-of-band verifier — [CryptPad threat model](https://blueprints.cryptpad.org/document/threatmodel/), [Proton 2019](https://proton.me/blog/cryptographic-architecture-response), [Code Verify](https://engineering.fb.com/2022/03/10/security/code-verify/) (KQ4).
- Offline delivery via user-owned or untrusted relays: Briar Mailbox on the user's own device — [briarproject.org](https://briarproject.org/download-briar-mailbox/); Cwtch servers storing only group-key ciphertext — [docs.cwtch.im](https://docs.cwtch.im/docs/servers/introduction) (KQ5).
- Tab throttling/freezing stops the router — [Chrome 88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88), [Page Lifecycle](https://developer.chrome.com/docs/web-platform/page-lifecycle-api) (KQ3).
- Owner's existing rules in this repo: no plaintext to hosting, local UI for minimal hosting trust, tests and docs for every feature — [docs/plans/2026-10-31-web-local-mode.md](../../docs/plans/2026-10-31-web-local-mode.md).

### Inferences
- Can promise (with sources behind each): message content and attachments are E2EE and never reach GitHub or the project node; the project node (Design B) sees only NTCP2 ciphertext; no third party is in the path in Design A; no telemetry (verifiable in a static bundle); reproducible bundle with published hashes.
- Must not promise: sender/receiver anonymity against the project node operator or against anyone who can observe it (Design B) — that operator is a non-rotating guard that also knows router identity; anonymity against I2P-level floodfill/Sybil adversaries beyond what a native firewalled i2pd gets (and the browser population is smaller and more distinctive); safety against a malicious or coerced host (the served code is the root of trust); safety against extensions or a compromised profile; availability while the tab is in the background (freezing); that contacts or floodfills cannot tell which entry node you use (Design B: the LeaseSet's gateway hash is a project node, visible to every correspondent and, unless EncryptedLeaseSet is used, to floodfills).
- Standard mitigations, each with a precedent in the findings:
  1. Keep the entry node untrusted the Snowflake way: end-to-end keys the entry never has (true in NTCP2 beyond the first hop), plus **several independent operators and a user-selectable/randomised entry**, so one operator is not "at both ends"; document it exactly as Tor documents guards. Use EncryptedLeaseSet so floodfills do not learn the gateway, and state that contacts still do.
  2. **Per-session router identity** (regenerate RouterInfo/static key on load, no persistence) to deny cross-session linkage by the entry node — at the cost of peer profiles, which a browser client barely uses anyway. Note this does not help if the messenger's own destination keys are stable (they must be); linkage then moves to the LeaseSet layer.
  3. **Relay-side offline mail** on infrastructure that stores only ciphertext addressed to opaque destinations (Cwtch model) or on a user-owned device (Briar Mailbox model); never on the Pages origin.
  4. **No plaintext to hosting, enforced structurally**: static bundle, meta-CSP with `connect-src` restricted to the loopback/WSS endpoints, no analytics, and tests that assert no network egress other than the router transport (consistent with the repo's "no plaintext to hosting" rule).
  5. **Reproducible builds + pinned hashes**: publish bundle hashes per release in signed tags/release notes; serve `integrity` attributes for every sub-resource (SRI covers the sub-resources, not `index.html`); consider a Code-Verify-style verifier (extension or a service-worker TOFU check) for the root document, while stating plainly that without it the host is trusted on every load (CryptPad's wording is a good template).
  6. **Do not use WebRTC**; avoid the Chrome-88 throttling exemption hack; instead detect `freeze`/`visibilitychange` and surface "router paused" honestly, and size tunnel/LeaseSet lifetimes so reconnection after background is fast.
  7. **Opt-in only, telemetry-free, and a plain-language threat statement in the app** listing the three parties that learn something (hosting: that you loaded the page; entry node: your IP, router identity, timing; I2P floodfills: your destination's LeaseSet) — mirroring the "what the first server sees" style of the Tor FAQ.
  8. Keep the **native-process bridge (Design A)** as the recommended mode for anyone with an anonymity need, and label the pure-browser mode as convenience/E2EE-only; this is what Proton does with native apps and what Quiet plans with Arti-in-WASM.

### Gaps
- No quantitative basis was found for how many independent entry operators or what padding regime would make Design B's "both ends" correlation impractical; the literature cited is qualitative for I2P.
- No deployed example of a service-worker-based bundle-hash TOFU verifier was located (CryptPad's is a proposal); feasibility on GitHub Pages (service workers are allowed; headers are not) is untested here.
- Legal/coercion exposure of a project-run entry node (logs, subpoena) was outside scope and not researched.
