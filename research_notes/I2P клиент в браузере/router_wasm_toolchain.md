# Compiling an I2P router to WebAssembly for a GitHub-Pages-served browser page: toolchain facts, crypto cost, netDb bootstrap

Research date: 2026-11-01. All version numbers and dates are as found on that day. "Local probe" marks measurements made from this machine during the research session; "inference" marks the researcher's reasoning rather than a sourced fact. Repo-internal facts cite absolute file paths in `/home/artamonov/projects/gipny-i2pd`.

## Key question 1 — Emscripten path: porting the C++ i2pd router (Boost, OpenSSL, zlib, sockets, pthreads, Asyncify/JSPI, sizes, precedents)

### Takeaway
Every building block exists in isolation (Boost headers and zlib are Emscripten ports, OpenSSL builds with `emconfigure ... no-asm no-threads`, TCP is emulated over WebSocket with a websockify-style bridge), but the combination i2pd needs — Boost.Asio reactor + pthreads + blocking `select()` — is exactly where Emscripten is weakest: Asio's `select()` loop is a live open bug under the WebSocket emulation (Nov 2025), pthreads require cross-origin isolation that GitHub Pages cannot provide natively (only via a service-worker hack with a Safari-specific fallback), UDP (SSU2) is impossible, and i2pd's maintainers declined a wasm target in 2023 citing pthreads. No published Emscripten port of a comparable Boost.Asio/OpenSSL daemon was found.

### Cited Findings

**Emscripten state in 2026**
- Current Emscripten release is 6.0.13 (2026-10-19); 6.0.12 (2026-10-08), 6.0.11 (2026-10-02), 6.0.10 (2026-09-21), 6.0.8 (2026-08-20) precede it. — [Emscripten ChangeLog](https://github.com/emscripten-core/emscripten/blob/main/ChangeLog.md)
- In 6.0.8 (2026-08-20): "The `JSPI` setting is no longer considered experimental, and the compiler diagnostic warning has been removed. (#27559)"; the same release added `epoll` support (`epoll_create1`/`epoll_ctl`/`epoll_wait`). 6.0.12 added a zero-timeout `epoll_wait` path "without an `ASYNCIFY`/`JSPI` requirement". — [Emscripten ChangeLog](https://github.com/emscripten-core/emscripten/blob/main/ChangeLog.md)
- `-sUSE_PTHREADS` and `-sMEMORY64` are deprecated in favour of `-pthread` and `-m64` / `--target=wasm64` (#27025). — [Emscripten ChangeLog](https://github.com/emscripten-core/emscripten/blob/main/ChangeLog.md)

**Sockets**
- By default Emscripten emulates POSIX TCP over WebSockets; the docs say "This emulation is not very complete at the moment" and "you will need to use something like WebSockify on the server side." Configured with `-sWEBSOCKET_URL` and `-sWEBSOCKET_SUBPROTOCOL` (`binary`/`text`). — [Emscripten networking docs](https://emscripten.org/docs/porting/networking.html)
- "Direct UDP communication is not available in browsers." WebRTC Data Channels are named as the closest alternative, but "Currently Emscripten does not provide a C/C++ API for interacting with WebRTC." — [Emscripten networking docs](https://emscripten.org/docs/porting/networking.html)
- Full POSIX sockets proxy: link with `-lwebsocket.js -sPROXY_POSIX_SOCKETS -pthread -sPROXY_TO_PTHREAD`; a native bridge lives in `tools/websocket_to_posix_proxy/` and performs real TCP/UDP on the page's behalf. Limits stated: it "requires multithreading and proxying the application `main()` to a pthread"; "Because all API calls are individually proxied, this support can be slow"; it is "mostly useful for developing testing infrastructure and debugging"; `poll()`, `close()` (use `shutdown()`) and `select()` are not proxied. — [Emscripten networking docs](https://emscripten.org/docs/porting/networking.html)
- Boost.Asio under the default WebSocket emulation: Emscripten issue #25759 "`select`/`poll` with timeout does not block" (opened 2025-11-10, still open) reports "an infinite `select()` loop in `boost::asio` sockets … because the syscall does not use the timeout. We're using the default emulated TCP over web sockets implementation. `select()` is called on a PThread." Triage on 2026-06-15 suspected a fix in commit 8694832; the reporter replied "Probably for some cases, but this did not work for WebSockets." — [emscripten-core/emscripten#25759](https://github.com/emscripten-core/emscripten/issues/25759)

**pthreads, SharedArrayBuffer, cross-origin isolation, GitHub Pages**
- Emscripten pthreads rely on SharedArrayBuffer; "Pthreads code will not work in deployed environment unless these headers are correctly set" (COOP/COEP). Flags: `-pthread` on compile and link, `-sPTHREAD_POOL_SIZE`, `-sPROXY_TO_PTHREAD`. The main browser thread cannot `Atomics.wait`, so Emscripten busy-waits in `pthread_join`/`pthread_mutex_lock` there ("on the Web it is bad for the main browser thread to wait on anything else"); `fork()`, signals and thread priorities are unsupported. The page's browser-support paragraph still says pthreads "will currently only work in the Firefox Nightly channel" — stale text, contradicted by the compat data below. — [Emscripten pthreads docs](https://emscripten.org/docs/porting/pthreads.html)
- MDN: "To use shared memory your document must be in a secure context and cross-origin isolated"; the `SharedArrayBuffer` constructor on the global object is hidden unless the two headers are set, and `postMessage()` throws for SABs otherwise. — [MDN SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)
- Browser compat (mdn/browser-compat-data, read 2026-11-01): `SharedArrayBuffer` Chrome 68 (BCD's pre-Spectre original; the gated, cross-origin-isolated return is Desktop Chrome 92 / Android Chrome 88 per the MDN-linked 2021 Chrome note, and BCD lists Chrome Android 89), Firefox 79, Safari 15.2; `Cross-Origin-Embedder-Policy` Chrome 83, Firefox 79, Safari 15.2; COEP `credentialless` Chrome 96, Firefox 119, Safari: not supported. — [BCD SharedArrayBuffer.json](https://github.com/mdn/browser-compat-data/blob/main/javascript/builtins/SharedArrayBuffer.json); [BCD Cross-Origin-Embedder-Policy.json](https://github.com/mdn/browser-compat-data/blob/main/http/headers/Cross-Origin-Embedder-Policy.json)
- Wasm threads feature: Chrome 74 (2019-04-23), Chrome Android 88 (2021-01-19), Firefox 79 (2020-07-28), Safari and Safari iOS 15.2 (2021-12-13); Baseline "Widely Available (since 2024-06-13)". — [web-features: wasm-threads](https://web-platform-dx.github.io/web-features-explorer/features/wasm-threads)
- GitHub Pages: the community request "Allow setting COOP and COEP headers in Github Pages" (#13309) is still a request with "No ETA at the moment"; no official GitHub doc offering custom headers was found. — [GitHub community discussion #13309](https://github.com/orgs/community/discussions/13309)
- coi-serviceworker README: adds COOP/COEP "through a service worker, for sites where you can't set HTTP headers, such as GitHub Pages"; on first load "the script reloads the page so the service worker can add the required headers" (override via `doReload`); must be a separate file served from your own origin over HTTPS, cannot be loaded from a CDN; `coepCredentialless` defaults to true and `coepDegrade` (default true) "falls back to `require-corp` if credentialless fails." The README does not mention Safari/iOS. Repo: 589 stars, last push 2023-12-09. — [gzuidhof/coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker)
- coi-serviceworker Safari history (issues): #13 "Allow Safari / WebKit to have SharedBuffer too" (closed 2023-06-27), #20/#21 fixing "credentialless vs require-corp" detection "to work with Safari" (2023-08-01), #25 "Retry with require-corp if credentialless fails" (2023-12-04). — [coi-serviceworker issues](https://github.com/gzuidhof/coi-serviceworker/issues?q=safari)
- Field report: a Zoom developer thread describes an iPhone X on iOS 16.7.10 failing when SharedArrayBuffer was enabled via coi-serviceworker; the poster's workaround was skipping the service worker on iOS; thread auto-closed without a confirmed fix (secondary source). — [Zoom devforum thread](https://devforum.zoom.us/t/session-failing-when-using-sharedarraybuffer-on-ios/122170)

**Asyncify vs JSPI (single-threaded event loop)**
- Asyncify "automatically transforms your compiled code into a form that can be paused and resumed"; it "can cause the Wasm output to be much larger"; speed overhead "is usually not extreme, something like 50% or so"; build with `-O3`. JSPI (`-sJSPI`): "The code size will remain the same"; requires explicit `JSPI_IMPORTS`/`JSPI_EXPORTS`. — [Emscripten Asyncify docs](https://emscripten.org/docs/porting/asyncify.html)
- JSPI browser support: Chrome/Chrome Android 137 (2025-05-27), Edge 137, Firefox/Firefox Android 153 (2026-07-21), Safari/Safari iOS 27 (2026-09-14); Baseline "Newly Available (since 2026-09-14)", expected Widely Available 2029-03-14. — [web-features: wasm-jspi](https://web-platform-dx.github.io/web-features-explorer/features/wasm-jspi)

**Boost, OpenSSL, zlib**
- Emscripten ships a `boost_headers` port: Boost 1.83.0 headers only, enabled with `-sUSE_BOOST_HEADERS=1` or `--use-port=boost_headers`. The ports directory contains `zlib` (1.3.2, `-sUSE_ZLIB`) but no OpenSSL port (full list: boost_headers, bullet, bzip2, cocos2d, emdawnwebgpu, freetype, giflib, harfbuzz, icu, libjpeg, libmodplug, libpng, mpg123, ogg, regal, sdl2*, sdl3*, sqlite3, vorbis, zlib). — [tools/ports/boost_headers.py](https://github.com/emscripten-core/emscripten/blob/main/tools/ports/boost_headers.py); [tools/ports/zlib.py](https://github.com/emscripten-core/emscripten/blob/main/tools/ports/zlib.py); [tools/ports listing](https://github.com/emscripten-core/emscripten/tree/main/tools/ports)
- Building compiled Boost libraries with b2's `toolset=emscripten` broke on Windows with emsdk 4.0.22: issue "Boost no longer builds using toolset=emscripten as of emsdk 4.0.22" (bfgroup/b2 #568, opened 2026-03-18, b2 ≤ 1.90.0, still open); cause is the removed extensionless `emcc`/`em++` launchers; workarounds are `using emscripten : : emcc.bat ;` in `user-config.jam` or creating an empty `emcc` file. — [bfgroup/b2#568](https://github.com/bfgroup/b2/issues/568)
- A Boost-users thread notes the official Emscripten Asio port dates from 2015 and is believed to be standalone Asio, not Boost.Asio. — [boost-users thread](https://lists.preview.boost.org/archives/list/boost-users@lists.preview.boost.org/thread/VA6UHIB6LDC6YY53XBQKOYFAYWHQFAEA)
- OpenSSL: no official Emscripten target page was found. Community recipes: `engineeringstuff/openssl-wasm` builds any OpenSSL tag inside a Docker image with emsdk via `emmake make`, output is a JS loader plus `.wasm` (examples 3.1.0, 1.1.1; Configure flags not listed). — [engineeringstuff/openssl-wasm](https://github.com/engineeringstuff/openssl-wasm). A CI commit wraps `Configure` in `emconfigure` with `no-asm no-threads no-shared no-dso` for OpenSSL 3.1.1 on the `emscripten/emsdk:3.1.43` image. — [syncad CI commit](https://gitlab.syncad.com/hive/common-ci-configuration/-/commit/36953dc43a9b6ce208a9a86463f63ed6743dc9fa)

**i2pd's own position and precedents**
- i2pd issue #1817 "Add a wasm release target?" (opened 2022-12-03, closed 2023-01-06). Maintainer r4sas: "We are not planning add it and can not say anything about difficulties"; closing comment: "I looked in wasi-sdk, there is bunch of problem, like `pthread`, so I think it is not possible to make it work on wasm for now." The requester wanted "fully decentralized browser-based applications using i2pd as the communication transport". — [PurpleI2P/i2pd#1817](https://github.com/PurpleI2P/i2pd/issues/1817)
- The only comparable "anonymity daemon in a browser" efforts found are Rust/Arti (see KQ2) and CheerpJ/WebVM proxying via Tailscale (KQ3); no Emscripten port of a Boost.Asio + OpenSSL daemon was found.
- Size datapoint (not i2pd): a full libsodium build is 278,330 bytes as WASI WebAssembly vs 731,484 bytes native stripped (2019). — [00f.net libsodium wasm benchmark](https://00f.net/2019/04/09/benchmarking-webassembly-using-libsodium/)

### Inferences
- i2pd's `libi2pd` needs Boost.Asio (sockets + reactor), Boost.program_options (a compiled library, not covered by the headers-only port) and OpenSSL; all three must be built by hand with `emconfigure`/b2, and Asio would fall back to its `select` reactor, which is the exact code path of open issue #25759.
- i2pd is multi-threaded by design (the release workflow in this repo installs `libboost-program-options-dev libssl-dev zlib1g-dev` and compiles the router in, `/home/artamonov/projects/gipny-i2pd/.github/workflows/release.yml` lines 128–139); keeping that model means `-pthread` + `PROXY_TO_PTHREAD`, hence SharedArrayBuffer, hence COOP/COEP. On GitHub Pages that is only reachable through coi-serviceworker, which costs a reload on first visit and must downgrade to `require-corp` on Safari (no `credentialless`), so every cross-origin resource the page loads must carry CORP/CORS headers.
- A single-threaded rewrite of i2pd's event model is not a build flag: it would need the router's blocking paths converted to Asyncify (≈50% CPU overhead, larger binary) or JSPI (same size; Baseline only since Safari 27 / Firefox 153 in late 2026 — older phones excluded).
- SSU2 (UDP) cannot exist in the browser at all; NTCP2 over a WebSocket bridge (websockify or the project's own entry/bridge service) is the only transport. Either way the page talks to one bridge, not to I2P peers directly.
- Net: the Emscripten path is feasible as an engineering project but has no precedent, fights the Asio/pthreads model, and still ends up with a bridge-dependent, TCP-only client — the same topology a purpose-built client-only router would have with far less code.

### Gaps
- No binary-size figure for an Emscripten build of i2pd or any Boost.Asio+OpenSSL daemon exists; nobody has published one.
- The Emscripten pthreads page's browser-support text is stale ("Firefox Nightly"); Emscripten's docs do not state a current browser matrix for pthreads.
- Whether Emscripten commit 8694832 (2026) fixes `select()` timeouts for WebSocket-emulated sockets is unresolved (issue #25759 still open).
- No fetched source for the maximum WebSocket-emulated throughput or latency overhead of Emscripten's socket layer.

## Key question 2 — Rust path: Rust I2P routers in 2026, runtime abstraction, wasm32 constraints, Veilid as a template

### Takeaway
`emissary` (now at `eepnet/emissary`, MIT, 260 stars, last commit 2026-10-30, v0.4.0) is the only actively developed Rust I2P router; its core is an async library behind a `Runtime` trait (TCP/UDP/timers/spawn/RNG/gzip as associated types), has a `no_std` feature and pure-Rust crypto, so a `wasm32-unknown-unknown` runtime is architecturally plausible but nobody has built one (no wasm issue or PR exists). The Ethereum Foundation's Arti-in-browser project (Jan–Mar 2026) shows what such a port costs: ~28 crates patched, single-threaded `?Send` futures, `web_time`, `getrandom` `wasm_js`, in-memory storage, a WebSocket/WebRTC transport and a plain-HTTPS bootstrap archive — and it is still "not recommended for production".

The directory also has `mock.rs` and `noop.rs`. — [emissary-core/src/runtime/mod.rs](https://github.com/eepnet/emissary/blob/master/emissary-core/src/runtime/mod.rs)
- Concrete runtimes live in `emissary-util/src/runtime/{tokio.rs, smol.rs}`; `emissary-util` also holds `reseeder.rs`, `su3.rs`, `certificates.rs`, `storage.rs`, `port_mapper`. Issue #169 "runtime: replace async-std with smol" closed 2025-07-09. — [emissary-util/src](https://github.com/eepnet/emissary/tree/master/emissary-util/src); [eepnet/emissary#169](https://github.com/eepnet/emissary/issues/169)

**wasm32 constraints of the Rust ecosystem**
- tokio 1.54.1: on all Wasm targets only `sync`, `macros`, `io-util`, `rt`, `time` build; "Enabling any other feature (including `full`) will cause a compilation failure." `tokio::net` exists on `wasm32-wasip1`/`wasip2` only under `tokio_unstable`. Timers may panic on non-WASI wasm. — [docs.rs tokio, WASM support](https://docs.rs/tokio/latest/tokio/#wasm-support)
- getrandom 0.4.3: WASI and Emscripten targets are supported out of the box; `wasm32-unknown-unknown` needs the `wasm_js` crate feature, which uses "Crypto.getRandomValues via wasm-bindgen"; "We strongly recommend against enabling this feature in libraries." — [docs.rs getrandom](https://docs.rs/getrandom/latest/getrandom/)
- wasm-bindgen-futures 0.4.80: `spawn_local` "Runs a Rust `Future` on the current thread"; `JsFuture` is "A Rust `Future` backed by a JavaScript `Promise`"; the crate "is now a thin shim re-exporting from js_sys::futures." — [docs.rs wasm-bindgen-futures](https://docs.rs/wasm-bindgen-futures/latest/wasm_bindgen_futures/)
- The workspace `Cargo.toml` declares `tokio` with `features = ["full"]` and `reqwest 0.12.21`, but `emissary-core/Cargo.toml` consumes neither as a normal dependency (tokio and `emissary-util` appear only under `[dev-dependencies]`); they are used by `emissary-util` (reseeder, tokio/smol runtimes) and `emissary-cli`. So the native-only crates sit outside the core library, behind the `Runtime` seam. — [emissary workspace Cargo.toml](https://github.com/eepnet/emissary/blob/master/Cargo.toml); [emissary-core/Cargo.toml](https://github.com/eepnet/emissary/blob/master/emissary-core/Cargo.toml)

**Arti in the browser (closest precedent)**
- Ethereum Foundation write-up (2026-03-20, work Jan–Mar 2026): ~28 crates touched; a new `tor-time` crate uses `web_time::Instant` because `std::time::Instant` is "unavailable in WASM"; "WASM is single-threaded" — a `tor-async-compat` crate rewrites `#[async_trait]` to `?Send` on WASM (51 files), spawning uses `wasm_bindgen_futures::spawn_local()`, blocking operations panic; "Browsers can't open raw TCP connections" — networking is stubbed and replaced by a Snowflake transport: "WebSocket or WebRTC → KCP → SMUX → TLS (rustls) → Tor protocol"; SQLite replaced by in-memory storage with IndexedDB persistence; `subtle-tls` replaced by `futures-rustls` + `rustls-rustcrypto` ("still experimental (alpha status)"); `getrandom` "does not work out of the box on WASM" → `wasm_js`; the `psl` crate made compilation "consume 10GB+ of memory" and was swapped for `public-suffix` (~430 KB). "The first working prototype bootstrapped in ~3 minutes in WASM versus ~15 seconds native"; with a `bootstrap.zip` (consensus, authority certs, microdescriptors) fetched "over a plain HTTPS connection before Tor is operational" bootstrap dropped to seconds — "this is a weaker trust model than standard Tor bootstrapping" and "the user's IP is visible to the bootstrap server". ~6,100 lines of new Rust+TypeScript across 10+ upstream crates; "upstream merge with the Tor Project is in progress"; production use not recommended, audit planned. — [EF: Embedding Arti in the browser](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- tor-js landing page: "a small gateway relays bytes to Tor relays over KPS (WebRTC/QUIC)"; the gateway only forwards encrypted bytes; JS wrapper ~24 kB, wasm size not stated. — [ethereum.github.io/tor-js](https://ethereum.github.io/tor-js/)

### Inferences
- emissary is the only realistic Rust starting point. Its `Runtime` trait is exactly the seam a browser port needs: a `WasmRuntime` whose `TcpStream` wraps a WebSocket to the project's bridge (as Veilid's `ws.rs` does with `ws_stream_wasm`), whose `UdpSocket::bind` returns `None` (no SSU2), whose `spawn` is `spawn_local`, and whose `Instant` is `web_time`. The `no_std` feature and `default-features = false` crypto deps suggest the core avoids OS assumptions, but the `Send + 'static` bounds on `Runtime`, `TcpStream` and `JoinSet` would need the same `?Send` treatment Arti required (51 files there).
- The Arti timeline (three months, ~28 crates, for a team with weekly Tor Project syncs) is the best available effort estimate for "take an existing Rust anonymity router to wasm32"; emissary is smaller and younger than Arti, which cuts both ways (less to patch, less tested).
- Reseeding and storage must be re-done for the browser regardless (reqwest/filesystem are native-only), which overlaps with KQ6.

### Gaps
- No one has reported compiling emissary (or ire) for `wasm32-unknown-unknown`; there is no evidence of how many `Send`/`std` assumptions lie outside the `Runtime` trait.
- No benchmark of emissary's CPU or memory on any platform was found.
- The wasm binary size of tor-js/Arti is not published; no size datapoint for a Rust router on wasm exists.

## Key question 3 — Java path: running the Java I2P router under CheerpJ in 2026

### Takeaway
CheerpJ 4.3 (2026-04-21) runs Java 8/11/17 (21 planned; 21 and 25-preview listed on the architecture page) with Java threads time-sliced on a single browser thread, and does non-HTTP networking only by joining a Tailscale tailnet over WebSockets — reaching arbitrary Internet hosts additionally needs an exit node the deployer operates. It is proprietary with a free Community tier only for individuals/one-person companies (with a "Built with CheerpJ" credit) and £100/developer/month above that; no evidence of any P2P router running under it was found.

### Cited Findings
- Architecture: bytecode first runs in an interpreter, hot code is JIT-compiled to JavaScript; the JVM "is written in C++ and compiled to WebAssembly and JavaScript with Cheerp"; Java threads are "scheduled by CheerpJ and take turns on one browser thread" (the page's own thread or a Web Worker's, depending on how CheerpJ is started); Java 8, 11, 17 and 21 supported, Java 25 in preview, each with its own OpenJDK build; "CheerpJ 5.0" is mentioned only for an experimental WebAssembly-GC engine. — [CheerpJ architecture](https://cheerpj.com/docs/explanation/architecture)
- CheerpJ 4.3 released 2026-04-21: "CheerpJ currently supports Java 8, 11 and 17", Java 21 "planned for later this year", focus on stability and Swing/touch usability (long-press as hover), "With CheerpJ 5.0 on the horizon…". — [CheerpJ 4.3 blog](https://labs.leaningtech.com/blog/cheerpj-4.3). Earlier: 4.0 (April 2025) first multi-version release with Java 11; 4.1 (2025-05-28) Java 17 preview, SSL for Java 11, "improved networking stack". — [CheerpJ 4.1 news](https://leaningtech.com/news/cheerpj-41)
- Networking: `java.net.URL`/`HttpURLConnection` go through the browser Fetch API, same-origin or CORS-permitted only, HTTP upgraded to HTTPS. For everything else "CheerpJ provides them through Tailscale, a VPN that carries the traffic over WebSockets"; configured with `tailscaleAuthKey` or `tailscaleLoginUrlCb` (mutually exclusive), `tailscaleControlUrl` for self-hosted Headscale; covers "anything that is not HTTP(S), such as TCP and UDP sockets"; "CheerpJ cannot become responsible for the user's traffic"; custom enterprise networking backends on request. — [CheerpJ networking guide](https://cheerpj.com/docs/guides/Networking)
- "a Tailscale network by default is isolated from the internet, so it is necessary to configure an exit node that routes all the internet traffic in and out of your VPN"; without Tailscale CheerpJ "can only do same-origin requests". — [CheerpJ Swing browser tutorial](https://cheerpj.com/docs/tutorials/java-browser)
- The sibling WebVM post explains the mechanism: in a browser "you can only do HTTP(S), and even then, you are severely limited by CORS policies", so "we need a proxy server to perform the protocol upgrade and unwrap the WebSocket packets before sending them to the destination." — [WebVM networking via Tailscale](https://labs.leaningtech.com/blog/webvm-virtual-machine-with-networking-via-tailscale)
- Licensing (Application licences): Community — free, with a "Built with CheerpJ" credit, for software published under your own name "including commercial use, for individuals and one-person companies" and non-commercial open source, only when loading CheerpJ from the CDN; Small Business — £100 per developer per month (under 50 staff, under $5M revenue, under $10M funding, up to 10 developers), self-hosting is a £5,000/year add-on; Enterprise — quoted, includes self-hosting and OEM redistribution. "Bundling or self-hosting the runtime counts as redistribution". — [CheerpJ licensing](https://cheerpj.com/licensing/)

### Inferences
- The Java router's hundreds of threads would be green-threaded on one browser thread (no SharedArrayBuffer requirement, so no COOP/COEP problem), but CPU-bound crypto would share that one thread with the UI unless CheerpJ is started in a Worker.
- Every NTCP2/SSU2 packet would traverse browser → WebSocket → Tailscale DERP/proxy → tailnet exit node → Internet. The exit node is operated by the project and sees all peer traffic; it is functionally the same bridge as in the Emscripten/Rust paths, with a third-party control plane (Tailscale or self-hosted Headscale) and auth keys embedded in a public page.
- For this project (an open-source product shipped by an organisation, served from its own Pages origin) the Community tier does not obviously apply; self-hosting the runtime is a paid add-on, and loading a closed-source JVM from a vendor CDN contradicts the project's hosting-sees-nothing stance recorded in the handoff brief.

### Gaps
- No public example of a long-running multi-threaded networking daemon (let alone a P2P router) under CheerpJ was found; its performance for that workload is unmeasured.
- The licensing page lists Java 8/11/17 while the architecture page lists 21 and 25-preview — the exact Java-21 status in CheerpJ 4.3 is ambiguous between the two pages.
- Whether CheerpJ's Tailscale layer supports UDP end-to-end through an exit node (needed for SSU2) is not documented beyond the generic "TCP and UDP sockets" sentence.

## Key question 4 — Crypto performance in WebAssembly and the load of a client-only I2P router

### Takeaway
Published numbers are scarce and mostly desktop/Node: wasm Ed25519 (dalek) runs ~4,000 ops/s in Node vs ~7,100 native and ~485 for pure-JS noble (older), wasm ChaCha20-Poly1305 reaches ~190–340 MB/s vs ~1.5 GB/s native, and generic wasm crypto is 5–8× slower than native; WebCrypto now offers X25519/Ed25519 in all engines (Chrome 133/137, Firefox 130, Safari 17.x). No mobile-browser figures were found. Against i2pd's defaults (3+3 two-hop exploratory tunnels, reseed threshold 25) and a shipped ~2,500-RouterInfo snapshot, the arithmetic says a client-only router is dominated by Ed25519 verification at startup (seconds on a phone) and otherwise idles at a few tunnel builds per minute — far below the ceilings above, but the numbers are inference, not measurement.

### Cited Findings

**Benchmarks**
- libsodium compiled to WASI (Wasmtime, 2019): elliptic-curve point multiplication ≈7× slower than native, password hashing 8× slower; native used SIMD, the wasm build did not; `-O2` produced the fastest code; wasm builds remain faster than pure-JS libsodium. — [00f.net: Benchmarking WebAssembly using libsodium](https://00f.net/2019/04/09/benchmarking-webassembly-using-libsodium/)
- ed25519-dalek compiled to wasm (hazae41 "berith"/`ed25519_dalek`), Node, hardware unstated: `@hazae41/berith 1.1.12 (unserialized) 4,072 ops/sec`, `(serialized) 3,544 ops/sec`, `@noble/ed25519 1.7.1 485 ops/sec`, `supercop.wasm 5.0.1 5,902 ops/sec`, `node:crypto (unserialized) 7,102 ops/sec`. Deno 1.26 on Apple M1 Max: berith 289.94 µs/iter vs noble 2.1 ms/iter (7.25× faster). The page does not say which operation (sign vs verify) the numbers are. — [deno.land ed25519_dalek README](https://deno.land/x/ed25519_dalek@1.1.18)
- RustCrypto AEADs compiled to wasm, 16 KB blocks: Wasmtime — aes128-gcm 44.13 MB/s, chacha20-poly1305 193.05 MB/s (196.54 with simd128); WAVM — aes128-gcm 57.01 MB/s, chacha20-poly1305 335.82 MB/s; native Rust on a 2.4 GHz Core i9 — aes128-gcm 1.91 GB/s, chacha20-poly1305 1.48 GB/s. — [morus crate README](https://docs.rs/crate/morus/latest)
- Peer-reviewed 2025 paper (Buljić, Kadušić, Živić, Marevac, Journal of Communications 20(6):681–693, published 2025-11-11) benchmarked Ed25519 as pure JS, WebCrypto, wasm non-batch and wasm batch plus RSA and hybrid AES-GCM: "Wasm batch verification delivers the highest throughput, while WebCrypto provides a balanced compromise"; concrete figures are in the PDF, which was not accessible. — [JCM paper page](https://www.jocm.us/show-321-2118-1.html)
- CryptPad's library review: for asymmetric encryption libsodium.js and the Web Crypto API "perform about similar", but libsodium.js "on Firefox is even worse than the one of TweetNaCl-JS" (undated review). — [CryptPad review PDF](https://blueprints.cryptpad.org/_assets/review/libraries/main.pdf)

**WebCrypto coverage**
- Secure curves in WebCrypto (Igalia, 2025-02-28/03-31): Chrome 133 shipped X25519 by default (Feb 2025); Firefox 130 shipped Ed25519 and X25519 (Sept 2024); WebKit enabled Ed25519 by default Feb 2023 (STP 178) and X25519 Dec 2024 (STP 211). — [Igalia: Secure Curves](https://blogs.igalia.com/jfernandez/?p=1913). Chrome M137 is "the first stable version shipping the Ed25519 feature enabled by default". — [IPFS blog, Aug 2025](https://blog.ipfs.tech/2025-08-ed25519/)
- Wasm fixed-width SIMD: Chrome/Chrome Android 91 (2021-05-25), Firefox 89 (2021-06-01), Safari/Safari iOS 16.4 (2023-03-27); Baseline Widely Available since 2025-09-27. — [web-features: wasm-simd](https://web-platform-dx.github.io/web-features-explorer/features/wasm-simd)

**I2P workload inputs**
- netDb lookups "are sent out one of the router's outbound exploratory tunnels, and the replies return through its inbound exploratory tunnels"; "Lookups are generally sent to the two" closest floodfills in parallel (iterative lookups since 0.8.9); routing key = SHA256(key ‖ yyyyMMdd) rotating at midnight UTC; stores flood to the three closest floodfills; "about 6% of routers are floodfills", threat analysis cites "around 1700 floodfill routers"; local RouterInfo expiry is 72 h with fewer than 120 routers, ~30 h at 300, 1 h for SSU-introducer RIs; exploration asks a floodfill for non-floodfill routers near a random key and "yields only a few hashes per query"; a RouterInfo bundles identity (encryption key, signing key, certificate), addresses, publish time, options and a signature. — [i2p.net: Network Database](https://i2p.net/en/docs/overview/network-database)
- Exploratory tunnels default to two hops, client tunnels mostly two or three, maximum seven; tunnel testing is mandatory since 2026-02; participants may drop tunnels carrying no traffic within two minutes. — [i2p.net: Tunnel Routing](https://i2p.net/en/docs/overview/tunnel-routing)
- i2pd defaults: `exploratory.inbound.length = 2`, `exploratory.inbound.quantity = 3`, `exploratory.outbound.length = 2`, `exploratory.outbound.quantity = 3`; `reseed.threshold = 25` ("Minimum number of known routers before requesting reseed"); `floodfill = false`; `notransit` disables transit tunnels. — [i2pd configuration](https://docs.i2pd.website/en/latest/user-guide/configuration/); same defaults in source, [libi2pd/Config.cpp](https://github.com/PurpleI2P/i2pd/blob/openssl/libi2pd/Config.cpp) lines 268–269, 333–336 (read via GitHub API 2026-11-01)
- i2pd tunnel constants (branch `openssl`, read 2026-11-01): `TUNNEL_EXPIRATION_TIMEOUT = 660` s ("11 minutes"), `TUNNEL_EXPIRATION_THRESHOLD = 60` s, `TUNNEL_RECREATION_THRESHOLD = 90` s ("1.5 minutes"), `TUNNEL_CREATION_TIMEOUT = 30` s, `STANDARD_NUM_RECORDS = 4` ("in VariableTunnelBuild message"), `MAX_NUM_RECORDS = 8`; pool limits `TUNNEL_POOL_MAX_INBOUND_TUNNELS_QUANTITY = 16`, `TUNNEL_POOL_MAX_OUTBOUND_TUNNELS_QUANTITY = 16`, `TUNNEL_POOL_MAX_NUM_BUILD_REQUESTS = 3`; build records `TUNNEL_BUILD_RECORD_SIZE = 528`, `SHORT_TUNNEL_BUILD_RECORD_SIZE = 218` bytes. — [libi2pd/Tunnel.h](https://github.com/PurpleI2P/i2pd/blob/openssl/libi2pd/Tunnel.h) lines 37–42; [libi2pd/TunnelPool.h](https://github.com/PurpleI2P/i2pd/blob/openssl/libi2pd/TunnelPool.h) lines 32–36; [libi2pd/I2NPProtocol.h](https://github.com/PurpleI2P/i2pd/blob/openssl/libi2pd/I2NPProtocol.h) lines 64–65
- This project's release snapshot: the `netdb-seed` job runs `cargo run --locked --release -p i2p-embed --example netdb_snapshot -- "$PWD/seed-dir" 2500 360` (target 2,500 routers, 360 s), counts `routerInfo-*.dat` files and tars `seed-dir/netDb` into `i2pd-netdb-seed.tar.gz`. — `/home/artamonov/projects/gipny-i2pd/.github/workflows/release.yml` lines 121–152
- Live reseed bundles (local probe 2026-11-01): `i2pseeds.su3` from nine responding servers was 23,906–66,009 bytes each (see KQ6 table).

### Inferences
- Startup: verifying a shipped snapshot of ~2,500 RouterInfos means ~2,500 Ed25519 verifications. At the Node/desktop wasm rate (~4,000/s) that is under a second; assuming a mid-range phone is 3–10× slower than a desktop (not measured), 2–7 s, which can be spread over idle time or deferred until a RouterInfo is actually used.
- Steady state with i2pd's exploratory defaults (3 in + 3 out, 2 hops) plus one client pool of similar size: ~12 tunnels alive. With i2pd's 660 s tunnel lifetime and 90 s recreation threshold, each tunnel is rebuilt roughly every 9.5 minutes, so the baseline is ~1.3 builds/minute (more with failed builds, up to 3 concurrent build requests per pool), each costing per hop one X25519 agreement and one ChaCha20-Poly1305 record (528-byte ECIES or 218-byte short records, 4 records per message) plus reply decryption — tens of asymmetric operations per minute, i.e. negligible at thousands per second.
- Traffic: a client-only router (no transit, `notransit`) carries only its own bytes; at ~190–340 MB/s wasm ChaCha20-Poly1305 throughput the symmetric cost of a messenger-class workload (KB/s) is noise. NTCP2 frames and tunnel-layer AES are the only per-byte costs.
- netDb churn: exploration "yields only a few hashes per query" and lookups go to two floodfills, so ongoing Ed25519 verification is tens per minute, not thousands.
- Memory: 2,500 RouterInfos at ~1 KB each on the wire (the su3 sizes above put a compressed bundle of a few dozen RIs at ~60 KB) is a few MB parsed; the router's working set is dominated by the wasm binary, buffers and the crypto library, plausibly tens of MB — well under the ~300 MB iOS floor in KQ5. This is an estimate; no measured figure exists.
- WebCrypto could offload X25519/Ed25519 and AES-GCM to native code, but I2P needs ChaCha20-Poly1305 (NTCP2, ECIES) and AES-256/CBC tunnel layers; WebCrypto's AEAD support is AES-only (not verified in this session — see Gaps), so a wasm implementation is still required for the hot path.

### Gaps
- No benchmark of X25519, Ed25519, ChaCha20-Poly1305 or SHA-256 in wasm on a mobile browser (Safari iOS or Chrome Android) was found; all figures above are desktop or Node/Deno.
- The JCM 2025 paper's actual Ed25519 WebCrypto-vs-wasm numbers are only in its PDF (not retrieved).
- The I2P specification pages could not be fetched: `i2p.net/spec/tunnel-creation-ecies`, `/spec/updates` and `/spec/tunnel-creation` returned HTTP 404 on 2026-11-01 (the site restructured its `/en/docs/how/*` and `/spec/*` paths; only `/en/docs/overview/*` pages resolved). Tunnel lifetime and record sizes above therefore come from i2pd's source constants rather than the spec; the Java router's default client-pool quantities were not sourced.
- The claim that WebCrypto has no ChaCha20-Poly1305 was not verified against MDN/spec in this session.
- Average RouterInfo size and the size of this project's snapshot tarball are not in any fetched source (the workflow prints them only in the run summary).

## Key question 5 — WebAssembly limits in mobile browsers in 2026 (memory, Memory64, SIMD, threads, JSPI)

### Takeaway
On paper wasm32 memory is 4 GB (Chrome since M83), SIMD, threads and (since Safari 27, Sept 2026) JSPI are in every engine, and Memory64 is in Chrome 133/Firefox 134 but not Safari; in practice iOS Safari has been measured to give a page ~1 GB on first load and 300–500 MB after reloads (WebKit bug closed as duplicate, not fixed), and threads still need cross-origin isolation.

### Cited Findings
- Spec-level status (webassembly.org features.json, read 2026-11-01): Fixed-width SIMD, Relaxed SIMD, Memory64, JS Promise Integration, Exception handling (exnref), GC, Tail call, Multiple memories — phase 5; Threads — phase 4; Shared-Everything Threads — phase 1. — [webassembly.org/features](https://webassembly.org/features/)
- Memory ceiling: Chrome raised wasm32 memory from 2 GB to 4 GB ("the largest amount of memory possible with 32-bit pointers"), test on "Chrome M83 (currently in Beta) or later" (2020-05-14); Emscripten defaults to 2 GB and needs an explicit opt-in above it. — [V8 blog: Up to 4GB of memory in WebAssembly](https://v8.dev/blog/4gb-wasm-memory)
- iOS: WebKit bug 269777 "Only ~300 MB of RAM is reliably available to WebAssembly pages" (2024-02-20): on iPhone Xs / iPad Pro 3rd gen / iPhone 12 / iPhone 14 Pro (iOS 17.0.3–17.3.1) the first visit could allocate ~1 GB, after a reload ~300–500 MB, one run only 28 MB; a Redmi Note 10 5G on Chrome 121 "reliably reached about 4GB"; closed RESOLVED DUPLICATE of bug 269937 on 2024-02-22. — [WebKit bug 269777](https://bugs.webkit.org/show_bug.cgi?id=269777). Bug 269937 "MegaBug: WASM memory, SAB and Gigacage fragmentation, causes unpredictable wasm memory allocation" is itself RESOLVED DUPLICATE (created 2024-02-22, last changed 2024-05-16). — [WebKit bug 269937](https://bugs.webkit.org/show_bug.cgi?id=269937). Bug 221530 (2021) reported that Safari "kills/(crashes?)/reopens the whole tab without notice" instead of failing `memory.grow()`, and that a WebKit engineer said iOS may kill any process for memory pressure; RESOLVED DUPLICATE. — [WebKit bug 221530](https://bugs.webkit.org/show_bug.cgi?id=221530)
- Memory64: Chrome/Chrome Android 133 (2025-02-04), Edge 133, Firefox/Firefox Android 134 (2025-01-07), Safari and Safari iOS not supported; "Baseline availability blocked since February 2025 by Safari (20 months)". — [web-features: wasm-memory64](https://web-platform-dx.github.io/web-features-explorer/features/wasm-memory64)
- SIMD: Chrome/Chrome Android 91 (2021-05-25), Firefox 89, Safari/Safari iOS 16.4 (2023-03-27); Widely Available since 2025-09-27. — [web-features: wasm-simd](https://web-platform-dx.github.io/web-features-explorer/features/wasm-simd)
- Threads: Chrome 74, Chrome Android 88 (2021-01-19), Firefox 79, Safari/Safari iOS 15.2 (2021-12-13); Widely Available since 2024-06-13 — but usable only when cross-origin isolated (see KQ1). — [web-features: wasm-threads](https://web-platform-dx.github.io/web-features-explorer/features/wasm-threads); [MDN SharedArrayBuffer](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)
- JSPI: Chrome/Chrome Android 137 (2025-05-27), Firefox/Firefox Android 153 (2026-07-21), Safari/Safari iOS 27 (2026-09-14); Newly Available since 2026-09-14. — [web-features: wasm-jspi](https://web-platform-dx.github.io/web-features-explorer/features/wasm-jspi)
- Emscripten's pthreads page notes "Firefox Nightly limits threads per domain to 20 by default" and that `ALLOW_MEMORY_GROWTH` with pthreads can slow JS-side memory access (page text of unstated date). — [Emscripten pthreads docs](https://emscripten.org/docs/porting/pthreads.html)

### Inferences
- A browser router must budget for a few hundred MB on iOS, not 4 GB, and must survive the tab being killed rather than seeing an allocation error — persistent state (netDb, keys) has to be written to IndexedDB incrementally.
- Memory64 is irrelevant for the next years (Safari absent); wasm32 with `-sALLOW_MEMORY_GROWTH` and a modest initial heap is the target.
- JSPI-only designs exclude every phone not on iOS 27 / Firefox 153 / Chrome 137; a design that needs neither threads nor stack switching (plain async Rust compiled with wasm-bindgen, or an Asyncify'd C++ build) has the widest reach.

### Gaps
- No Chrome-for-Android documentation of a per-tab wasm memory cap was found; the only datapoint is the reporter's ~4 GB on one 2024 device.
- Relaxed SIMD's per-browser versions were not retrieved (only its phase-5 status).
- No measurement of wasm SIMD speed-ups for ChaCha20/AES on ARM phones was found.

## Key question 6 — Bootstrapping a browser router's netDb: reseed servers from a browser, shipping a signed snapshot, fetching via the entry node, floodfill lookups for an outbound-only router

### Takeaway
Browser-direct reseeding is effectively unavailable: a live probe of all 19 hosts in i2pd's current default `reseed.urls` on 2026-11-01 found 17 serving the ~24–66 KB `i2pseeds.su3`, of which only one (spiral.likogan.dev) sends `Access-Control-Allow-Origin: *` — and every host tested, including that one, answers 403 unless the request carries the `Wget/1.11.4` User-Agent that i2pd hard-codes — a header a web page can override only in some browsers, if at all (not tested per browser). The project already builds a ~2,500-RouterInfo snapshot at every release and deploys the web UI from the same GitHub Pages origin, so serving that tarball (or a per-RI JSON index) same-origin is the zero-CORS path; the alternative is to pull RouterInfos through the loopback/bridge connection after pairing, as the web-local-mode plan already orders ("first pairing and `web_info`, then bootstrap"). Once seeded, I2P lookups need no inbound TCP: queries leave through outbound exploratory tunnels and replies come back through inbound tunnels built over peers.

**Floodfill lookups for an outbound-only router**
- Lookups "are sent out one of the router's outbound exploratory tunnels, and the replies return through its inbound exploratory tunnels"; sent to the two closest good floodfills in parallel; routing key rotates daily; exploration returns "non-floodfill routers near that key". — [i2p.net: Network Database](https://i2p.net/en/docs/overview/network-database)
- Exploratory tunnels default to two hops; tunnels are "temporary and unidirectional"; testing is mandatory since 2026-02. — [i2p.net: Tunnel Routing](https://i2p.net/en/docs/overview/tunnel-routing)

### Inferences
- Even the single CORS-enabled reseed host is unreliable from a page: reseed servers gate on the `Wget/1.11.4` User-Agent. The Fetch Standard's current forbidden request-header list (read 2026-11-01) names `Accept-Charset`, `Accept-Encoding`, `Access-Control-Request-*`, `Connection`, `Content-Length`, `Cookie`, `Date`, `DNT`, `Expect`, `Host`, `Keep-Alive`, `Origin`, `Referer`, `Set-Cookie`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade`, `Via` and any `Proxy-`/`Sec-` prefix — `User-Agent` is not on the list, so overriding it from `fetch()` is browser-dependent rather than impossible ([Fetch Standard, forbidden request-header](https://fetch.spec.whatwg.org/#forbidden-request-header)); it was not tested per browser here. Either way `Origin` is always sent and cannot be removed, so CORS applies, and 18 of 19 hosts fail on that alone. A browser router therefore needs its own bootstrap source rather than the public reseed network.
- Because the Pages site and the app share one origin, a snapshot published into `_site` needs no CORS at all. The probe shows GitHub Release asset downloads do not send CORS headers (so a browser cannot fetch the snapshot from a Release directly), while `raw.githubusercontent.com` does send `Access-Control-Allow-Origin: *` — committing a snapshot to a branch, or copying it into the Pages build, are the two workable publication routes. A JSON or msgpack index of RouterInfos (hash → base64 RI, published time) is more browser-friendly than a tar.gz, but the tarball can be unpacked in wasm (zlib port, `flate2`).
- The snapshot's trust model matches Arti's: the user trusts the release pipeline (and GitHub) for the initial peer set, which is at least as strong as i2pd's default `reseed.verify = false`. Signing it with the project's release key (the workflow already signs/uploads release assets) restores integrity; freshness is bounded by the 72 h / 30 h local expiry rules, so a snapshot older than ~a day or two should be followed by exploration or a bridge-assisted refresh.
- "Bootstrap via the entry node" means: after pairing, request the native side's netDb (it already lays out the same tarball on first start) over the loopback/bridge WebSocket — zero extra infrastructure and no IP exposure to a third-party reseed host. For the hosted (non-loopback) topology the bridge becomes the reseed server and sees the user's IP, like Arti's bootstrap server.
- Once seeded, an outbound-only, TCP-only router is a normal I2P participant: all netDb traffic is tunnelled, so it needs no reachable address, only enough RouterInfos with NTCP2 addresses to build 2-hop tunnels through the bridge.

### Gaps
- The su3 specification page itself could not be fetched (`i2p.net/spec/updates` and `geti2p.net/spec/updates` returned 404/no content on 2026-11-01); the format facts above come from i2pd's parser, not the spec, so header fields beyond magic/content-type/signature type are not documented here.
- No reseed operator publishes a CORS policy, so a negative probe is the best available evidence; non-responding hosts may simply have been slow or blocking this network, and the probe was run once from one vantage point.
- The CORS probe of release assets covered one asset of one release (`BUILD-MANIFEST.json` in v0.4.19); GitHub's CDN behaviour could differ per asset type or change over time.
- Whether current Chrome, Firefox and Safari let `fetch()` send a custom `User-Agent` (needed to pass the reseed servers' `Wget/1.11.4` gate) was not tested; MDN's forbidden-header page could not be fetched in this session.
- The actual router count and size of the latest `i2pd-netdb-seed.tar.gz` are only in the release run summary, not in any fetched artifact.
- The project's own documents never use the phrase "entry node" (grep of `docs/` found no hits); this note interprets it as the loopback native process / hosted bridge described in the web-local-mode plan.
