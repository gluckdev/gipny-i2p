# Browser transports and entry-node designs for an outbound-only I2P router in a browser

Scope: a WebAssembly I2P router running in a page served from `https://gluckdev.github.io/...` (GitHub Pages) must carry NTCP2 (Noise over TCP) to the I2P network. The page cannot open TCP, so some node outside the browser must terminate a browser-reachable transport. Two designs are compared: (A) a dumb WebSocket-to-TCP forwarder on the user's own node that relays raw NTCP2 bytes to arbitrary I2P routers; (B) an "NTCP2 over WebSocket" transport added to the project's i2pd fork, so that any reachable project node is a normal first hop. Research date: 2026-11-01. All facts carry a URL; items I could not verify from a fetched page are in "Gaps" or marked "unverified".

Context from the repository (not web evidence): the project already ships a "web local mode" in which the Pages UI connects to a native process on `ws://127.0.0.1:<port>` with a bearer capability and Origin/Host checks (`docs/plans/2026-10-31-web-local-mode.md`), and owner memory records a "no local ports" rule for the embedded i2pd with the loopback web mode as the explicit exception. Both designs A and B add a listening socket on a node; see Q6.

## Q1. 2026 support matrix and limits of WebSocket, WebTransport and WebRTC DataChannels (desktop and mobile)

### Takeaway
As of 2026 all three transports are usable in Chrome, Firefox and Safari (desktop and iOS), but only two are certificate-free for a self-hosted node: WebTransport with `serverCertificateHashes` (Chrome 100+, Firefox 125+, Safari/iOS 26.4+, certificate validity capped at two weeks, ECDSA P-256 only, HTTP/3 over UDP) and WebRTC DataChannels (universal since 2017-2020, self-signed DTLS, but need signalling and ICE). WebSocket is universal but from an https page requires `wss://` with a browser-trusted certificate except for loopback.

### Cited Findings
- WebTransport support: Chrome 97-159, Edge 98-155, Firefox 114-162, Safari desktop 26.4-27.1 (plus Technology Preview), Safari on iOS 26.4-27.2, Chrome for Android 156, Firefox for Android 159, Samsung Internet 18.0-30; Chrome 91-94 "disabled by default"; global usage 91.64% (StatCounter, September 2026) — [caniuse.com/webtransport](https://caniuse.com/webtransport)
- MDN browser-compat-data: `WebTransport()` constructor `version_added` chrome 97, firefox 114, safari 26.4 (safari_ios mirrors 26.4, chrome_android/edge/samsung/webview mirror Chrome 97); `options.serverCertificateHashes` chrome 100, firefox 125, safari 26.4 (ios mirror); no notes recorded for these entries — [mdn/browser-compat-data api/WebTransport.json](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/WebTransport.json)
- MDN badge: WebTransport is "Baseline 2026, Newly available. Since March 2026, this feature works across the latest devices and browser versions"; "Some parts of this feature may have varying levels of support." — [MDN WebTransport API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API)
- WebKit blog (Mar 24, 2026): "Safari 26.4 adds support for WebTransport"; "It runs over HTTP/3 and QUIC, providing multiple streams that won't block each other"; the post also claims "WebTransport can run over HTTP/2 and TCP as a fallback with the same API"; the post does not mention `serverCertificateHashes` — [WebKit Features for Safari 26.4](https://webkit.org/blog/17862/webkit-features-for-safari-26-4/)
- WebKit Bugzilla 300057 "Implement WebTransportOptions.serverCertificateHashes", reported 2025-10-02 by Alex Christensen, RESOLVED FIXED, "Committed 300917@main (3fbb5096bc1f)"; no behaviour notes or OS versions in the bug — [bugs.webkit.org 300057](https://bugs.webkit.org/show_bug.cgi?id=300057)
- `serverCertificateHashes` rules (MDN constructor page): certificate must be X.509v3; "Validity period must be less than 2 weeks, and the current time must fall within that period"; public key "must minimally include ECDSA with secp256r1 (NIST P-256). RSA keys must not be used"; `algorithm` is `sha-256` (only algorithm in spec); "only supported for transports using dedicated connections (`allowPooling` is `false`)"; `NotSupportedError` if the transport does not support hashes; use case "non-publicly routable hosts or ephemeral VMs" — [MDN WebTransport() constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/WebTransport)
- W3C WebTransport Editor's Draft (29 October 2026) §14.4: "the expiry period is limited to two weeks"; "This requirement limits the scope of potential key compromise"; the limit also accommodates "clock skew across devices"; "The only function defined in this document is SHA-256"; browsers "MAY reject" weak keys as implementation-defined; constructor throws `NotSupportedError` when pooling is combined with hashes; the underlying fetch uses redirect mode "error" — [w3c.github.io/webtransport](https://w3c.github.io/webtransport/)
- WebTransport runs on HTTP/3: "HTTP/3 was standardized in 2022 ... based on the QUIC protocol (itself based on UDP ...)"; the MDN API overview mentions no HTTP/2 or TCP fallback — [MDN WebTransport API](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport_API); contradicted in part by the WebKit post's claim of an HTTP/2 fallback "with the same API" — [WebKit 26.4 post](https://webkit.org/blog/17862/webkit-features-for-safari-26-4/)
- Third-party compatibility write-up claims WebKit and Firefox compare the `algorithm` string literally (uppercase "SHA-256" silently fails) and that WKWebView/in-app browser support is unconfirmed — secondary, unverified — [issoh.co.jp](https://www.issoh.co.jp/tech/details/16251/)
- WebRTC (`RTCPeerConnection`) support: Chrome 23-159, Edge 79-155 (15-18 partial), Firefox 22-162, Safari 11-27.1 + TP, Safari iOS 11-27.2, Chrome Android 156, Firefox Android 159, Samsung Internet 4-30; global usage 97.26% — [caniuse.com/rtcpeerconnection](https://caniuse.com/rtcpeerconnection)
- WebRTC DTLS certificates are browser-generated X.509 with a private key; "By default the new certificate is configured with `expires` set to a value of 2592000000 milliseconds, or 30 days"; maximum 365 days; all browsers must support RSASSA-PKCS1-v1_5 2048/SHA-256 and ECDSA P-256; "available across browsers since January 2020" — [MDN RTCPeerConnection.generateCertificate()](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/generateCertificate_static)
- Safari 26.4 WebRTC fixes relevant to DataChannels: "`RTCDataChannel` close events now fire when `RTCPeerConnection` closes"; `RTCDataChannelInit` now enforces ranges on `maxPacketLifeTime`/`maxRetransmits` — [WebKit 26.4 post](https://webkit.org/blog/17862/webkit-features-for-safari-26-4/)
- WebSocket from a secure context: "browsers will prevent making connections to unencrypted WebSockets when the request is made from a Secure Context"; secure WebSocket servers "must use TLS certificates that can be verified by the connecting user agent"; "The only exception to this is if both server and client are operating exclusively on loopback or localhost addresses" — [libp2p websockets spec](https://github.com/libp2p/specs/blob/master/websockets/README.md)
- WHATWG WebSockets Standard (Last Updated 19 October 2026): the constructor maps `http`→`ws` and the connection step fetches with scheme `http` for `ws` / `https` for `wss`, i.e. the handshake goes through Fetch and inherits its mixed-content policy; the WebSocket spec itself contains no mixed-content text — [websockets.spec.whatwg.org](https://websockets.spec.whatwg.org/)
- libp2p WebRTC-direct spec notes per-browser behaviour: SDP munging "is disallowed by the specification, but not enforced across the major browsers (Safari, Firefox, Chrome)"; Chromium's `WebRTC-NoSdpMangleUfrag` field trial "blocks this ufrag munging and so breaks this step" (hence the munging-free v2); "a browser uses a new UDP port for each `RTCPeerConnection`"; Firefox does not let the page read its own certificate fingerprint via `RTCCertificate#getFingerprints` (fingerprint must be parsed from local SDP) — [libp2p webrtc-direct.md](https://github.com/libp2p/specs/blob/master/webrtc/webrtc-direct.md)

### Inferences
- For a node the user runs at home, WebSocket is the only transport that needs a Web-PKI certificate; WebTransport (cert hash) and WebRTC (DTLS fingerprint) are both CA-free, but WebTransport needs UDP/HTTP/3 reachability and a hash the page must learn out of band, and WebRTC needs either a signalling channel or a libp2p-style "certhash in the address" trick.
- Safari/iOS support for WebTransport and cert hashes is new (26.4, March 2026) and tied to OS updates; Snowflake-style WebRTC is the only option with a long track record on iOS (Safari 11+).
- The WebKit post's "HTTP/2 and TCP fallback" sentence is unconfirmed by MDN/spec text and should be tested before relying on it for NAT'd home nodes without UDP forwarding.

### Gaps
- I did not find a WebKit or Apple document stating which iOS/macOS versions carry `serverCertificateHashes` beyond the BCD "26.4" value, nor whether WKWebView/in-app browsers expose it.
- No fetched source gives caniuse data for WebSocket itself (universally supported; not disputed) — omitted rather than cited from memory.
- Whether any browser actually ships WebTransport over HTTP/2 is unresolved (WebKit post vs MDN).

## Q2. Mixed-content rules: `ws://127.0.0.1`, `ws://` to LAN addresses, Chrome Local Network Access (LNA), Firefox and Safari in 2026

### Takeaway
Loopback (`127.0.0.0/8`, `::1`, and `localhost` when it is guaranteed to resolve to loopback) is a potentially trustworthy origin, so an https page may open `ws://127.0.0.1`; RFC1918 LAN addresses are not, so `ws://192.168.x.x` from an https page is blockable mixed content in every engine. Separately, Chrome 142 introduced an LNA permission prompt for public→local/loopback requests and Chrome 147 (April 2026) extended it to WebSockets and WebTransport; Firefox began rolling out an equivalent prompt in 2026; WebKit supports the spec but has not enabled it by default.

### Cited Findings
- Secure Contexts: an origin is potentially trustworthy if its scheme is `https` or `wss`, or its host matches `127.0.0.0/8` or `::1/128`; `localhost`/`*.localhost` only "If the user agent conforms to the name resolution rules" which "boil down to ensuring that localhost never resolves to a non-loopback address"; no private-network range is listed — [W3C Secure Contexts ED 2023-11-10](https://w3c.github.io/webappsec-secure-contexts/)
- MDN Mixed content: "Local resources are considered to be from secure origins, just like HTTPS origins. This includes `file:` URLs, and content accessed from loopback addresses such as `http://127.0.0.1/` or `http://localhost/`"; browsers auto-upgrade only image, video and audio; "all mixed content that is not upgradable" is blockable; upgrades are blocked "if the URL's host is an IP address rather than a domain name"; Safari blocks all mixed content by default — [MDN Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content)
- W3C Mixed Content ED (23 February 2023): "An a priori authenticated URL is equivalent to a potentially trustworthy URL"; a request is mixed content when "its URL is not a potentially trustworthy URL"; "Any mixed content that is not upgradeable as defined above is considered to be blockable" — [w3c.github.io/webappsec-mixed-content](https://w3c.github.io/webappsec-mixed-content/)
- Practical statement from a browser-P2P project: "`ws://` only works on `http://` sites" and "`wss://` only works on `https://` site with SSL certificates" — [Veilid veilid-wasm README](https://gitlab.com/veilid/veilid/-/raw/main/veilid-wasm/README.md)
- Chrome LNA blog (published June 9, 2025; update 2025-09-29: prompt "launching in Chrome 142"): address spaces are "local network" (RFC1918 ranges, 169.254/16, fc00::/7, fe80::/10, mapped IPv4), "loopback" (127.0.0.0/8, ::1/128) and "public"; the permission "can only be requested from secure contexts"; permission-gated local requests "are exempt from mixed-content checks" when Chrome can tell before DNS that the target is local — private-IP literal, `.local` name, or `fetch(..., {targetAddressSpace: "local"})`; WebSocket, WebTransport and WebRTC were listed as not-yet-gated gaps to be shipped "soon"; LNA replaces the paused Private Network Access (PNA) CORS-preflight design — [developer.chrome.com/blog/local-network-access](https://developer.chrome.com/blog/local-network-access)
- Chrome 147 (stable April 7, 2026): "WebSockets connections to local addresses now trigger permission prompts"; "All current LNA enterprise policies still apply to the LNA WebSockets restrictions"; WebTransport requests to the local network are "gated behind a permission prompt" and "This permission is restricted to secure contexts"; `WindowClient.navigate()` gap closed for subframes; WebRTC is not mentioned — [Chrome 147 release notes](https://developer.chrome.com/release-notes/147)
- Secondary reports on Chrome 147 (all from search snippets, pages not fetched): Citrix describes the new prompt "Local Network Access restrictions for WebSockets" and the `LocalNetworkAccessAllowedForUrls` policy — [Citrix CTX696569](https://support.citrix.com/external/article/CTX696569/chrome-147-and-edge-147-local-network-ac.html); a Webflow issue reports iframes additionally need `allow="loopback-network"` — [webflow/mcp-server#124](https://github.com/webflow/mcp-server/issues/124); a vendor page claims a plain-HTTP page from a public origin fails silently without a prompt — [Visualware](https://myconnectionserver.visualware.com/support/v11/userguide/chrome-lna-websocket); Olares claims Chrome 148 tightened checks further — [Olares known issues](https://docs.olares.com/manual/help/known-issues.html); Phoronix (8 April 2026) summarises the 147 change the same way — [Phoronix](https://phoronix.com/news/Chrome-147-Stable-Released)
- Firefox: Mozilla's KB "Control personal device and local network permissions in Firefox" describes a prompt near the address bar with allow/block and "Don't ask again", `network.lna.enabled` / `network.lna.block_trackers` prefs and a `LocalNetworkAccess` enterprise policy; per search snippets it is enabled from Firefox 149 for users with ETP Strict, with rollout to all users "beginning with Firefox 151" — fetch of the KB page was blocked by a client challenge, so the version numbers come from search snippets — [support.mozilla.org KB](https://support.mozilla.org/en-US/kb/control-personal-device-local-network-permissions-firefox)
- LWN (April 21, 2026) on Firefox 150: the release notes initially said LNA restrictions were "turned on for all users", then "Mozilla seems to have removed the local-network-access restrictions information" from the notes — [LWN 1068839](https://lwn.net/Articles/1068839/); the live Firefox 150.0 release notes (April 21, 2026) contain no LNA text — [Firefox 150.0 release notes](https://www.firefox.com/en-US/firefox/150.0/releasenotes/)
- A FOSDEM 2026 talk on Firefox LNA describes the model as three categories (localhost / local network / public) where requests toward a more private category need permission — from a search snippet, transcript not fetched — [FOSDEM 2026 talk transcript](https://ftp.fau.de/fosdem/2026/h1309/QCSKWL-firefox-local-network-access.vtt)

- The WebKit 26.4 feature post does not mention Local Network Access — [WebKit 26.4 post](https://webkit.org/blog/17862/webkit-features-for-safari-26-4/)

### Inferences
- `https://gluckdev.github.io` → `ws://127.0.0.1:<port>` is allowed by mixed-content rules in all engines (loopback is potentially trustworthy), which is why the existing web local mode works; from Chrome 147 it additionally triggers an LNA permission prompt (loopback counts as a local destination), and Firefox 149+/151+ will show a "personal device" prompt. The project's UI should expect and explain that prompt.
- `https://` page → `ws://192.168.1.10` (phone on the home LAN) is blocked as mixed content independent of LNA. Chrome's blog says permission-gated requests to a private-IP literal are exempt from mixed-content checks, and Chrome 147 made WebSockets permission-gated, but no fetched source states that plain `ws://<private IP>` is now permitted from an https page; treat it as untested. Firefox and Safari have no such exemption in any fetched source. The portable assumption for design A on a phone is therefore `wss://` with a trusted certificate, WebTransport with a hash, or WebRTC.
- LNA prompts are a UX cost for both designs when the node is on the user's own LAN or machine; a public VPS entry node (design B) avoids them entirely because public→public is not gated.

## Q3. How Snowflake, WebTunnel, libp2p WebRTC-direct, libp2p WebTransport and Veilid connect browsers to native nodes without CA certificates, and what the entry node learns

### Takeaway
Three patterns exist: (1) WebRTC with self-signed DTLS, authenticated by fingerprints carried in signalling (Snowflake, via a broker) or embedded in the dial address with no signalling at all (libp2p WebRTC-direct); (2) WebTransport with a self-signed cert whose hash is in the address and rotated every 14 days (libp2p); (3) plain `wss://` behind a real website with a CA certificate (Tor WebTunnel, Veilid). In every design the entry node learns the browser's IP address and sees only encrypted bytes of the inner protocol.

### Cited Findings
- Snowflake (USENIX Security 2024, Bocovich, Breault, Fifield, Serene, Wang): blocking resistance comes from "numerous, ultra-light, temporary proxies" that "accept traffic from censored clients using peer-to-peer WebRTC protocols"; proxies "are simple enough to be implemented in JavaScript, in a web page or browser extension" — [USENIX abstract](https://www.usenix.org/conference/usenixsecurity24/presentation/bocovich)
- Snowflake rendezvous: the client's rendezvous message is an SDP offer "which contains the information needed for a WebRTC connection, such as the client's external IP addresses and cryptographic data to secure a later key exchange"; the broker hands it to a polling proxy and relays the proxy's SDP answer; "Snowflake now supports three rendezvous methods" — domain fronting, AMP cache and Amazon SQS, all HTTPS — [Snowflake paper PDF §2.1](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf)
- Snowflake authentication without CAs: "The peers authenticate each other at the DTLS layer using certificate fingerprints that were exchanged during rendezvous"; a data channel is "UDP for network transport, DTLS ... and SCTP"; the DTLS of the data channel is only hop-by-hop, Tor's own encryption runs inside — [Snowflake paper PDF §2.3](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf)
- What a Snowflake proxy learns/does: "No complicated processing occurs at the proxy. The main value of a Snowflake proxy is its IP address"; "As the proxy negotiates the WebRTC connection with its client, it also connects to the bridge using WebSocket. Unlike the client connection, the bridge connection presents no challenges: it's just HTTPS to an open port on a server"; the broker "does not record nor publish the IP addresses of clients or proxies" — [Snowflake paper PDF §2.2-2.3 and §4](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf) (section numbers mapped from pdftotext headings; the §4 subsection title was not captured)
- Snowflake session continuity across proxies uses the Turbo Tunnel pattern with KCP and smux ("KCP provides reliability and retransmission, and smux detects and terminates timed-out streams"); because it "uses ordinary unprivileged APIs, its WebRTC can only look like WebRTC" — [Snowflake paper PDF §2.3, §1](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf)
- Snowflake proxy population: "Web browser extension proxies predominate, representing about 80% of" roughly "140,000 daily IP addresses"; a "web badge" runs "the same JavaScript code as the extension, but runs in an ordinary web page" — [Snowflake paper PDF §4](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf); the project site shows "127,599 Snowflakes (and counting)" and says Snowflake "uses a technology called WebRTC, which is commonly employed by videoconferencing software" — [snowflake.torproject.org](https://snowflake.torproject.org/)
- Tor WebTunnel operator requirements: "A self-hosted website, including a configurable web server (such as NGINX or Apache) and a domain under your control"; "A valid TLS certificate" (acme.sh suggested); a static IPv4 and inbound TCP "without NAT interference"; NGINX proxies a secret path to the bridge on `127.0.0.1:15000` with `Upgrade`/`Connection` WebSocket headers and sets `X-Real-IP`/`X-Forwarded-For` (so the bridge receives the client IP) — [community.torproject.org WebTunnel setup](https://community.torproject.org/relay/setup/webtunnel/)
- WebTunnel announcement (March 12, 2024): "inspired by HTTPT", designed to "mimic encrypted web traffic (HTTPS)", and "can coexist with a website on the same network endpoint, meaning the same domain, IP address, and port" — [Tor blog: Introducing WebTunnel](https://blog.torproject.org/introducing-webtunnel-evading-censorship-by-hiding-in-plain-sight/)
- libp2p WebRTC-direct: goal "No need for trusted TLS certificates"; address `/ip4/1.2.3.4/udp/1234/webrtc-direct/certhash/<hash>/p2p/<peer-id>`; the server is an ICE Lite agent on one UDP port, multiplexing by source IP:port; the browser builds a synthetic remote SDP answer from the multiaddr, so "no signalling is needed"; v1 derives ICE ufrag/password by munging (`libp2p+webrtc+v1/`), v2 puts the client's ICE password into the synthetic answer (`libp2p+webrtc+v2/<client_pwd>`) to avoid munging "that browsers are removing"; after DTLS the connection "provides confidentiality and integrity but not authenticity", so a Noise XX handshake over data channel id 0 with prologue `libp2p-webrtc-noise:<fingerprint_A><fingerprint_B>` binds the DTLS fingerprints; the server must "disable certificate fingerprint verification" during DTLS because it does not know the browser's fingerprint yet; "Browsers do not allow loading a custom certificate"; implementations "MUST support hash algorithm `sha-256`"; servers "SHOULD have a rate limiting mechanism" against STUN-triggered allocation; amplification limited by QUIC's three-times rule — [libp2p webrtc-direct.md](https://github.com/libp2p/specs/blob/master/webrtc/webrtc-direct.md)
- libp2p WebTransport: multiaddr is a QUIC multiaddr "followed by `/webtransport` and a list of multihashes of the certificates that the server uses" (omitted when a CA-signed cert is used: "libp2p nodes that possess a CA-signed TLS certificate MAY use that certificate"); "the validity of the certificate MUST be at most 14 days, and MUST NOT use an RSA key"; on boot the node creates "one self-signed certificate with a validity of 14 days, starting immediately" and "another certificate with the 14 day validity period starting on the expiry date of the first certificate", advertises both hashes, and "Once the first certificate has expired, the node starts using the already generated next certificate"; "The first stream that the client opens on a new WebTransport session is used to perform a libp2p handshake using Noise", with the server listing hashes in the `webtransport_certhashes` Noise extension and the client verifying "that all certificate hashes are contained in the server's list"; Chrome "implemented and shipped support for draft-02"; Firefox text is dated (described as still working on it) — [libp2p webtransport/README.md](https://github.com/libp2p/specs/blob/master/webtransport/README.md)
- libp2p WebSocket: `/ws`, `/tls/ws`, `/tls/sni/<name>/ws`, `/wss`, `/dns/example.com/wss`; secure servers need certificates "obtained externally and configured in the same way as you would for an HTTP server"; loopback is the only exception — [libp2p websockets spec](https://github.com/libp2p/specs/blob/master/websockets/README.md)
- Veilid WASM nodes: "TCP/UDP sockets are unavailable in the browser", limiting WASM nodes "to communicating using WebSockets"; a browser node "select[s] another node to act as its Inbound Relay"; bootstrap is direct `ws://bootstrap-v1.veilid.net:5150/ws` because DNS TXT lookup is unavailable in browsers; "Any wss:// URL containing an IP address causes an RPC error in veilid-core" (unsupported as of v0.2.3); "Running WASM on HTTPS sites [Not currently implemented]" — planned "Outbound Relays" that must have CA-trusted certificates — [Veilid veilid-wasm README](https://gitlab.com/veilid/veilid/-/raw/main/veilid-wasm/README.md)
- i2pd maintainer view of a WebRTC/WebSocket-based library (HumbleNet) in 2017: "It wouldn't be able to talk to any other routers ... it uses websockets and webrtc on the lower layers, it doesn't seem to be plain tcp/udp" — [PurpleI2P/i2pd#899](https://github.com/PurpleI2P/i2pd/issues/899)

### Inferences
- What each entry node learns: Snowflake proxy — client IP, encrypted DTLS payload, the fixed bridge it forwards to (it cannot see Tor circuits); WebTunnel bridge — client IP and the Tor link (it is a normal guard/bridge); libp2p server — browser IP and, after Noise, the browser's peer ID; Veilid relay — browser IP and node ID. None of these designs hides the browser's IP from its first hop; all rely on the inner protocol for content secrecy.
- libp2p WebRTC-direct is the only pattern that needs neither a CA certificate nor a signalling server nor a 14-day rotation: a node can publish `<ip>:<udp port> + sha-256 certhash` once per certificate lifetime (up to 365 days by WebRTC rules). It requires a UDP port reachable from the browser and server-side WebRTC (Pion/libdatachannel/webrtc-rs) in the node.
- Veilid's status (wss with IP certs unsupported, outbound relays unimplemented) shows the WebSocket-only route stalls exactly on the certificate problem for self-hosted nodes.

### Gaps
- I could not fetch the Snowflake GitLab wiki or README (HTTP 403); all Snowflake quotes are from the paper and project site.
- No WebTunnel spec/README was fetchable beyond the setup page and blog; I did not verify whether WebTunnel can run with a self-signed cert (the setup page requires "A valid TLS certificate").
- Veilid's current (2026) relay status is unverified; the README text may be stale (its last version marker is v0.2.3).

## Q4. Certificates for home/self-hosted entry nodes: Let's Encrypt with DDNS/DNS-01, WebTransport self-signed hashes with rotation, WebRTC DTLS fingerprints — which suits a user running a node at home for their own phone browser

### Takeaway
A home node can get a browser-trusted certificate only for a DNS name it controls (DNS-01 works without any inbound port; Let's Encrypt's new IP-address certificates require HTTP-01/TLS-ALPN-01 over a public IP and a 6-day lifetime, so they are useless behind NAT). CA-free alternatives are WebTransport with a self-signed ECDSA P-256 cert rotated at most every 14 days (the phone must learn the current hash) or WebRTC with a self-signed DTLS certificate verified by fingerprint, for which no spec-imposed rotation limit was found (the only cap fetched is the browser-side 365-day limit on certificates the browser itself generates). For "my phone through my own home node", WebRTC-direct-style fingerprints or a DDNS name + DNS-01 are the practical choices; WebTransport hashes work but need a hash-distribution channel and UDP reachability.

### Cited Findings
- Let's Encrypt: "Update: January 15, 2026. Six-day and IP address certificates are now generally available"; "requesting an IP address in a certificate will automatically select a short-lived certificate profile"; for IP addresses "validation will be restricted to the http-01 and tls-alpn-01 challenge types. The dns-01 challenge type will not be available because the DNS is not involved in validating IP addresses"; requires "an ACME client that supports ACME certificate profiles" — [letsencrypt.org 6-day and IP certs](https://letsencrypt.org/2025/01/16/6-day-and-ip-certs)
- Secondary coverage (search snippets, pages not fetched) adds that short-lived certificates are valid 160 hours (about six days), are opt-in via the "shortlived" ACME profile, and contain no OCSP or CRL URLs — [linuxiac](https://linuxiac.com/lets-encrypt-launches-ip-address-certificates-with-6-day-lifetimes/); [heise](https://heise.de/-11147604); these phrases were not in the fetched Let's Encrypt post text
- Challenge types: DNS-01 "asks you to prove that you control the DNS for your domain name by putting a specific value in a TXT record"; can be used to "validate domain names whose webservers aren't exposed to the public internet" and "allows you to issue wildcard certificates"; downside "Keeping API credentials on your web server is risky"; HTTP-01 "can only be done on port 80"; HTTP-01 and TLS-ALPN-01 "can be used to validate IP Addresses as well", DNS-01 "cannot be used to validate IP Addresses" — [letsencrypt.org challenge types](https://letsencrypt.org/docs/challenge-types/)
- WebTransport self-signed certificates: validity under two weeks, ECDSA P-256 only, SHA-256 hash, no revocation needed because the cert is ephemeral — [MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/WebTransport); [W3C §14.4](https://w3c.github.io/webtransport/); rotation recipe: generate current + next cert, advertise both hashes, switch at expiry, regenerate — [libp2p webtransport spec](https://github.com/libp2p/specs/blob/master/webtransport/README.md)
- WebRTC DTLS certificates: browser-generated, default 30-day expiry, maximum 365 days; ECDSA P-256 and RSA 2048 mandatory — [MDN generateCertificate](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/generateCertificate_static); server-side fingerprint carried in the dial address and bound by Noise — [libp2p webrtc-direct](https://github.com/libp2p/specs/blob/master/webrtc/webrtc-direct.md)
- Tor WebTunnel's answer to the certificate question is "domain under your control" + "A valid TLS certificate" + static IPv4 without NAT, i.e. not a home-NAT design — [WebTunnel setup](https://community.torproject.org/relay/setup/webtunnel/)
- Veilid rejects `wss://` with IP literals and requires CA-trusted certificates on relays — [Veilid README](https://gitlab.com/veilid/veilid/-/raw/main/veilid-wasm/README.md)
- Loopback exemption (same machine only): loopback origins are potentially trustworthy, so no certificate is needed when the browser and node share a host — [W3C Secure Contexts](https://w3c.github.io/webappsec-secure-contexts/); [MDN Mixed content](https://developer.mozilla.org/en-US/docs/Web/Security/Mixed_content)

### Inferences
- Let's Encrypt IP certificates do not help a home node: HTTP-01/TLS-ALPN-01 need port 80/443 reachable from Let's Encrypt on the public IP, the cert is for the public IP (not the LAN IP the phone uses), and it expires in six days.
- DNS-01 with a DDNS-capable DNS provider is the only Web-PKI path for a home node: the name can resolve to the LAN address (or public address with hairpin NAT), no inbound port is needed for issuance, and the 90-day cert renews unattended; the cost is a domain and an API credential stored on the node.
- WebTransport cert hashes: the node must rotate at least every 14 days and the phone's page must obtain the current hash (QR code, pasted string, or fetched from the node over a channel that itself needs trust); hash mismatch after rotation is a recurring failure mode unless two overlapping certs are advertised as libp2p does. HTTP/3 also requires UDP reachability from the phone.
- WebRTC DTLS fingerprint: no fetched spec limits the validity of the node's (server-side) DTLS certificate, and the browser-side cap is 365 days, so a hash pasted once can plausibly last months; there is no CA, no DNS, no 14-day rotation, and Safari/iOS support is mature. Whether browsers check the remote DTLS certificate's validity dates at all was not verified. Without a signalling server the libp2p WebRTC-direct trick (server as ICE Lite, certhash in address) is required, which the node must implement.
- Mixed-content note: `wss://` to a DDNS name is clean in all browsers; WebTransport and WebRTC bypass the mixed-content question entirely (they are not `ws://`), but Chrome's LNA prompt still applies to WebTransport on LAN targets from Chrome 147, and WebRTC gating is "planned" in Chrome's blog with no shipping version found.

### Gaps
- No fetched source on DDNS providers with ACME DNS-01 API support or on Let's Encrypt issuing for names that resolve to private IPs (Let's Encrypt validates only the DNS TXT record, so it should work, but this is inference).
- No source found on whether iOS Safari enforces the WebTransport 14-day rule identically to Chrome (WebKit bug has no behaviour notes).

## Q6. Design A (byte forwarder on the user's node) vs design B (NTCP2-over-WebSocket in the project's i2pd fork): what each endpoint learns, implementation effort, anonymity-set implications

### Takeaway
NTCP2 is a length-prefixed Noise XK stream over TCP whose initiator must already know the responder's static key, so a dumb forwarder (A) can relay it unchanged and learns only the browser's IP, the target router IP:port and timing, while remote I2P routers see the forwarder's IP as the browser router's address; it is the smaller protocol change and keeps the browser router's first hops unconstrained. Design B makes a project node the browser router's Noise peer and sole first hop: it learns the browser's IP, RouterIdentity and the second hop of every tunnel, and the small, enumerable set of project nodes becomes a guard-like concentration point. In both designs the dominant cost is the WASM router itself (NTCP2, netDB, tunnels), not the transport shim.

### Cited Findings
- NTCP2 is "a Noise-based TCP transport for router-to-router links" using "Noise_XKaesobfse+hs2+hs3_25519_ChaChaPoly_SHA256"; data phase: "Each frame is preceded by a two-byte length, big endian", obfuscated "by XORing a mask derived from SipHash"; "Maximum size including length field is 65537 bytes" — [i2p.net NTCP2 spec](https://i2p.net/en/docs/specs/ntcp2/)
- The initiator needs the responder's static key before connecting: "Alice knows Bob's static key already (K)"; "rs = Bob's 32-byte static key as published in the RouterInfo"; published NTCP2 addresses "must contain "host" and "port" options" plus "s", "i", "v" — [NTCP2 spec](https://i2p.net/en/docs/specs/ntcp2/)
- Outbound-only routers: "If Alice does not publish her NTCP2 address ... for incoming connections, she must publish a "NTCP2" router address containing only her static key and NTCP2 version"; that address "will not contain "i", "host" or "port" options, as these are not required for outbound NTCP2 connections"; "If the router is hidden, or NTCP2 is outbound only, '4' and '6' may be combined in a single address" — [NTCP2 spec](https://i2p.net/en/docs/specs/ntcp2/)
- Spec inconsistency in the same NTCP2 page: it also says "Alice must verify that all three options are present and valid before connecting using the NTCP2 protocol" (s, i, v), which conflicts with the outbound-only address that omits "i" — [NTCP2 spec](https://i2p.net/en/docs/specs/ntcp2/)
- RouterAddress: transport_style is "a String defining the transport protocol this router address uses" (1-256 bytes), with a 1-byte cost, an always-zero expiration and an options Mapping; RouterInfo "is one of two structures stored in the network database", signed by the router identity; the common-structures page has no rule about addresses with unknown transport styles — [i2p.net common structures](https://i2p.net/en/docs/specs/common-structures/)
- NetDB: "A router publishes its own RouterInfo by directly connecting to a floodfill router"; caps "U means that the router is NOT directly reachable on ANY transport address"; "A router should usually publish the R or U capability"; cap "H: Hidden" is listed without explanation; some routers send their RouterInfo through an exploratory tunnel to hide their IP from the floodfill — [i2p.net network database](https://i2p.net/en/docs/overview/network-database/)
- Transport selection is per message by bidding among transports; "I2P supports multiple transports simultaneously" — [i2p.net transport overview](https://i2p.net/en/docs/overview/transport/)
- websockify: "a WebSocket to TCP proxy/bridge. This allows a browser to connect to any application/server/service"; TLS via `--cert`/`--key` (auto-detected, `--ssl-only` available); a single fixed target, or multi-target via `--token-plugin`/`--token-source` where the client picks a target by `token` URL parameter or hostname; only RFC 6455 since 0.5.0; ports exist in JavaScript/Node.js, C, Clojure, Ruby — [novnc/websockify](https://github.com/novnc/websockify)
- Snowflake's design principle for an entry relay: "No complicated processing occurs at the proxy. The main value of a Snowflake proxy is its IP address" — [Snowflake paper](https://www.usenix.org/system/files/usenixsecurity24-bocovich.pdf)
- I2P's own future-work list includes an "indirect" transport for routers "that are not reachable by all other routers, as one form of restricted routes" — [i2p.net transport overview](https://i2p.net/en/docs/overview/transport/)
- i2pd upstream does not build to WASM ("bunch of problem, like `pthread`") — [PurpleI2P/i2pd#1817](https://github.com/PurpleI2P/i2pd/issues/1817)

### Inferences
- Design A, what each endpoint learns. Forwarder (user's node): browser IP (loopback or LAN/phone), the destination router IP:port of each connection (chosen by the browser via token/path, so the forwarder sees exactly which I2P routers the browser router peers with), connection timing and byte counts; it cannot read or modify NTCP2 payloads because the Noise XK session is keyed to the remote router's static key and the browser's ephemeral/static keys. Remote I2P routers: they see the forwarder's IP as the browser router's address; the browser router behaves like a NAT'd outbound-only router (address with only `s` and `v`, cap `U`) co-located with the user's node. The floodfill: a RouterInfo for the browser router if the browser publishes one (optional; an outbound-only router can stay unpublished/hidden at the cost of only building tunnels through routers it dials).
- Design B, what each endpoint learns. Project node: browser IP, the browser router's RouterIdentity (it completes Noise XK with it), every I2NP message the browser sends or receives (encrypted per hop, but the node is hop 1 of every browser tunnel, so it knows the second hop of each tunnel and all netDB lookups the browser issues through it), plus timing. Other routers: see the project node as the browser router's peer. Floodfills: if project nodes advertise a new transport style in their RouterInfo, the entire netDB can enumerate "browser entry nodes"; if the entry list is hard-coded in the Pages app instead (Snowflake/Veilid pattern), the netDB learns nothing but the list is a single point of blocking.
- Anonymity set. In A the browser router's first hops are arbitrary routers and its apparent IP is its own node, which is indistinguishable from an ordinary firewalled router; the set it blends into is "all U-capability routers". In B every browser router's tunnels start at one of a few project nodes, so (i) the project operator or anyone who compromises/coerces a project node sees all browser users' IPs and tunnel second hops, (ii) an observer of project nodes' traffic can count browser users and correlate timing, and (iii) the anonymity set is "users of this project's browser client", which is small. This is the Tor guard-concentration problem without guard rotation or a large guard pool.
- Implementation effort. A: forwarder is an existing component class (websockify with `--token-plugin`, or a small addition to the Rust node's existing WebSocket server from web local mode, which already does Host/Origin/capability checks), no i2pd changes; wss/cert handling needed only for the phone-at-home case (Q4). B: i2pd fork gains a WebSocket listener (plus TLS termination or a reverse proxy), NTCP2 framing over WS messages, a RouterAddress style or out-of-band entry list, rate limiting and abuse handling for public exposure; upstream merge is unlikely (Q5). Both: the WASM router must implement NTCP2 (X25519, ChaCha20-Poly1305, SipHash, AES-obfuscated ephemeral keys), RouterInfo/LeaseSet parsing, floodfill lookups, tunnel building (ECIES-X25519 garlic), and session layers; upstream i2pd cannot be compiled to WASM per its maintainers, so this is new code or a Rust/Go port.
- Hybrid: A's forwarder can also be the only hop of B — if a project VPS runs a forwarder with a token whitelist, browser routers without a home node still reach arbitrary routers, and the VPS learns the same as the forwarder in A (browser IP, router targets, timing) but not RouterIdentity or I2NP contents. That retains A's unconstrained first hops with B's "no home node" convenience, at the cost of the VPS seeing peer selection.
- Project-rule tension: both designs put a listener on the user's node (A: WebSocket forwarder; B: WebSocket transport on project nodes and possibly on user nodes). The memory note "no local ports" with the loopback web-mode exception already covers a loopback listener on the same machine; a LAN/phone-reachable listener is a new exception that needs owner sign-off.
- Transport choice for A on the phone-at-home path: `wss://` + DNS-01 cert, or WebRTC-direct-style fingerprints (no cert, no rotation, Safari 11+), or WebTransport hashes (two-week rotation, Safari 26.4+). On the same machine `ws://127.0.0.1` suffices but triggers Chrome 147+/Firefox 149+ LNA prompts.

### Gaps
- No I2P document states how routers treat a RouterAddress with an unknown transport style (common-structures page has no such rule); whether an "NTCP2WS" style would be silently ignored or cause RouterInfo rejection needs a code check in i2pd/Java I2P.
- The NTCP2 spec's "all three options present" check versus the s+v-only outbound address should be resolved by reading i2pd's RouterInfo address validation code before relying on an unpublished browser-router address.
- No measured data on how many I2P routers are outbound-only (`U`) in 2026, which bounds design A's anonymity set.
- Whether the browser router can usefully avoid publishing any RouterInfo (pure "hidden" operation) without breaking tunnel building is not stated in fetched docs; the netDB page defines the `H` cap but not its semantics.
- Per-engine behaviour of WebSocket binary frame size limits and backpressure for 64 KiB NTCP2 frames was not researched.
