# Prior art: anonymity routers and P2P overlay nodes running inside a web browser (WebAssembly/JavaScript)

Research date: 2026-11-01. Scope: every serious attempt found to run an anonymity router or overlay node in a browser tab, what architecture each used, what worked, what failed, and the measured limits. All URLs below were retrieved during this session unless marked **unverified**. Reddit was not searchable (the site blocks the crawler used here) and zzz.i2p is reachable only inside I2P, so those two venues are reported as gaps rather than as negative results.

Conventions: dates are the ones printed by the source (commit/issue/article dates). "Option C++/Emscripten", "Option Rust/wasm32", "Option Java/CheerpJ" and "Option new client-only router" refer to the four candidate approaches the reader is choosing between.

---

## Key question 1 — Has anyone run an I2P router (i2pd, Java I2P, go-i2p, emissary, any Rust implementation) in a browser or compiled one to WebAssembly?

### Takeaway
No. Across GitHub repositories, issues and code, the I2P forum (i2pforum.net), geti2p.net and the i2pd documentation, the only trace of the idea is a 2022 i2pd issue that the maintainers closed as "not possible for now" because of pthreads; no I2P implementation has a wasm target, a browser build, or an open issue tracking one as of 2026-11-01.

### Cited Findings
- i2pd issue #1817 "Add a wasm release target?" was opened 2022-12-03 by a user who wanted "i2pd offered as wasm to support fully decentralized browser-based applications using i2pd as the communication transport layer"; maintainer r4sas replied the same day "We are not planning add it and can not say anything about difficulties", then on 2023-01-06 "I looked in wasi-sdk, there is bunch of problem, like `pthread`, so I think it is not possible to make it work on wasm for now. Closing issue." — [PurpleI2P/i2pd#1817](https://github.com/PurpleI2P/i2pd/issues/1817)
- GitHub repository search (via `gh search repos`, which matches name/description/topics) returned zero results for each of: `i2pd wasm`, `i2p webassembly`, `i2p emscripten`, `i2p wasm`, `emissary i2p`, `i2p router rust`. The query `i2p browser` returned only browser *profiles/launchers* that talk to a locally installed router (i2p/i2p-browser, i2p/i2pbutton, i2p/i2p.firefox, mikalv/i2p-browser-build-scripts, etc.), none of which runs a router in the page — e.g. [i2p/i2p.firefox](https://github.com/i2p/i2p.firefox) ("A pre-configured browser profile … for easily configuring an I2P browser on Windows").
- GitHub issue search returned zero results for `wasm`, `emscripten`, `webassembly`, `cheerpj` in `PurpleI2P/i2pd` (other than #1817), `i2p/i2p.i2p`, `go-i2p/go-i2p` and `eepnet/emissary`; a global issue search for `i2p wasm` returned only two unrelated hits (a Skywire RFC and a Russian-language issue in fum-lab/fum) — [skycoin/skywire#4317](https://github.com/skycoin/skywire/issues/4317), [fum-lab/fum#122](https://github.com/fum-lab/fum/issues/122) (relevance of the second not verified).
- GitHub code search returned zero results for `__EMSCRIPTEN__` in PurpleI2P/i2pd, `cheerpj` in i2p/i2p.i2p, `syscall/js` in the go-i2p organisation, and `i2p wasm32` globally; in eepnet/emissary the string `wasm` occurs only in `Cargo.lock` files (transitive dependency names), not in source — [eepnet/emissary](https://github.com/eepnet/emissary).
- emissary (Rust) describes itself as "a lightweight and embeddable I2P router" with transports NTCP2 and SSU2, client protocols I2CP and SAMv3, and a layout of `emissary-core/` ("I2P protocol implementation as an asynchronous library"), `emissary-util/` ("runtime implementations and reseeder") and `emissary-cli/` ("`tokio`-based I2P router"); repo created 2023-12-31, 260 stars, last push 2026-10-30, now hosted at eepnet/emissary (the altonen/emissary URL redirects there) — [eepnet/emissary README](https://github.com/eepnet/emissary)
- emissary-core 0.4.0's `Runtime` trait (bounds `Clone + Unpin + Send + 'static`) requires associated types `TcpStream`, `UdpSocket`, `TcpListener`, `JoinSet`, `MetricsHandle`, `Instant`, `Timer` and functions `spawn`, `time_since_epoch`, `now`, `rng`, `join_set`, `register_metrics`, `timer`, `delay`, `gzip_compress`, `gzip_decompress`; the docs name tokio and futures as example backends, i.e. the runtime is pluggable, but a TCP stream/listener and a UDP socket type are still mandatory — [docs.rs emissary_core::runtime::Runtime](https://docs.rs/emissary-core/latest/emissary_core/runtime/trait.Runtime.html)
- The Skywire RFC "rfc(wasm-visor): reach .onion and .i2p from the nested browser — as reachability, not as anonymity" (opened 2026-08-29, open, no linked PRs) explicitly rejects running Tor or I2P inside the wasm visor and proposes native gateway visors instead, reasoning: "A tab has WebSocket, WebTransport and WebRTC and nothing else", "I2P's NTCP2 transport is TCP, and SSU2 is UDP, so both are unavailable to a tab", and asks that UI/docs say "reachability, not anonymity", citing Brave's Tor-in-a-tab as a disclosure precedent — [skycoin/skywire#4317](https://github.com/skycoin/skywire/issues/4317)
- Searches restricted to i2pforum.net, geti2p.net, i2pd.website and docs.i2pd.website for "I2P router browser WebAssembly" returned only browser-configuration pages (proxy on 127.0.0.1:4444) and the I2P Browser download page, which per the search summary says the I2P Browser is on hiatus (page not fetched; the URL redirected to i2p.net and returned 404 on 2026-11-01) — [geti2p.net browser download](https://geti2p.net/en/browser/download), [geti2p.net browser-config](https://geti2p.net/en/about/browser-config), [i2pd FAQ](https://docs.i2pd.website/en/latest/user-guide/FAQ/)
- A web search for "I2P router compiled to WebAssembly" surfaced only the native implementations (emissary-core on docs.rs, mikalv/go-i2p, i2pd packages, PeterZander/i2p-cs) with no wasm build — [docs.rs emissary-core source](https://docs.rs/crate/emissary-core/latest/source/src/router/mod.rs), [mikalv/go-i2p](https://github.com/mikalv/go-i2p), [PeterZander/i2p-cs wiki](https://github.com/PeterZander/i2p-cs/wiki)

### Inferences
- The project would be the first browser I2P router. There is no port to borrow from; the closest reusable precedent is the Tor work in Key question 2 (Arti → wasm), which maps onto Option Rust/wasm32 via emissary-core rather than onto i2pd.
- The i2pd maintainers' 2023 verdict was about wasi-sdk (WASI), not Emscripten; Emscripten does implement pthreads (see Key question 6), so the verdict does not by itself close Option C++/Emscripten — but it does mean upstream i2pd will not carry the port.
- emissary-core's Runtime abstraction is the most promising hook on the I2P side: a browser runtime would have to supply WebSocket/WebRTC-backed `TcpStream`/`UdpSocket` types that talk to a bridge, exactly as tor-js supplied a Snowflake/KPS `SocketProvider` to Arti. Whether the rest of emissary-core compiles for `wasm32-unknown-unknown` (threads, `Instant`, filesystem, SQLite-like storage) was not tested here.

### Gaps
- zzz.i2p and the I2P development forum are not reachable from the clearnet crawler; a search there could not be performed. Reddit (r/i2p) is blocked for the crawler used. Both are therefore "not searched", not "no results".
- No check was made of the I2P proposals index (geti2p.net/spec/proposals) beyond the domain-restricted search above.
- Whether emissary-core builds for wasm32 at all was not attempted.

## Key question 2 — Tor in the browser: Snowflake, WebTunnel, Arti-in-wasm experiments, and the Tor Project's position

### Takeaway
Tor is the only anonymity network with a working, full-protocol client in the browser as of 2026: the Ethereum Foundation compiled Arti to wasm (tor-js, Jan–Mar 2026, patches being upstreamed), two independent from-scratch browser Tor clients exist (hazae41/echalote in JS, cmyocyte/tor-wasm in Rust), and all of them reach relays through a WebSocket/WebRTC bridge or gateway because a tab has no TCP; the Tor Project itself ships only the Snowflake *proxy* in browsers and has treated a browser client as a long-horizon ticket since 2020.

### Cited Findings

**Snowflake and WebTunnel (what the Tor Project itself runs in browsers)**
- Snowflake's browser add-on (Firefox, Chrome, Edge) hosts a *proxy*: "Donate your bandwidth and help Tor users circumvent censorship"; the add-on "is designed for people who want to support others", not for personal circumvention — [snowflake.torproject.org](https://snowflake.torproject.org/)
- USENIX Security 2024 paper: "The temporary proxies are simple enough to be implemented in JavaScript, in a web page or browser extension"; proxies talk to clients with "peer-to-peer WebRTC protocols" and forward "to a centralized bridge"; "When an in-use proxy goes offline, its client switches to another on the fly, invisibly to upper network layers." — [Bocovich et al., USENIX Security '24](https://www.usenix.org/conference/usenixsecurity24/presentation/bocovich)
- The Tor client side of Snowflake (and WebTunnel) runs natively in Tor Browser/Orbot; the Tor Project pages fetched contain no statement that the Tor client itself runs in a browser — [snowflake.torproject.org](https://snowflake.torproject.org/)
- WebTunnel: "a pluggable transport that attempts to imitate web browsing activities based on HTTPT"; the bridge sits behind a web server (NGINX forwards a secret path to the bridge at 127.0.0.1:15000, with WebSocket upgrade headers); the setup page mentions no browser-side JavaScript/wasm component — [community.torproject.org WebTunnel bridge guide](https://community.torproject.org/relay/setup/webtunnel/). The only browser-client use of WebTunnel found is cmyocyte/tor-wasm's "WebTunnel (WS + HMAC)" transport option (below).

**Arti and the Tor Project's own tickets**
- Arti issue #20 "Try to build in wasm; identify blockers" was opened by nickm on 2020-10-13 ("Wouldn't it be nice to finally have Tor in your browser? Let's build for WASM and wee [sic] what if anything gets in the way.") and closed 2022-02-15 — [tpo/core/arti#20](https://gitlab.torproject.org/tpo/core/arti/-/work_items/20)
- Arti issue #343 "Allow a Runtime to have no raw TCP sockets (for wasm)", opened by nickm 2022-02-15 and still **open** on 2026-11-01: "in browser environments, you can't open raw TCP sockets from wasm; instead you have to use WebSockets or such. That's not a _complete_ showstopper: we could still use WebSockets for alternative transports, and then make those mandatory for wasm environments … We'll need a websocket-only implementation of snowflake or something that can get used when we don't have raw TCP. This ticket is probably pretty far down the road." — [tpo/core/arti#343](https://gitlab.torproject.org/tpo/core/arti/-/issues/343)
- The only wasm change merged early was MR !84 enabling the `js` feature of `getrandom` so crates pass `cargo check --target wasm32-unknown-unknown` — [tpo/core/arti!84](https://gitlab.torproject.org/tpo/core/arti/-/merge_requests/84)
- The Tor Project does compile Rust to wasm for the browser, but for the Lox bridge-distribution client inside Tor Browser, not for the Tor client: tor-browser-build issue 40818 "Enable wasm target for rust compiler" (MR 695, 2023) — [tor-browser-build#40818](https://gitlab.torproject.org/tpo/applications/tor-browser-build/-/issues/40818)
- A 2026-04-24 Tor forum post by Q_Misell proposed that a browser run the Tor client itself via a wasm Arti build (or the poster's own Torrosion library), noting browsers can make WebRTC and WebSocket connections and that "only four relays offer WebSocket connections" via Snowflake — [forum.torproject.org/t/21506](https://forum.torproject.org/t/tor-project-snowflake-relays/21506). The thread has **no replies** (Discourse JSON, 1 post, checked 2026-11-01). **Unverified:** a search-engine summary attributed to a Tor developer the view that a browser port is feasible but unsatisfying because "tor client instances (including Arti clients) are expensive to start up and run. You want one long-running instance, not a bunch of throwaway ones"; its origin could not be located (it is not in this thread, and the GitLab notes API for arti#20/#343 returned 401 Unauthorized).

**tor-js (Ethereum Foundation, Arti compiled to wasm) — the most complete precedent**
- Article "Embedding Tor in Browser Wallets, Frontends, and dApps" (2026-03-20, Andrew Morris & Ali Atiia; work period January–March 2026): Arti compiled to `wasm32-unknown-unknown`; branch `wasm-arti-client` holds "~6,100 lines of new Rust + TypeScript wrapper, with changes across 10+ upstream Arti crates" — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- Blockers and fixes (same article): `std::time::Instant` → `tor-time` crate on `web_time::Instant` (`performance.now()`), SystemTime migration across ~26–28 crates; threads/`Send` bounds → `tor-async-compat` proc-macro rewriting `#[async_trait]` to `?Send` on wasm (51 files); native sockets → Snowflake transport over WebSocket or WebRTC (`SnowflakeChannelFactory`, +741 lines; stack WebSocket/WebRTC → KCP → SMUX → TLS (rustls) → Tor); SQLite → in-memory directory/state synced to IndexedDB; `ring` → `futures-rustls` on `rustls-rustcrypto` (pure Rust; diff −8,434/+307 lines); `getrandom` `wasm_js` feature; `psl` replaced by 1Password's `public-suffix` (~430 KB trie), which cut wasm *compile-time* memory from "10GB+" to "~2.6GB" — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- Measured: first prototype bootstrap "~3 minutes" in wasm vs "~15 seconds" native; ~10,000 microdescriptors; using `crypto.subtle.digest()` avoided "~3 seconds of overhead for 10k entries". Not reported: wasm size, throughput, circuit-build time, runtime memory — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- Trust-model caveats stated by the authors: the fast-bootstrap archive (consensus, authority certs, microdescriptors) is fetched over plain HTTPS before Tor is up, so the user's IP is visible to the bootstrap server; consensus/authority-cert signatures are verified with Arti's parsers, "a weaker trust model than standard Tor bootstrapping"; a compromised bootstrap server "could serve a malicious view of the network"; `rustls-rustcrypto` is alpha; reduced `performance.now()` precision may affect congestion control/padding; no process isolation from the dApp; wasm fingerprinting risk; WebSocket bridges have a "centralizing effect", so WebRTC-by-default is a priority — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- Upstreaming: `tor-time` and `tor-async-compat` "under review", weekly syncs with the Tor Project since January 2026 — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/). EF monthly update dated 2026-02-28: "By February 2, `arti-client` compiled to WebAssembly for the first time, a major milestone"; "end-to-end functionality achieved (Feb 10)"; "The team pivoted fully to making the real Arti client work in the browser (over maintaining a separate implementation)"; "Upstream merge strategy: break work into multiple smaller PRs for Tor Project review"; "Project name consolidated under TorJS (replacing separate Arti/webtor-rs naming)"; March goal "Finish testing and auditing of the Arti WASM client in collaboration with the Tor Project"; "The Tor Project expressed interest in revisiting PIR for this purpose" (private retrieval of relay descriptors at bootstrap) — [EF update February 2026](https://reads.ethereum.foundation/blog/update-february-2026/). EF's connectivity page lists tor-js as "Shipped" and says "Builds are reproducible: byte-identical WASM on x86_64 and aarch64 across three machines" — [reads.ethereum.foundation/foundations/connectivity](https://reads.ethereum.foundation/foundations/connectivity/). **Unverified:** a search-engine summary of the former EF workstream page (now redirected; not fetched) said the Tor Project team had mixed views on the approach and that as of 2Q26 Tor was reviewing and merging the wasm compatibility work.
- Shipped package (repo created 2025-10-21, 22 stars, pushed 2026-10-29, MIT, status "Experimental"): wrapper 33 kB gzip with wasm fetched from CDN, or 2.6 MB gzip with wasm embedded, or 32 kB + 1.9 MB `tor_js_bg.wasm`; "Browsers can't open raw TCP sockets, so to reach Tor relays from a browser you connect through a **gateway** — a small server that proxies relay connections and serves a fast-bootstrap snapshot"; the gateway is dialed over KPS ("WebRTC in browsers; QUIC in Node.js"), each relay connection is an HTTP `CONNECT` tunnel on its own KPS stream; storage is IndexedDB in browsers; the public demo gateway is "for demonstration only (limited capacity, may disappear at any time)" — [ethereum/tor-js README](https://github.com/ethereum/tor-js), [tor-js issue #6 "Security validation"](https://github.com/ethereum/tor-js/issues/6), [ethereum.github.io/tor-js](https://ethereum.github.io/tor-js/)
- Independent measurement (tor-ethers, 2026-05, Node.js with direct TCP, not browser): first `tor.ready()` "~10-30 seconds" with the "brotli-compressed ~3MB" fast-bootstrap bundle; steady-state ~800–1000 ms per simple RPC vs ~100–200 ms clearnet (+500–700 %); `eth_getCode` (~26 KB response) ~1200–1500 ms; "Most public RPCs block Tor exit nodes" — [andyguzmaneth/tor-ethers](https://github.com/andyguzmaneth/tor-ethers)

**Independent from-scratch browser Tor clients**
- hazae41/echalote (created 2022-11-04, 38 stars, updated 2026-10-27): "Zero-copy Tor protocol for the web (JS + WebAssembly)"; "Use at your own risk … It has security issues"; features "Unsafe Tor protocol (with Ed25519, ntor, kdf-tor)", "Meek (HTTP) transport (without domain-fronting)", "Snowflake (WebRTC/WebSocket) transport (without domain-fronting)", "Unsafe TLS"; the README example dials `wss://snowflake.bamsoftware.com/` and extends a circuit by hand — [hazae41/echalote](https://github.com/hazae41/echalote). The EF said its earlier Echalot-based module suffered "behavioral divergence from the canonical Tor client" and security gaps identified by the Tor Project that "would have required essentially reimplementing Tor to close" — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- cmyocyte/tor-wasm (created 2026-02-26, last commit 2026-02-27, 1 star, AGPL-3.0, "Not Audited"): "A minimal Tor client written from scratch for WebAssembly", reusing Arti's `tor-rtcompat` and crypto crates; its README claims neither C Tor nor Arti "can be directly compiled to WebAssembly" (Arti: "Depends on tokio, native networking"); bundle "538KB gzipped"; transports WebSocket → WebTunnel (HMAC probe-resistant) → meek via Cloudflare Worker; connection modes Direct (Browser → Bridge WS→TCP → Guard), Blinded two-hop (Bridge A sees client IP, Bridge B sees guard IP) and Peer-bridge (volunteer WebRTC→WS proxy); consensus is fetched via a Cloudflare Worker and verified against "at least 5 of 9" hard-coded directory authorities; offline bundle "Single ~3-4MB HTML file"; targets "Chrome, Firefox, Safari, iOS Safari" and a PWA app — [cmyocyte/tor-wasm](https://github.com/cmyocyte/tor-wasm)
- webtor-rs (Igor Barinov) "ported the concept to Rust but remained a separate implementation" per the EF; the GitHub repo igor53627/webtor-rs no longer resolves (gh: "Could not resolve to a Repository", 2026-11-01); a third-party summary said it used Arti 1.8.0 / tor-proto 0.37.0 and was "not designed for WASI runtimes" (**unverified**, deepwiki returned 429) — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/), [deepwiki webtor-rs](https://deepwiki.com/igor53627/webtor-rs/2.1-project-goals)

**Academic**
- No PETS/FOCI paper on a wasm onion-routing client was found. Nearest: "Just add WATER: WebAssembly-based Circumvention Transports" (FOCI 2024) — wasm for pluggable transports, not a client — [petsymposium.org FOCI 2024](https://www.petsymposium.org/foci/2024/foci-2024-0003.php); "When Your Browser Becomes The Paper Boy: An Anonymous Browser Network" (IFIP SEC 2018) — browsers forming an onion-routing overlay among themselves — [IFIP SEC 2018 abstract](https://ifipsec2018.pwr.edu.pl/abstract28.html)

### Inferences
- The wasm-Arti port is the single most relevant blueprint for Option Rust/wasm32: its blocker list (Instant/SystemTime, `Send` bounds, sockets, SQLite, C crypto, getrandom) is exactly the list a wasm port of emissary-core would hit, and its solutions (web_time, `?Send`, pluggable socket provider, IndexedDB-backed state, pure-Rust crypto) are reusable patterns.
- Every working browser Tor client, including the Tor-Project-adjacent one, needed a server-side bridge/gateway that terminates WebSocket/WebRTC and opens TCP to relays. The bridge sees the client IP and the first-hop relay (both tor-js and tor-wasm say so), which is why tor-wasm added two-hop "blinded" bridges and tor-js wants WebRTC by default. An I2P browser router would face the identical bridge-trust problem for NTCP2/SSU2 peers.
- The Tor Project's position is best read from its tickets: desirable in principle (nickm 2020), never prioritised (#343 open since 2022, "pretty far down the road"), now being upstreamed on EF initiative with "mixed views". The 3-minute vs 15-second bootstrap and the EF's own list of trust weaknesses are the Tor Project's likely reasons for caution.
- "From scratch" browser clients (echalote, tor-wasm) appeared faster but carry explicit "unsafe"/"not audited" labels; the EF abandoned the from-scratch path precisely because it diverged from the canonical client. This argues against Option new client-only router unless its protocol surface is tiny.

### Gaps
- Tor Project developer comments on arti#20/#343 could not be read (GitLab notes API 401 without a token); the 2026 forum thread has no replies. The "expensive to start up" quote is therefore unverified and should not be cited as the Tor Project's position.
- No browser-side measurements of tor-js exist in the sources (only Node numbers); wasm memory at runtime and throughput are unreported.
- webtor-rs source is gone; its architecture is known only second-hand.
- WebTunnel was not researched beyond the bridge setup guide: it is a pluggable transport of the native Tor client, and no browser-client role for it was found other than tor-wasm's reuse of the name/handshake.

## Key question 3 — Veilid: its WebAssembly build and WebSocket transport for browser nodes

### Takeaway
Veilid is the only overlay in this survey that treats browser nodes as first-class network members: `veilid-wasm` (Rust → wasm via wasm-bindgen) joins the real network over WebSocket only, gets inbound reachability by electing a native node as "Inbound Relay", bootstraps from a hard-coded `ws://` server because DNS is unavailable, and still cannot run from an HTTPS page against IP-addressed peers because the planned "Outbound Relays" are "[Not currently implemented]".

### Cited Findings
- "TCP/UDP sockets are unavailable in the browser. This limits WASM nodes to communicating using WebSockets." Browser nodes cannot open ports, so they pick another node as an Inbound Relay, and other nodes connect back over WebSocket — [veilid-wasm README (main)](https://gitlab.com/veilid/veilid/-/blob/main/veilid-wasm/README.md)
- "Lookup of DNS records is unavailable in the browser", so TXT-record bootstrapping fails; browser nodes must list a `ws://…/ws` bootstrap URL in `network.routing_table.bootstrap[]` — [veilid-wasm README](https://gitlab.com/veilid/veilid/-/blob/main/veilid-wasm/README.md)
- `ws://` works only on `http://` pages and `wss://` only on `https://` pages; a `wss://` URL containing an IP address "is unsupported by Veilid as of v0.2.3" and causes an RPC error after which the node loses communication; Outbound Relays, which would be "hosted alongside the web app", need CA-trusted certificates and would let wasm nodes reach TCP/UDP/WS/WSS peers, are marked "[Not currently implemented]" in the current README — [veilid-wasm README](https://gitlab.com/veilid/veilid/-/blob/main/veilid-wasm/README.md)
- Build: a Rust crate using `wasm-bindgen` to expose `veilid-core::VeilidAPI`, with `tsify` + `serde-wasm-bindgen`; tests run in Firefox via `wasm_test_js.sh` — [veilid-wasm README](https://gitlab.com/veilid/veilid/-/blob/main/veilid-wasm/README.md)
- Changelog history of browser support (latest released version listed: 0.5.7, undated in the file): 0.1.8 "Fix WASM compilation"; 0.2.1 "Use `getrandom` in WASM for RNG", "Increase privacy for WASM builds by rewriting internal paths"; 0.2.2 "Reverse connect for WASM nodes"; 0.3.0 "Failures to hole-punch UDP or reverse-connect TCP or UDP now falls back to inbound relaying"; 0.3.4 "noise for WASM in browsers when websockets are RST dropped rather than handshake closed"; 0.4.2 "Up to 256 concurrent each of TCP and WebSocket connections now, up from 32" (veilid-server), "wasm tests went from 731 seconds to 112 seconds"; 0.4.4 "Remove wee_alloc due to memory leak issues"; 0.4.8 "Add `require_inbound_relay` option … forces OutboundOnly/InboundRelay mode"; 0.5.0 "Deprecation of WSS protocol"; 0.5.2 "Reduced size of veilid_wasm_bg.wasm by 25% by disabling tracing instrumentation"; 0.5.3 "Ensure WebSocket connections don't ever resolve hostnames except for bootstrap"; 0.5.4 "Proper IPv6 support for `wasm32-unknown-unknown`", "No more wasm-pack"; 0.5.6 "veilid-wasm and veilid-flutter WASM blob size greatly reduced (-47%)", "`backtrace` support removed for wasm32 builds" — [Veilid CHANGELOG](https://gitlab.com/veilid/veilid/-/blob/main/CHANGELOG.md)
- Unreleased (as of 2026-11-01): "In a browser, `app-lifecycle` follows a page's visibility, back/forward cache and freeze events"; "a node with no datagram protocol, such as a browser, keeps only ordered routes"; "New `app-lifecycle` feature, on in veilid-flutter and veilid-wasm, saves the routing table"; "A second browser `online` or `offline` event while a detached node was not listening no longer panics"; BLAKE3 "uses its WASM SIMD implementation on wasm32, which adds 14 KB to the `.wasm`", "supported by browsers since Safari 16.4" — [Veilid CHANGELOG](https://gitlab.com/veilid/veilid/-/blob/main/CHANGELOG.md)

### Inferences
- Veilid solved the inbound problem by a protocol-level feature (native nodes agree to relay for browser nodes) rather than by a separate bridge daemon; the price is that browser nodes are "OutboundOnly/InboundRelay" clients that never relay for others.
- The WSS-with-IP restriction is the browser CA rule biting a DHT whose peers are addressed by IP; Veilid's answer (CA-certified outbound relays co-hosted with the web app) is still unbuilt after ~3 years, which signals how hard the certificate problem is for an overlay whose native nodes have no domain names. libp2p's WebTransport/WebRTC-direct certhash mechanisms (Key question 4) are the engineering answer Veilid lacks.
- Veilid's most recent work (app-lifecycle, freeze/visibility events, saving the routing table on freeze) is direct evidence that background-tab suspension is a real operational issue for browser overlay nodes.

### Gaps
- No throughput, latency, CPU or memory figures for veilid-wasm were found; the changelog gives only size deltas (−25 %, −47 %) without absolute numbers.
- Whether browser nodes can store DHT records or only read them was not stated in the README fetched.

## Key question 4 — libp2p browser nodes: how browser peers connect to native peers, and lessons about certificates and NAT

### Takeaway
libp2p is the only stack that solved browser↔native connectivity without CA certificates: WebTransport (certhash in the multiaddr, certificates valid ≤14 days with rotation, Noise handshake binding the hash) and WebRTC-direct (certhash + SDP munging, server must be publicly reachable) let any browser dial any public native node, while browser↔browser goes through a circuit-relay-v2 signalling path; WebSocket "never saw widespread adoption" in libp2p because browsers demand a CA-signed certificate.

### Cited Findings
- "When connecting to a WebSocket server, browsers require the server to present a TLS certificate signed by a trusted CA (certificate authority). Few nodes have such a certificate, which is the reason that WebSocket never saw widespread adoption in the libp2p network." WebTransport instead lets browsers "accept the server's certificate by checking the (SHA-256) hash of the certificate (using the `serverCertificateHashes` option), even if the certificate is 'just' a self-signed certificate … as long as the browser knows the certificate hash in advance" — [libp2p docs source: webtransport.md](https://github.com/libp2p/docs/blob/master/content/concepts/transports/webtransport.md)
- WebSocket costs 6 RTTs to a usable libp2p connection (TCP, TLS 1.3, WS upgrade, multistream security, security handshake, muxer negotiation) vs 3 RTTs for WebTransport over QUIC — [libp2p docs source: webtransport.md](https://github.com/libp2p/docs/blob/master/content/concepts/transports/webtransport.md)
- Implementation status: WebTransport in go-libp2p is "fully implemented, functional, and listed as a default transport", enabled by default in Kubo; js-libp2p "also supports WebTransport"; "WebTransport support in Wasm environments also exists in rust-libp2p" (PR 4015) — [libp2p docs source: webtransport.md](https://github.com/libp2p/docs/blob/master/content/concepts/transports/webtransport.md)
- WebTransport spec: "the validity of the certificate MUST be at most 14 days, and MUST NOT use an RSA key"; nodes keep a current and a next certificate and advertise both hashes; because "the self-signed certificate doesn't allow the nodes to authenticate each others' peer IDs … it is therefore necessary to run an additional libp2p handshake" (Noise) whose `webtransport_certhashes` extension must include the hash of the certificate in use; Chrome "implemented and shipped support" for draft-02 with `serverCertificateHashes`, Firefox was in progress — [libp2p specs: webtransport](https://github.com/libp2p/specs/blob/master/webtransport/README.md)
- WebRTC-direct spec: goal "No need for trusted TLS certificates"; the multiaddr carries `/webrtc-direct` plus a multihash of the server certificate; the browser constructs the remote SDP locally ("SDP munging"), which "is disallowed by the specification, but not enforced across the major browsers"; Chromium's `WebRTC-NoSdpMangleUfrag` field trial "blocks this ufrag munging and so breaks this step" in v1, so v2 is recommended; the server must "disable certificate fingerprint verification" and rely on a later Noise handshake; "Given that _B_ is publicly reachable, _B_ acts as a ICE Lite agent" (no NAT traversal in this mode); client MUST set `a=max-message-size:16384`; "a browser uses a new UDP port for each `RTCPeerConnection`"; servers must rate-limit STUN because each message allocates memory — [libp2p specs: webrtc-direct.md](https://github.com/libp2p/specs/blob/master/webrtc/webrtc-direct.md)
- WebRTC (browser-to-browser) spec: "The WebRTC browser APIs do not support half-closing of streams nor resets of the sending part of streams", so libp2p adds protobuf framing with FIN/STOP_SENDING/RESET_STREAM/FIN_ACK; "Encoded messages including their length prefix MUST NOT exceed 16kiB to support all major browsers"; keep messages ≤1204 bytes to avoid head-of-line blocking because the browser hides the path MTU; FAQ: "Why not use a central TURN servers? … libp2p should rely as little as possible on central infrastructure" (Circuit Relay v2 is used instead) — [libp2p specs: webrtc README](https://github.com/libp2p/specs/blob/master/webrtc/README.md)
- libp2p docs (webrtc.md): "libp2p WebRTC enables browsers nodes to connect to public server nodes without those endpoints providing a TLS certificate"; WebRTC in libp2p uses data channels (SCTP over DTLS) and ICE for NAT traversal — [libp2p docs source: webrtc.md](https://github.com/libp2p/docs/blob/master/content/concepts/transports/webrtc.md)
- Safari/iOS support for `serverCertificateHashes` is listed as arriving in iOS Safari 26.4, and MDN marks WebTransport "Baseline" since March 2026 (caniuse/MDN; no Apple primary source found) — [caniuse serverCertificateHashes](https://caniuse.com/mdn-api_webtransport_webtransport_options_servercertificatehashes_parameter), [MDN WebTransport()](https://developer.mozilla.org/docs/Web/API/WebTransport/WebTransport)
- Reference app: libp2p/universal-connectivity, "Realtime decentralised chat … between multiple programming languages (Go, Rust, TypeScript) and runtimes (Web, native binary) using QUIC, WebRTC and WebTransport" (updated 2026-10-29) — [libp2p/universal-connectivity](https://github.com/libp2p/universal-connectivity)
- Emscripten's view of the same problem: "Currently Emscripten does not provide a C/C++ API for interacting with WebRTC" and none for WebTransport datagrams either — [emscripten networking docs](https://emscripten.org/docs/porting/networking.html)

### Inferences
- What libp2p changed to admit browsers: it added *new transports with certhash-in-address* and an extra Noise handshake, and a *relay protocol* (circuit relay v2) for signalling — it did not change the core wire protocols. An I2P browser router cannot do the same unless native I2P routers also learn a browser-dialable transport (a "NTCP2-over-WebTransport" or "SSU2-over-WebRTC-datachannel" RouterAddress), which is a network-wide protocol change; otherwise a bridge is unavoidable.
- The certificate lesson is decisive for the bridge design: if the bridge is a native node addressed by IP (as I2P routers are), only WebTransport-with-certhash or WebRTC-direct can reach it from an HTTPS-served PWA; WSS needs a domain name and a CA certificate. Veilid's stalled "Outbound Relay" shows the cost of ignoring this.
- rust-libp2p's wasm WebTransport support means the Rust ecosystem already has a browser-side WebTransport client usable from a wasm32 build, which favours Option Rust/wasm32 for the bridge leg.

### Gaps
- The connectivity.libp2p.io matrix page and blog.libp2p.io could not be fetched (TLS certificate mismatch at the fetcher); the per-implementation matrix (e.g. rust-libp2p WebRTC-direct in wasm, js-libp2p WebRTC-direct dialing) was not confirmed from the live site.
- No performance figures for browser libp2p nodes were collected.

## Key question 5 — Other overlays with browser clients: Nym, Lokinet/Session, Hypercore/Holepunch, Yggdrasil, Tailscale/NetBird, WebTorrent (and Skywire). What did each change to admit browser peers?

### Takeaway
Every overlay that admitted browsers did so by adding a WebSocket (or WebRTC) *edge* — a native node or relay that speaks the browser transport and proxies the real protocol — rather than by porting the whole node: Nym runs a real mixnet client in a Web Worker but enters via a gateway WebSocket; Hyperswarm relays its DHT over WebSocket; Tailscale and NetBird run WireGuard-in-wasm but carry it only over DERP/relay WebSockets; WebTorrent forked the swarm (WebRTC peers can only talk to WebRTC-capable peers); Yggdrasil added `ws://`/`wss://` peering for native nodes but has no browser node; Lokinet and Session have no browser client at all.

### Cited Findings

**Nym (mixnet client really runs in the browser)**
- "A browser or WebView has neither" raw sockets nor a filesystem, so "it runs a WASM client inside a Web Worker"; browser has only "WebSockets and `fetch`, under mixed-content rules"; "The mixnet behaviour is identical in both modes, only the integration shape differs"; `nym-smoldvpn` has no browser build because its datapath does "not compile for `wasm32-unknown-unknown`" — [nym.com/docs/developers/browsers](https://nym.com/docs/developers/browsers)
- Architecture: the mix-* packages are "thin facades over a single shared tunnel, which runs in a Web Worker"; one `smolmix-wasm` instance per page; mixnet work "is CPU-bound and must not block the UI thread"; smolmix-wasm contains an IPR client that "Opens a WebSocket to an entry gateway" (WSS by default), `smoltcp` ("the browser exposes no raw sockets") and `rustls` with "the Mozilla CA bundle compiled into the WASM"; "The tunnel is one-shot per WASM instance" — after disconnect "the page must reload to build a new tunnel" — [nym.com/docs/developers/mix-architecture](https://nym.com/docs/developers/mix-architecture)
- mixFetch v2 diagram: "mix-tunnel (shared singleton, Web Worker, smolmix-wasm)", "smoltcp userspace TCP/IP + rustls TLS", "WebSocket to entry gateway", "Nym mixnet (3 mix layers)", exit via "IPR exit gateway"; gaps vs native fetch: "no cookies or credentials, no HTTP cache, no `AbortController`"; "HTTPS-only in practice" — [nym.com/docs/developers/mix-fetch](https://nym.com/docs/developers/mix-fetch)
- The WebAssembly client "allows any webassembly-capable runtime to build and send Sphinx packets to the Nym network" and supports "building Sphinx packets from mobile apps and browser-based client-side apps"; advice: "do not load external resources from CDNs" because "A lot of metadata leaks when you make an HTTP request from a browser window" — [nym.com webassembly-client](https://nym.com/docs/developers/clients/webassembly-client)

**Hypercore / Holepunch**
- `@hyperswarm/dht-relay`: ":test_tube: This project is still experimental. **Do not use it in production**"; "Relaying the Hyperswarm DHT over framed streams to bring decentralized networking to everyone"; relaying side wraps a real `hyperdht` instance, relayed side (e.g. browser) constructs `new DHT(stream)` over a WebSocket wrapper; the API then "matches that of the Hyperswarm DHT" — [holepunchto/hyperswarm-dht-relay](https://github.com/holepunchto/hyperswarm-dht-relay)
- A community WebSocket relay server (dht-relay-wss) is described as alpha with possible breaking changes — [HDegroote/dht-relay-wss](https://github.com/HDegroote/dht-relay-wss)

**Yggdrasil**
- yggdrasil-go changelog: 0.5.7 (2024-08-05) "WebSocket support for peerings, by using the new `ws://` scheme in `Listen` and `Peers`" and "`wss://` scheme can be used to connect to a WebSocket peer behind a HTTPS reverse proxy"; 0.5.14 (2026-06-19) `?origin=` parameter for WebSocket peer URIs; 0.5.15 (2026-10-24) WebSocket timeouts and SNI; the changelog has "no mentions of WebAssembly, wasm, or browser" — [yggdrasil-go CHANGELOG](https://github.com/yggdrasil-network/yggdrasil-go/blob/develop/CHANGELOG.md)
- Yggstack (userspace SOCKS/port-forwarder build) lists "Web browser access" among the gaps it fills, but it is a separate native binary, not a browser node — [yggdrasil-network/yggstack](https://github.com/yggdrasil-network/yggstack); the "Yggdrasil on ChromeOS" extension routes 0200::/7 through a separately installed Yggstack proxy — [Chrome Web Store](https://chrome.google.com/webstore/detail/yggdrasil-on-chromeos/hcgljgobhoaeojnhikfmnhdpmgbmflec)
- GitHub search `yggdrasil wasm` returned only unrelated projects (a language runtime and an Unleash feature-flag spike) — [sighphyre/yggdrasil-wasm](https://github.com/sighphyre/yggdrasil-wasm)

**Tailscale (WireGuard + userspace stack in wasm)**
- Tailscale SSH Console (2022-10-27, beta): "your browser becomes a Tailscale client"; the team "ported the following to WebAssembly": the client, WireGuard, "a complete userspace network stack (from gVisor)" and an SSH client; "added WebSockets as another transport for DERP" because the DERP HTTP client was incompatible with the browser's fetch()-based transport; "SSH traffic goes through DERP relays"; ephemeral auth key, in-memory WireGuard keypair, reauthentication per session; the first binary was "rather…large", trimmed by "a few megabytes" with "still more work to be done here" — [tailscale.com/blog/ssh-console](https://tailscale.com/blog/ssh-console)
- `cmd/tsconnect` "builds and serves the static site that is generated for the Tailscale Connect JS/WASM client"; published as npm `@tailscale/connect`; dev-mode state in `sessionStorage` — [tailscale/tailscale cmd/tsconnect](https://github.com/tailscale/tailscale/tree/main/cmd/tsconnect)
- WebVM (2022-10-05): "the browser does not expose access to lower-level protocols such as UDP and TCP"; the Tailscale wasm module is "16MB" (wasm-opt saved only ~1 MB) versus the whole CheerpX VM under 6 MB, so networking is loaded lazily on login; lwIP compiled to wasm handles TCP/IP over a MessageChannel TUN; DERP "uses regular HTTPS and WebSockets when direct connections fail"; ephemeral nodes disappear after inactivity and a reload requires logging in again — [labs.leaningtech.com WebVM post](https://labs.leaningtech.com/blog/webvm-virtual-machine-with-networking-via-tailscale)

**NetBird (same pattern, 2026)**
- "The heart of the Browser Client is a NetBird peer compiled to WebAssembly (WASM)" using wireguard-go; "All traffic routes through NetBird relay servers using WebSocket while maintaining end-to-end WireGuard encryption"; temporary peers are removed "after 10 minutes of inactivity"; no WebRTC/ICE path is documented (page updated 2026-06-15) — [docs.netbird.io browser-client-architecture](https://docs.netbird.io/about-netbird/browser-client-architecture)

**WebTorrent (hybrid swarms)**
- WebTorrent "uses WebRTC instead of TCP/uTP as the transport protocol"; a browser peer "can only connect to other clients that support WebTorrent/WebRTC" and "can only download torrents that are seeded by a WebRTC-capable torrent client"; `webtorrent-hybrid` (Node.js) "can download torrents from WebRTC peers or TCP peers (i.e. normal peers)"; "we made a few changes to the tracker protocol" (WebSocket `wss://` trackers for signalling) — [webtorrent.io/faq](https://webtorrent.io/faq)

**Lokinet / Session**
- Session's FAQ names only desktop, Android and iOS clients ("Session's desktop, Android, and iOS clients have been audited by Quarkslab") and no web client; Lokinet is "a powerful onion router that is fast enough to handle real-time voice communications" and is presented as a planned component, not current transport — [getsession.org/faq](https://getsession.org/faq)
- Lokinet is "the reference implementation of LLARP (low latency anonymous routing protocol), a layer 3 onion routing protocol" (i.e. a TUN-level VPN-style client) — [oxen-io/lokinet](https://github.com/oxen-io/lokinet); GitHub searches for a Session/Oxen web client returned only website repositories (session-foundation/session-website, oxen-io/websites) — [session-foundation/session-website](https://github.com/session-foundation/session-website)

**Skywire**
- Skywire's 2026-08-29 RFC proposes that a wasm visor in a browser reach .onion/.i2p only through native gateway visors running real Tor/I2P clients, and rejects the pure-Go `opd-ai/go-tor` as a foundation because its README says it "should NOT be considered safe or production-ready" — [skycoin/skywire#4317](https://github.com/skycoin/skywire/issues/4317)

### Inferences
- Taxonomy of what changed per project: (a) *protocol edge added, node ported*: Nym (gateway WebSocket; full Sphinx client in wasm), Tailscale/NetBird (DERP/relay WebSocket; full WireGuard + userspace IP stack in wasm), Veilid (inbound relay + WS); (b) *protocol forked for browsers*: WebTorrent (WebRTC-only swarm with hybrid bridges); (c) *node not ported, RPC relayed*: Hyperswarm (DHT relayed over WebSocket, browser holds no DHT state); (d) *native-only*: Yggdrasil, Lokinet/Session, I2P.
- For an I2P PWA, pattern (a) is the analogue of Option Rust/wasm32 or C++/Emscripten with a WS/WebTransport edge on native routers (or a dedicated bridge); pattern (c) is the project's existing "headless agent + WebSocket" plan (docs/plans/2026-09-30-web-client.md) and is what Hyperswarm chose when porting was too costly.
- Nym's design choices — Web Worker for the CPU-bound client, single shared tunnel, one-shot instance requiring page reload — are concrete answers to running crypto-heavy overlay code in a tab; they also show the practical ceiling (no concurrent tunnels, HTTPS-only, no reuse after disconnect).

### Gaps
- Nym publishes no latency/throughput/bundle-size figures for the browser client in the pages fetched.
- Hypercore's own numbers (relay throughput, browser limits) were not found; the dht-relay README has no performance section.
- Tailscale's current wasm size (2026) is unknown; only WebVM's 2022 figure (16 MB) was found.

## Key question 6 — Quantitative limits reported (CPU, memory, throughput, battery, connection survival in background tabs)

### Takeaway
Hard numbers are scarce: the only end-to-end anonymity-client measurements are tor-js's bootstrap (~3 min in wasm vs ~15 s native at prototype stage; ~10–30 s later with a ~3 MB snapshot) and ~800–1000 ms per request in steady state (Node), plus bundle sizes (tor-js 1.9 MB wasm, tor-wasm 538 KB gz, Tailscale 16 MB); nobody reports battery figures, and background behaviour is governed by browser platform rules (Chrome: 1 wake/min after 5 min hidden unless WebRTC/audio; freeze/discard under pressure; iOS: whole-process suspension with WebSocket drops) rather than by anything the projects measured.

### Cited Findings

**Bootstrap, latency, throughput**
- tor-js prototype: bootstrap "~3 minutes" in wasm vs "~15 seconds" native; ~10,000 microdescriptors; `crypto.subtle.digest()` avoided "~3 seconds of overhead for 10k entries" — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- tor-js with fast-bootstrap bundle ("brotli-compressed ~3MB"): first `tor.ready()` "~10-30 seconds"; steady-state "~800–1000ms for a simple balance check"; `eth_getCode` (~26 KB) 1200–1500 ms; "Not acceptable: high-frequency event polling, block watching" (Node.js, direct TCP) — [andyguzmaneth/tor-ethers](https://github.com/andyguzmaneth/tor-ethers)
- libp2p: WebSocket needs 6 RTTs to a usable connection vs 3 for WebTransport — [libp2p docs webtransport.md](https://github.com/libp2p/docs/blob/master/content/concepts/transports/webtransport.md)
- Veilid test suite: "wasm tests went from 731 seconds to 112 seconds" (0.4.2) — [Veilid CHANGELOG](https://gitlab.com/veilid/veilid/-/blob/main/CHANGELOG.md)

**Binary size and memory**
- tor-js: 33 kB JS + wasm from CDN, 2.6 MB gzip with embedded wasm, or 32 kB + 1.9 MB `tor_js_bg.wasm` — [ethereum/tor-js README](https://github.com/ethereum/tor-js)
- tor-js wasm *compile* needed "10GB+" RAM until the `psl` crate was replaced (then "~2.6GB") — [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- tor-wasm: "538KB gzipped"; offline single-file bundle "~3-4MB HTML" — [cmyocyte/tor-wasm](https://github.com/cmyocyte/tor-wasm)
- Tailscale wasm: "16MB" (2022), wasm-opt saved ~1 MB, loaded lazily — [WebVM post](https://labs.leaningtech.com/blog/webvm-virtual-machine-with-networking-via-tailscale); Tailscale itself: "still more work to be done here" on size — [tailscale.com/blog/ssh-console](https://tailscale.com/blog/ssh-console)
- Veilid: wasm blob −25 % (0.5.2, tracing removed) and −47 % (0.5.6); `wee_alloc` removed "due to memory leak issues" (0.4.4); BLAKE3 SIMD +14 KB — [Veilid CHANGELOG](https://gitlab.com/veilid/veilid/-/blob/main/CHANGELOG.md)
- Nym: the browser client is "CPU-bound and must not block the UI thread" (hence a Web Worker); no figures — [nym.com mix-architecture](https://nym.com/docs/developers/mix-architecture)

**Toolchain bounds relevant to the four options**
- Emscripten: "by default Emscripten attempts to emulate such connections to take place over the WebSocket protocol", "you will need to use something like WebSockify on the server side", "This emulation is not very complete at the moment"; a full-POSIX proxy mode (`-sPROXY_POSIX_SOCKETS`) forwards each call to a server-side proxy and is "mostly useful for testing"; "Currently Emscripten does not provide a C/C++ API for interacting with WebRTC" nor for WebTransport datagrams; no direct UDP — [emscripten networking](https://emscripten.org/docs/porting/networking.html)
- Emscripten pthreads need SharedArrayBuffer, which browsers gate "behind Cross Origin Opener Policy (COOP) and Cross Origin Embedder Policy (COEP) headers"; "Pthreads code will not work in deployed environment unless these headers are correctly set"; "The Web API for atomics does not allow blocking on the main thread" (busy-wait fallback, `-sPROXY_TO_PTHREAD` moves `main()` off the UI thread) — [emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html)
- CheerpJ: `java.net.URL`/`HttpURLConnection` go through the browser Fetch API (same-origin or CORS); "Browsers do not give web pages raw TCP or UDP sockets", so generic TCP/UDP is provided "through Tailscale, a VPN carried over WebSockets", requiring Tailscale on the target the Java app must reach; server sockets are not mentioned — [cheerpj.com Networking guide](https://cheerpj.com/docs/guides/Networking); licensing: "free for personal, educational and hobby use, and for technical evaluation", non-commercial open-source projects qualify only if they load CheerpJ from the CheerpJ CDN and add a "Built with CheerpJ" credit, "Business use needs a licence", self-hosting the runtime is a licensed case — [cheerpj.com licensing](https://cheerpj.com/docs/licensing)

**Background tabs (platform rules, not project measurements)**
- Chrome 88+ intensive throttling: when "The page has been _hidden_ for more than 5 minutes", "The _chain count_ is 5 or greater", "The page has been silent for at least 30 seconds" and "WebRTC is not in use", timers are checked "once per **minute**"; pages with an `RTCPeerConnection` with an open `RTCDataChannel` or live `MediaStreamTrack` get regular (once-per-second) throttling instead; WebSocket exemption is not stated (only a test flag `AllowAggressiveThrottlingWithWebSocket`); Web Workers are not mentioned — [developer.chrome.com timer-throttling-in-chrome-88](https://developer.chrome.com/blog/timer-throttling-in-chrome-88)
- Page Lifecycle: when frozen "the browser suspends execution of freezable tasks in the page's task queues until the page is unfrozen"; when discarded "No tasks, event callbacks, or JavaScript of any kind can run"; discards "typically occur under resource constraints"; pages playing audio, using WebRTC, updating title/favicon, or sending push notifications "won't be discarded unless under extreme resource constraints"; Chrome's advice on freeze is to "Stop any network polling or close any open Web Socket connections" and "Close active WebRTC connections" — [developer.chrome.com page-lifecycle-api](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)
- Veilid's unreleased code responds to exactly these events: "In a browser, `app-lifecycle` follows a page's visibility, back/forward cache and freeze events" and saves the routing table — [Veilid CHANGELOG](https://gitlab.com/veilid/veilid/-/blob/main/CHANGELOG.md)
- iOS Safari: developer reports that WebSockets were closed when Safari went to the background (iOS 15 thread) — [Apple Developer Forums thread 696310](https://developer.apple.com/forums/thread/696310); PWAs freezing after backgrounding/relaunch (WebKit bug 211018) — [bugs.webkit.org 211018](https://bugs.webkit.org/show_bug.cgi?id=211018); a Worker-side WebSocket send could freeze the whole Worker on server disconnect (WebKit bug 287784, fixed 2025) — [bugs.webkit.org 287784](https://bugs.webkit.org/show_bug.cgi?id=287784). These are anecdotal/bug-tracker sources, not Apple documentation.
- Session lifetime assumptions in shipped browser nodes: Tailscale SSH Console uses ephemeral nodes and reauthenticates per session — [tailscale.com/blog/ssh-console](https://tailscale.com/blog/ssh-console); WebVM nodes "disappear after inactivity" and reload requires re-login — [WebVM post](https://labs.leaningtech.com/blog/webvm-virtual-machine-with-networking-via-tailscale); NetBird removes temporary peers "after 10 minutes of inactivity" — [docs.netbird.io](https://docs.netbird.io/about-netbird/browser-client-architecture); Nym's tunnel is "one-shot per WASM instance" — [nym.com mix-architecture](https://nym.com/docs/developers/mix-architecture)

### Inferences
- The ~12× bootstrap slowdown reported for the first wasm Arti build (3 min vs 15 s), and the directory-size problem (10k microdescriptors) that forced a server-prepared snapshot, will recur for I2P: netDb reseed + RouterInfo verification + tunnel building are the equivalent. I2P's fixed tunnel lifetime (10 minutes per the I2P tunnel specification; that page was not fetched here, and the tunnel-routing overview fetched only says failed tunnels are replaced and that "routers may delete participating tunnels that have received no traffic as of two minutes after creation" — [i2p.net tunnel-routing](https://i2p.net/en/docs/overview/tunnel-routing)) means continuous rebuild work, which sits badly with 1-wake-per-minute throttling in hidden tabs.
- Because no browser can keep a tab's overlay node alive reliably when hidden (Chrome freezes/discards; iOS suspends the process and drops WebSockets), every shipped browser node is designed to be ephemeral and to re-join on focus. An I2P router that must keep tunnels, lease sets and NTCP2 sessions alive would need either a WebRTC data channel kept open (Chrome's throttling exemption) or acceptance of re-bootstrapping on every return to foreground.
- COOP/COEP is a deployment constraint specific to Option C++/Emscripten (i2pd is multi-threaded): the PWA's origin must send those headers, which a plain static host may not allow (**unverified** for GitHub Pages in this session); Rust/wasm32 single-threaded async code (the tor-js path) avoids the requirement.
- CheerpJ's TCP path routes through a WebSocket-carried Tailscale VPN and the runtime is commercially licensed outside the CDN/credit terms; this makes Option Java/CheerpJ both a transport dependency on a third party and a licensing question, with no evidence anyone has run the Java I2P router in it.

### Gaps
- No source reports battery or CPU-utilisation measurements for any browser overlay node; none report wasm heap size at runtime.
- No browser-side (as opposed to Node.js) latency/throughput numbers for tor-js, and none at all for Nym, Veilid, Hyperswarm or NetBird.
- Chrome's exact freeze trigger timing and WebSocket exemption, and Apple's official background policy for PWAs, were not found in primary documentation.
- Whether GitHub Pages can emit COOP/COEP headers was not verified.

## Key question 7 — What the prior art implies for the four candidate approaches

### Takeaway
The only approach with a working precedent is "Rust async core + pluggable socket provider + pure-Rust crypto + IndexedDB state + a bridge/gateway speaking WebSocket/WebRTC" (Arti → tor-js); among the projects surveyed, nobody has pushed a multi-threaded C++ router through Emscripten or a Java router through CheerpJ, and from-scratch browser clients have so far ended as "unsafe/not audited".

### Cited Findings
- Arti's own README-level claim by a third party that it "Depends on tokio, native networking" and cannot be compiled directly was superseded within the same month by the EF port that did compile it with ~6,100 new lines across 10+ crates — [cmyocyte/tor-wasm](https://github.com/cmyocyte/tor-wasm) vs [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- emissary-core already separates the protocol library from the tokio runtime behind a `Runtime` trait with TCP/UDP associated types — [docs.rs emissary_core::runtime::Runtime](https://docs.rs/emissary-core/latest/emissary_core/runtime/trait.Runtime.html)
- i2pd maintainers closed the wasm request citing pthreads and do not plan a port — [PurpleI2P/i2pd#1817](https://github.com/PurpleI2P/i2pd/issues/1817); Emscripten pthreads require cross-origin isolation headers and forbid blocking on the main thread — [emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html); Emscripten sockets are WebSocket-emulated with a WebSockify-style proxy and "not very complete" — [emscripten networking](https://emscripten.org/docs/porting/networking.html)
- No hit for `cheerpj` in i2p/i2p.i2p code or issues; CheerpJ TCP/UDP requires its Tailscale-over-WebSocket integration and business use needs a licence — [cheerpj.com Networking](https://cheerpj.com/docs/guides/Networking), [cheerpj.com licensing](https://cheerpj.com/docs/licensing)
- From-scratch clients: echalote "It has security issues"; tor-wasm "Not Audited"; the EF abandoned Echalot-based tor-js because closing the gaps "would have required essentially reimplementing Tor" — [hazae41/echalote](https://github.com/hazae41/echalote), [cmyocyte/tor-wasm](https://github.com/cmyocyte/tor-wasm), [reads.ethereum.foundation](https://reads.ethereum.foundation/blog/embedding-arti-in-the-browser/)
- Every browser node surveyed has an edge component on the native side: Snowflake bridge, tor-js gateway (KPS/WebRTC, HTTP CONNECT per relay), tor-wasm bridge (WS→TCP, optionally two-hop), Veilid inbound relay + ws bootstrap, Nym entry gateway WebSocket, Hyperswarm dht-relay, Tailscale/NetBird DERP/relay WebSocket, WebTorrent wss trackers + hybrid peers — sources as cited in Key questions 2–5.

### Inferences
- Option Rust/wasm32 (emissary-core) has the strongest precedent and the fewest platform blockers (no pthreads/COOP-COEP, pure-Rust crypto available, rust-libp2p's WebTransport-in-wasm shows the bridge leg is buildable in Rust). Expected effort is on the order of the EF's Arti port (thousands of lines across many crates, months with upstream cooperation) plus the I2P-specific netDb/tunnel-lifetime problems.
- Option C++/Emscripten (i2pd) carries three independent risks none of the surveyed projects took on together: multi-threaded C++ under SharedArrayBuffer/COOP-COEP, Boost.Asio over Emscripten's incomplete WebSocket socket emulation, and an upstream that has declined the port.
- Option Java/CheerpJ has zero prior art, a transport that is itself a third-party VPN over WebSocket, and a licence to clear; it should be treated as unexplored rather than infeasible.
- Option new client-only router matches the history of echalote/tor-wasm: fastest to a demo, slowest to trust. It is only defensible if the I2P client surface it implements is much smaller than a full router (e.g. a client that speaks only to a trusted bridge router using I2CP-like semantics), which is close to the project's existing headless-agent plan rather than to "an I2P router in the browser".
- Whatever the option, the bridge/edge design (what it sees, who runs it, how it is addressed from an HTTPS PWA) is the actual architecture decision; tor-wasm's two-hop blinded bridges and libp2p's certhash transports are the two reusable answers found.

### Gaps
- No source attempted a cost estimate for porting an I2P router specifically; the inference above transfers Tor numbers by analogy only.
- The feasibility of a "WebTransport/WebRTC RouterAddress" in I2P's NTCP2/SSU2 specs (so native routers could be dialed directly from browsers) was out of scope and not researched.
