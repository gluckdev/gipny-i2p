# dht — `gipny-dht`: сеть релеев, где узлы хранят запечатанную почту друг для друга

Протокол, криптография и хранилище. Клиентская интеграция находится в
`libcore/src/dht_client.rs`, узел отдельного релея — в `core/relay/src/dht.rs`.
Seeds и политика хранения зависят от роли/конфигурации. История решения —
[relay-independence.md](../docs/relay-independence.md), текущие результаты и
границы — [журнал интеграции](../docs/today-2026-10-28.md).

## Что здесь

| Файл | За что отвечает | Главное |
|---|---|---|
| `src/crypto.rs` | Ключи и запечатывание | `pair_secret` (X25519 статических ключей пары), `card_secret`, `mail_key`/`intro_key`/`addr_key`/`bundle_key`, `day_of`, `seal`/`open` (XChaCha20-Poly1305 + паддинг до степени двойки), `seal_to`/`open_from` (эфемерный X25519 к получателю), `MAX_PLAINTEXT` |
| `src/items.rs` | Что кладётся в сеть | `mail`/`open_mail`, `intro`/`open_intro`, `address_record`/`open_address_record`, `bundle_record`/`open_bundle_record`, `mail_keys_to_poll`, `intro_keys_to_poll`, `delete_hash`, `PreparedItem`, TTL `MAIL_TTL_MS`/`ADDRESS_TTL_MS`/`BUNDLE_TTL_MS` |
| `src/proto.rs` | Сообщения между узлами | `NodeInfo` (+ `node_id`), `StoredItem`, `DhtRequest`, `DhtEnvelope`, `DhtResponse`, `pow_ok`/`solve_pow`, `PROTOCOL_VERSION`, `MAX_VALUE_BYTES` |
| `src/store.rs` | Хранилище узла | трейт `Storage`, `MemStorage`, `StoreLimits`, `admit` |
| `src/node.rs` | Узел | трейты `Transport`/`Connection`, `DhtNode` (`handle` — ответ другим; `bootstrap`, `lookup`, `put`, `get`, `delete`, `republish`, `maintain`, `add_candidates`, `known_peers`), `NodeConfig` (`dial_timeout` 60 с на подключение, `call_timeout` 120 с на обмен). Узел, не ответивший в последний раз, не участвует в поиске, пока `maintain` не найдёт его живым: иначе молчащий адресат стоил бы таймаута на каждое письмо |
| `tests/sim.rs` | Сеть в памяти | переживание смены узлов, поиск адреса после перезапуска, отказы узлов |

## Куда вносить правки

| Задача | Где |
|---|---|
| Как вычисляются ключи хранения | `crypto.rs` (`*_key`) |
| Формат письма или записи | `items.rs` |
| Новый запрос между узлами | `proto.rs` (`DhtRequest`/`DhtResponse`, в конец) + `node.rs::handle` |
| Сложность proof-of-work, k, α, таймауты | `node.rs`: `NodeConfig` |
| Квоты и сроки хранения на узле | `store.rs`: `StoreLimits` |
| Поиск узлов, репликация | `node.rs`: `lookup`, `put`, `republish` |
| Хранилище на диске (SQLite приложения или агента) | реализовать `Storage` в интегрирующем крейте, не здесь |
| Транспорт по i2p | реализовать `Transport`/`Connection` в интегрирующем крейте |

## Инварианты и грабли

- **Без `workspace = true` и без rusqlite.** От крейта по пути будет зависеть `core/relay` со своим workspace и своим SQLite.
- **Id узла выводится из адреса релея** и не должен связываться с личностью пользователя.
- **Хранящий узел видит только случайные байты под случайным ключом:**
  - любое новое содержимое запечатывается через `seal`;
  - новый вид записи получает свою метку (`label`);
  - первое письмо запечатывается только через `seal_to`, потому что называет отправителя.
- **Подпись записи лежит внутри шифротекста,** узел её не проверяет. Читатель берёт новейшую валидную запись.
- **Удалить может только тот, кто вскрыл письмо** (токен внутри). Хранить сам хэш токена как токен нельзя: тест `only_the_token_deletes`.
- **`solve_pow` блокирующий,** запускать через `spawn_blocking` (так делает `store_at`).
- **Сообщения ходят внутри протокола релея как непрозрачные байты** (`node::encode_envelope` и соседние функции).

## Обнаружение узлов и обслуживание после churn

Новый входящий `from` остаётся unconfirmed: наличие соединения от узла не
доказывает доступность заявленного обратного адреса. Подтверждение требует
ответа Ping с тем же destination. Политика `closest_to_share` продолжает
предпочитать подтверждённые адреса, а не автоматически распространять hearsay.

`maintain()` делает не более `min(2*k, max_peers)` проверок за tick, в группах
до `alpha` одновременно. Локальный порядковый счётчик даёт очередь по давности
последней попытки: новые кандидаты становятся в конец, повторный входящий
`learn(false)` не переносит существующий узел. Бюджет резервируется под mutex
до сетевых await. Проверяются и новые кандидаты, и ранее здоровые соседи:
иначе новый держатель копии мог никогда не подтверждаться, а умершие соседи
без исходящих запросов оставаться в рекламируемой ближайшей группе.

`Get.closer` теперь используется в том же опросе. После первоначальных
lookup/seed запросов опрашиваются не более `k` дополнительных уникальных
адресов; повторные адреса не опрашиваются, items дедуплицируются как прежде.
Это лимит destinations, а не числа всех RPC: pagination одного узла может
делать несколько Get. Общие bounds страниц/bytes/items и FindNode work остаются
отдельной задачей; мгновенная сходимость не обещается. Проверка seeds сохраняется.

Обслуживание периодическое. При `k=8`, таблице 2048 адресов и tick 45 минут
один обход без другой активности может занять около четырёх суток. Это не SLA
немедленной доставки или гарантия сохранности при одновременной потере всех
копий. Cadence, таблица, churn, нагрузка и TTL должны измеряться совместно.
Wire format и сохранённый `KnownPeer` от локальной очереди не меняются.

## Как проверить

Сборки и исполняемые регрессии — только GitHub Actions:

```
cargo test --locked -p gipny-dht
```

`tests/sim.rs` проверяет admission нового держателя, Get через seed вне ближайшей
группы и отсутствие starvation при новых/повторных входящих claims. Churn-тест
моделирует явные ограниченные циклы routing maintenance перед republish и
отключением последних первоначальных держателей, на 16 независимых mailbox keys.
Это не sleep/retry-until-green и не предзаполнение всех таблиц всеми адресами.
Без republish передача копий не должна проходить.

На `93295f1` [живой сценарий ухода участников по очереди](https://github.com/gluckdev/gipny-i2p/actions/runs/40772462191/job/123113082570)
прошёл. Но native simulation на этом SHA выявила intermittent discovery failure;
новые routing changes на
[`0fd14f2`](https://github.com/gluckdev/gipny-i2p/actions/runs/40779842463/job/123138418399)
прошли 19 unit и 10 simulation tests, включая три новые regressions и
16 churn placements. Linux security job на этом SHA также прошёл DHT suite.
In-memory tests не заменяют проверку новых изменений по живой I2P.
