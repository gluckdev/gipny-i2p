## Текущая архитектура

SAMv3 удалён при переходе 2026-09-24. В этом дереве `Core` приложения и
`SessionManager` агента/ботов используют `i2p-embed`: Rust wrapper → C ABI
C++ shim → `libi2pd`, **один роутер внутри процесса**. На Android shim и
роутер входят в `libi2pd.so`; JNI не запускает отдельный SAM daemon.
Роутер хранит собственное состояние отдельно от ephemeral outbound destination
и identity переписки. SAM, HTTP/SOCKS proxy и web console отключены;
NTCP2/SSU2, discovery и reseed самого роутера продолжают использовать IP.

[Актуальная схема](assets/architecture.svg) исправлена в первоисточнике;
старые упоминания SAM не скрываются удалением иллюстрации. Планы перехода,
оценки и release notes с `GIPNY_SAM_PORT`, `--sam`, `yosemite` или
`RouterHandle` остаются историей, что отмечено в [индексе](README.md).
Команды сборки находятся в [русском](../README.md) и
[английском](../README.en.md) README, платформенные шаги — в
[workflow guide](../.github/workflows/README.md).

Клиент принимает свою почту из встроенного релея через in-process pipe;
другие участники подключаются к этому релею через I2P. При его недоступности
сеть релеев ищет адрес и хранит зашифрованную почту с TTL и квотами.
Transport ACK релею отличается от E2E ACK сохранённого сообщения.
Bootstrap зависит от известных узлов и seeds конкретной сборки, а не от
самого наличия workflow тестового релея.

## Границы надёжности и доверия

- Group outbox принят только после commit полной транзакции. Ошибки до него
  не оставляют принятого сообщения или частичного fan-out. Guard очищает свои
  staged файлы при обычной ошибке; kill до commit может оставить encrypted
  crash-orphans без ссылок. Автоматический runtime GC здесь не добавлен.
- Групповые повторы допускают сетевые дубликаты (`at-least-once`). По истечении
  семи дней удаляются все оставшиеся ожидания сообщения, без ложного
  `delivered`. Исторически потерянные pending не восстанавливаются.
- SQLite `WAL`/`synchronous=NORMAL` и ratchet/incoming transaction architecture
  не переделаны. Новая атомарность не расширяет гарантии при потере питания.
- SHA256 из того же Release подтверждает целостность относительно manifest;
  это не независимая подпись издателя. HTTPS по-прежнему идёт через I2P
  outproxy, без прямого fallback. Установка зависит от платформы и разрешений.
- Успешный Android dispatch означает передачу запроса ОС, а не завершённую
  установку. Копия APK сохраняется после возврата intent для дальнейшего чтения
  installer; ошибка staging удаляет только собственный временный файл и
  сохраняет исходную загрузку.
- Release ограничивает журналы предупреждениями и ошибками без `debug.log`,
  `debug.prev.log` или подробного файла i2pd. Старые env/settings/UI не должны
  включать подробную диагностику в release. Публичные карточки и рабочий
  stderr CLI остаются частью интерфейса команд, не секретным debug journal.
- Удаление DM подтверждает сотрудничающее приложение второй стороны.
  Оно не отзывает скриншоты, старые backups или уже экспортированные файлы.
  Для старых incoming records без origin операция явно отказывается от
  недоказуемого удаления; локальные DB IDs не передаются как чужие origins.
  Номера неизменяемые внутри локального диалога, порядок двух offline
  отправок может различаться на устройствах.

## Сайт и дальнейший браузерный клиент

Pages — статика и сайт проекта. Он не создаёт профиль, не принимает сообщения
и ключи. Deployment требует отдельного включения Settings → Pages владельцем;
публикация в этой работе ещё не выполнена.

Существующий `gipny-web` — серверный gateway, где vault и crypto находятся на
сервере. Цель будущего браузерного клиента — crypto/storage на устройстве.
Browser transport, backend, порог и независимые временные доли offline mail
пока исследуются. Landing page не реализует распределённое хранилище или
статический web messenger.

Перед выпуском нужны общие проверки конечной ветки, проверка всех release
assets и отдельное подтверждение сценариев на поддерживаемых устройствах.
