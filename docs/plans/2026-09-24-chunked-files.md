# Большие файлы частями

2026-09-24, по просьбе владельца («больших файлов частями»).

## Context

Сейчас вложение едет целиком внутри одного письма: `WireAttachment { name, data }`
в `WirePayload`, лимит в приложении 12 МБ (`core/src/lib.rs` `MAX_ATTACHMENT_BYTES`).
Этого пути хватает только для маленьких файлов, и он уже сломан посередине:

- **Больше ~4 МБ письмо, по всей видимости, не доходит.** `pad_payload` поднимает
  его до корзины 16 МБ, к ней добавляются заголовок ratchet, AEAD и bincode, и
  кадр выходит за `MAX_FRAME` = 16 МБ (`relay.rs`, `core/relay/src/proto.rs`) —
  релей рвёт соединение («frame too large»). Не проверено живьём, но следует из
  чисел.
- Сеть релеев берёт не больше 4 МБ (`dht/src/crypto.rs` `MAX_PLAINTEXT`):
  `put_mail` отказывает, и письмо висит в очереди вечно.
- Payload больше `MAX_PAYLOAD_BYTES` (14 МБ) молча помечается «отправлено» и
  больше не повторяется.
- Встроенный релей держит не больше 24 МБ на получателя (`MemStoreLimits`) и
  вытесняет старое, чтобы влезло новое: большой файл выталкивает чужие письма.
- Отправитель и получатель держат файл целиком в памяти; `build_payload_from_db`
  расшифровывает все вложения заново на каждом повторе.

Это касается и уже выпущенного 0.4.13: вложение от ~4 до 12 МБ помечается
отправленным, рвёт соединение с релеем и повторяется раз в 5 мин неделю.

## Решение

Файл больше `INLINE_MAX` (128 КБ) идёт частями, каждая — отдельное письмо в той
же сессии ratchet и тем же маршрутом (релей собеседника или сеть релеев). Мелкие
вложения остаются как есть.

**На проводе** (новые поля в конце `WirePayload`, снимок `WireV9`, рецепт — в
`libcore/README.md`):

- в письме с текстом — `files: Vec<WireFileOffer>`:
  `{ file_id: [u8; 16], name, size: u64, sha256: [u8; 32], chunk_size: u32 }`;
- часть — отдельное письмо без текста, `file_chunk: Some(WireFileChunk { file_id, index: u32, data })`,
  `origin_msg_id = 0` (в чате её не видно);
- подтверждение — сводное и выборочное: `file_ack: Some(WireFileAck { file_id,
  received_up_to: u32, missing: Vec<u32> })`, одно на несколько частей (и сразу,
  если обнаружилась дыра). Отдельным полем, как `ack_for` для писем: части — не
  строки в `messages`.

`CHUNK_SIZE` = 192 КБ открытого текста: с заголовком и паддингом ложится в
корзину 256 КБ и проходит и через релей, и через сеть релеев.

**Отправитель.** Файл один раз шифруется на диске частями
(`AttachmentCipher::encrypt_chunk(index, …)`, уже умеет индекс в nonce) и
больше в память целиком не читается. Таблица `file_out(file_id, contact_id,
index, sent, delivered, attempts, last_attempt_at)`. Цикл отправки держит у
каждого получателя не больше `WINDOW` (16 частей, ~3 МБ) неподтверждённых, **считая
повторы**: столько лежит на релее, пока получатель не заберёт, — в пределах лимитов
релея, и чужие письма не вытесняются. Всё в базе, поэтому после перезапуска
передача продолжается с места.

**Повторы — не по общему таймеру.** «Не подтверждена» значит либо «потерялась», либо
«получатель не в сети», и отличить их отправитель не может. Общий бэкофф писем
(5 с → 5 мин, 7 дней) на частях дал бы гигабайт дублей на релее за сутки офлайна.
Поэтому:
- быстрый повтор — только частей из `missing`: это доказывает, что получатель жив,
  а часть пропала;
- по таймеру — только если получатель был слышен после отправки части, и не чаще
  раза в 30 мин;
- получатель, который не подтверждает части вовсе (старый клиент), — после
  `FILE_GIVE_UP` (сутки без единого `file_ack` при живом получателе) файл
  помечается недоставленным, пользователю это показывается.

**Маршрут.** Части — только через релей получателя (`Route::Relay`). Сеть релеев
держит не больше 64 записей / 16 МБ на ключ (`dht/src/store.rs`): письмо с
предложением файла может уйти туда, как любое письмо, а части ждут в `file_out`,
пока релей получателя не станет доступен.

**Старые клиенты** (0.4.11–0.4.13): часть для них — письмо без текста; bincode
по умолчанию терпит хвост незнакомых полей, и `persist_incoming` отбрасывает
пустое письмо молча — ни пустых пузырей, ни resync. Предложение файла они покажут
текстом без вложения.

**Получатель.** `file_in(file_id, contact_id, message_id, name, size, sha256,
chunk_size, received)`; части пишутся на диск зашифрованными, каждая на своё место
(смещение `index × (chunk_size + 16)`). Пришедшая часть подтверждается сразу,
дубль — тоже (подтверждение могло потеряться). Часть файла, о котором
ещё не пришло предложение (повторы перемешивают порядок), не выбрасывается, а
кладётся на время и подбирается, когда предложение придёт. Недособранный файл
удаляется через 7 дней (срок жизни письма на релее). Когда пришли все, sha256 сверяется
по расшифрованному потоку, и файл становится обычным вложением сообщения
(`attachments` с новой колонкой `chunk_size`; `NULL` — старый формат целиком).

**Интерфейс.** Событие `FileProgress { message_id, file_id, done, total,
direction }`; в чате у вложения полоса и «n из m МБ»; отмена отправки
(помечает части отменёнными, получателю — `file_cancel`). Сохранение большого
файла — потоком, без base64 через IPC.

**Группы.** Предложение файла уходит в группу как обычно; части — каждому
участнику своей сессией, с тем же окном. Повтор части — до подтверждения
(исправляет и то, что групповые письма сейчас повторяются только при неудачной
передаче на релей).

**Агент и bot-sdk** получают файлы тем же путём: `SessionManager` собирает
файл и отдаёт событие, когда он целиком; `/agent get` снимает лимит 8 МБ.

**Лимит размера:** 2 ГБ на файл (u32 частей по 192 КБ хватает с запасом; реальное
ограничение — диск и терпение i2p).

## Состояние (ветка `feat/chunked-files`)

| Шаг | Что | Где |
|---|---|---|
| 1. Протокол и хранение | готово | `WirePayload` + `WireV9`, `libcore/src/files.rs`, таблицы в `db.rs`, бэкап v3 (`chunk_size`), `MAX_PAYLOAD_BYTES` = 4 МБ с `MessageFailed` |
| 2. `SessionManager` | готово | `session.rs`: отправка с окном, сводные ack с дырами, повторы, сборка вне порядка, ранние части, GC; e2e `E2E_BIG_FILE` в `i2p-embed.yml` |
| 3. `Core` и Tauri | готово | `core.rs`, `files_progress`/`cancel_files`, потоковое сохранение, лимит 512 МБ |
| 4. UI | готово | полоса прогресса и «Отменить» в `chat.ts`, события в `state.ts` |
| 5. Агент, bot-sdk | готово | команда ждёт свои файлы; `/agent get` до 512 МБ; бот получает сообщение, когда файл целиком |
| Параллельные потоки | готово, замер идёт | `FILE_LANES` = 4 соединения с релеем получателя, части по кругу; окно 32 |
| Приём несколькими соединениями | готово | получатель со сторонним релеем держит до 3 лишних соединений с ним, пока идут части, и закрывает их через минуту тишины (`spawn_collect_lanes`); релей раздаёт новую почту по кругу, а неподтверждённое закрытым соединением отдаёт остальным; e2e `E2E_BIG_FILE` в `e2e-i2pd.yml` (релеи-серверы) |
| Окно на каждого собеседника | готово, замер идёт | `files::Flow`: окно с 4 частей растёт на часть за каждый вовремя пришедший ack и делится пополам при потере, не чаще раза за круг; время пути меряется по частям, ушедшим один раз; часть потеряна, когда старше `srtt + 4·rttvar` (10 с…2 мин); дыра в ack до таймаута — часть в пути, не потеря. Потери одного отправленного окна режут окно один раз; сокращение из-за части, которая лишь опоздала (ack на повтор быстрее половины круга), отменяется; после потери таймаут ×2 до первой дошедшей части; замер больше 4× среднего (часть ждала, пока получателя не было) не учитывается, пока их не больше окна. Тормоза по задержке (как LEDBAT/Vegas) нет: круг в i2p скачет от 6 до 40 с без всякой очереди, и каждая его версия держала окно на 2 (ноутбук, 2026-09-25: 8 КиБ/с). Очередь ограничена иначе: не больше `WINDOW` = 16 частей, по 4 на поток. Ack на каждую часть. Полос — по окну (`lanes_for`) |
| Отправка с диска | готово | большой файл запечатывается частями прямо из файла (`files::seal_from`), до 2 ГБ; фото и PDF при включённой очистке читаются в память, чтобы очиститься |

Замеры (e2e «релеи внутри ботов», GitHub-раннер, живая i2p):

- один поток, окно 16: 5 МБ за 24,4 с — **210 КиБ/с** (run 36046190496);
- четыре потока, окно 32: 20 МБ — прогон 36047667974 испорчен багом релеев
  (ниже); прогон 36052276213 встал: ~750 отправок на 107 частей (ниже);
- окно на собеседника, 8 частей на полосу: 20 МБ за 206,5 с — **99 КиБ/с**,
  ровно ~130 КиБ/с после разгона, отправлено ≈ пришло, одна лишняя полоса;
  10 МБ с перезапуском получателя — 458 с (run 36056012101). Дальше — 4 части
  на полосу, замер в следующем прогоне.

Почему окно стало адаптивным (run 36052276213, 4 полосы и окно 32 без
него): на файл в 107 частей ушло ~750, дошло ~400, из них разных 56. По
нескольким полосам части обгоняют друг друга, получатель называл дырой часть в
пути, и она тут же уходила снова; а 6 МБ в полёте — полминуты очереди в
потоках i2p, за ними тонули пинги, соединения рвались «без активности 80 с», и
релей слал всё неподтверждённое заново.

Найдено на ноутбуке (2026-09-25, e2e с перезапуском получателя, лог с
номерами частей): после перезапуска (1) части, пролежавшие на релее, давали
минутные замеры круга — таймаут упирался в 120 с, а тормоз по задержке
сравнивал с кругом из начала передачи и держал окно на 2 до конца файла;
теперь самый быстрый круг — из последних 32 замеров, а замер больше 4×
среднего не учитывается, пока их не больше окна; (2) из четырёх соединений
старого экземпляра до релея дошло закрытие одного, три остались в раздаче по
кругу и уносили долю новой почты — релеи теперь закрывают клиента, молчащего
90 с (пинг каждые 20 с); (3) лишние соединения к своему релею закрывались
после минуты без частей и открывались снова — теперь держатся 5 минут.

Дальше на ноутбуке (перезапуск получателя, 10 МБ): получатель при запуске
шлёт каждому отправителю ack с пометкой «вернулся» — что было в пути и не
дошло, уходит сразу, а не по таймауту (было 106 с до первого повтора); ack
возвращает время отправки своей части — круг меряется и у повторов, и
таймаут догоняет замедлившийся путь; релей отдаёт новую почту соединению с
наименьшим числом выданного и неподтверждённого, а не по кругу — из 73
частей, принятых релеем после перезапуска, получатель видел 36. Итог: 575–
1256 с → 224 с, повторов 30 из 64 → 4 из 41.

Найдено по пути: лишние соединения получателя к своему релею запускались
задачами, которых `shutdown` не останавливал. После перезапуска получателя
(e2e run 36056788336) старый экземпляр ещё полторы минуты читал по ним части
своей копией ratchet и писал её в ту же базу; копии разошлись, и каждая
следующая часть приходила «no session matched». Теперь все такие задачи
учитываются (`track`) и останавливаются с остальными.

Найдено по пути: релей читал кадр клиента внутри `select!` вместе с ожиданием
почты для него. Письмо, пришедшее посреди чтения кадра, обрывало чтение, и
следующее брало середину кадра за длину — «frame too large», разрыв, повтор
всего неподтверждённого. Теперь чтение кадра переживает `select!`
(`read_frame` в обоих релеях, с тестом).

## Шаги

1. Протокол и хранение: поля `WirePayload`, `WireV9` (и `libcore/README.md`, где
   ещё «WireV0..WireV7»), таблицы `file_out`/`file_in`, колонка
   `attachments.chunk_size`, запись/чтение частями; превышение `MAX_PAYLOAD_BYTES`
   — ошибка, а не молчаливое «отправлено»; юнит-тесты (нарезка, сборка вне
   порядка, часть раньше предложения, дубли, sha256, совместимость формата).
2. `SessionManager`: отправка с окном, приём, сборка, события. e2e: `E2E_BIG_FILE`, сначала 5 МБ (по живой i2p 30–100 КБ/с — минуты), по
   скорости из лога поднять; с перезапуском получателя посередине.
3. `Core` и Tauri: то же, события прогресса, потоковое сохранение, отмена.
4. UI: полоса прогресса, «n из m», отмена; снять лимит 12 МБ.
5. Группы, агент (`/agent get`), bot-sdk; документация.

## Проверка

- `cargo test` (юниты шагов 1–2) локально.
- `i2p-embed.yml` e2e с большим файлом; `e2e-i2pd.yml` — оба сценария с релеями.
- На телефоне: файл 100 МБ с десктопа, выключить Wi-Fi посередине, включить —
  передача продолжается.
