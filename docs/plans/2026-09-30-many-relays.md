# Несколько релеев на контакт: дублирование вместо одного

## Context

Просьба владельца (2026-09-30): «пусть релеи будут у всех и пусть дублируется
много раз, но пусть всё». Это ровно то, что делает SimpleX, и это же то, чего у
нас нет.

Сейчас письмо идёт на **один** релей получателя:

- `core/src/core.rs:2224` `route_for` возвращает `Option<Route>`, где
  `Route::Relay(tx)` — одно соединение на одного контакта. Если релей не
  отвечает, `Route::Dht` — медленный путь через сеть с PoW. Это **фолбэк**,
  а не параллель: пока фолбэк не сработал, дублей нет.
- `libcore/src/session.rs:177` `WirePayload::relay_address: Option<String>` —
  один адрес.
- `libcore/src/db.rs:94` `Contact::relay_address: Option<String>` — один адрес.
- `dht/src/items.rs:169` `open_address_record` возвращает **одну** лучшую
  запись через `best_record` (`.max_by_key(|r| r.seq)`, :157). Даже если в сети
  лежит пять адресов, читается один — самый свежий.

Итог: адрес релея контакта уезжает вместе с этим релеем, и доставка
останавливается, пока не сработает медленный DHT-фолбэк. Сеть релеев у нас
своя, размером в десятки узлов, и держать почту на одном из них — это одна точка
отказа на каждого контакта.

### Что берём у SimpleX

- **Дублирование на N серверов, выбранных получателем.** «the message is passed
  multiple times in parallel, through one node each time, using servers chosen by
  the recipient».
- **Не одним и тем же шифротекстом.** Их прямая оговорка: дублировать «to avoid
  having the same ciphertext in different queues (that would only be visible to
  the attacker if TLS is compromised)». То есть каждый экземпляр письма
  шифруется отдельно, иначе наблюдатель складывает два одинаковых блоба и
  видит, что это одно и то же сообщение, а значит связывает отправителя с
  получателем через два релея.
- **Сервер не хранит после доставки.** У нас это уже так: `MemStore` в памяти
  (`libcore/src/relay_server.rs:255`).
- **Сервер не знает, кто пользователь.** У нас тоже: `deposit(to: [u8;32], blob)`
  (:314) — только публичный ключ получателя и шифротекст.

### Чего у SimpleX нет и у нас не будет

Их «servers» — это публичные серверы SimpleX, и получатель выбирает их из сети.
У нас релеи живут в **нашей** сети релеев (десятки узлов), и у получателя нет
списка «мои N релеев» — есть только его личный встроенный релей. Поэтому N
релеев на контакт появляется так: получатель публикует в DHT **не один**
адрес, а список своих адресов, а отправитель раскладывает копии по ним всем.

Это дешевле, чем кажется: адреса уже публикуются, `publish_addresses`
(`libcore/src/dht_client.rs:174`) ходит по контактам и пишет по одной записи
каждому. Нужно научиться писать несколько и читать все.

---

## 1. Список вместо одного адреса (`dht/src/items.rs`)

`best_record` (:144) выбирает максимум по `seq` — это правильно для «самый
свежий адрес», и для списка это не годится. Новая функция рядом:

```rust
/// Every address this contact currently publishes, newest sequence first.
///
/// The same record the owner signs for each of their relays, so the owner is
/// the one deciding how many copies exist, and a relay that lies is discarded
/// by the signature check below exactly like before.
pub fn open_address_records(
    pair: &[u8; 32], owner_sign_pk: &[u8; 32], values: &[Vec<u8>], now_ms: u64,
) -> Vec<(String, u64)>
```

Она та же фильтрация из `best_record` (`:150-156` — `open`, `deserialize`,
`kind`, `owner`, `expires_at_ms`, подпись), но без `max_by_key`: собирает все
и сортирует по `seq` по убыванию. `open_address_record` (:169) остаётся и
становится `open_address_records(..).into_iter().next()` — обратная
совместимость, и она ещё нужна как «куда идти по умолчанию».

**Важно:** адреса дедуплицируются. Один и тот же адрес может прийти из двух
записей; в набор попадает один. Список ограничивается сверху (см. п. 4).

## 2. Несколько адресов в записи контакта

`WirePayload::relay_address: Option<String>` (`session.rs:177`) — старое поле,
оно остаётся: получатель, который ещё на старой версии, поймёт только его.
Рядом, в конец структуры (новое поле всегда в конец — `decode_payload` пробует
от нового к старому, `session.rs:726`):

```rust
#[serde(default)]
pub relay_addresses: Option<Vec<String>>,
```

`Contact` получает второе поле `relay_addresses: Vec<String>` в БД
(`libcore/src/db.rs:94`, `ensure_column` в стиле :651). Старый
`relay_address` — это первый элемент списка, и он остаётся заполненным, чтобы
всё, что читает одно поле (`route_for` для старых контактов, `warm_relay_of`),
продолжило работать.

## 3. Публикация всех адресов (`libcore/src/dht_client.rs`)

`publish_addresses` (:174) сейчас пишет одну запись. Теперь — по одной на
каждый наш адрес. Адреса приходят из `flush_relay_announcements`
(`core/src/core.rs:903`), который публикует адреса, узнанные от контактов: у нас
их может быть несколько (встроенный + внешний, а дальше — сколько наберётся).

Стоимость: каждая копия — отдельный `put` с PoW. Поэтому пишем не больше
`MAX_PUBLISHED_RELAYS` (константа, п. 4) и только те, что отличаются от уже
опубликованных.

## 4. Сколько релеев: константа, а не настройка

`MAX_PUBLISHED_RELAYS = 3` в `dht/src/items.rs` рядом с `ADDRESS_TTL_MS`.
Число выбрано так:

- **сверху** — три копии переживают падение двух релеев, и это уже редкость;
- **снизу** — каждый экземпляр стоит отправителю отдельное соединение и туннель
  в i2p, а туннели платные по времени. При `k=8` в DHT и десятках узлов в сети
  свалить три релея из одного контакта специально — работа, а не случайность;
- **`1` остаётся рабочим** — если у контакта один адрес (встроенный релей, как
  сейчас у всех), всё ведёт себя ровно как до этого. Дублирование включается
  само, когда адресов становится больше одного.

Это не настройка в UI намеренно: число, которое влияет на стоимость доставки и
на приватность, должно быть у нас в коде, а не выбираться человеком, который
не знает, сколько это стоит.

## 5. Раскладка копий (`core/src/core.rs`)

`route_for` (:2224) вместо `Option<Route>` возвращает `Vec<Route>`:

```rust
enum Route { Relay(PeerRelayConn), Dht }
```

Правила:

1. Собрать адреса контакта: `relay_addresses`, а если список пуст — старый
   `relay_address`, а если и он пуст — ничего.
2. Для каждого адреса дозвониться (`relay_for` уже умеет кэшировать соединения
   и поднимать их заранее, `session.rs:1027` `warm_relay_of`).
3. Отправить **на все N параллельно**, не дожидаясь остальных.
4. Считать доставленной, если **хотя бы один** принял. Остальные копии — в
   мусор: получатель удалит у себя лишние (п. 6), а `ack` придёт один раз.
5. `Route::Dht` — только если **ни один** релей не взял письмо, и только если
   мы в сети. Это поведение сохраняется.

**Шифрование каждой копии отдельно.** Письмо шифруется один раз в
`send_payload_via_relay` (:3504) — `build_ad` + `encode_payload` дают шифротекст
для ratchet-сессии с контактом. Для N релеев этот шифротекст одинаковый, и это
именно то, о чём SimpleX предупреждает: два одинаковых блоба в двух очередях
связывают отправителя с получателем.

Поэтому копия N получает свою обёртку: `payload.relay_address` = адрес этого
релея (это и так делается, :3516), и кладётся в `recipient`-специфичный
конверт с рандомизированным `nonce` в AAD. Сессия Double Ratchet при этом
**одна** — вторая копия не должна двигать ratchet, иначе получатель
расшифрует только одну. Это самое тонкое место работы: ratchet двигается при
отправке первого письма, копии 2..N переиспользуют тот же `header` и тот же
`ciphertext`, но с другим конвертом.

## 6. Приём и уборка дублей (`core/src/core.rs`)

Получатель тянет `pending_above` со всех N релеев. Дубликаты отсеются по
`(origin_msg_id, отправитель)`, что уже есть в `resolve_contact_message`
(:2988) и `resolve_group_message` (:2984) — то есть повторное сообщение с тем
же `origin_msg_id` тихо отбрасывается, и достаточно того, что оно пришло.

После успешного применения письма получатель шлёт `ack` **на каждый** релей, от
которого письмо пришло, а не на один. `ack` сейчас один (`ack_for`,
`session.rs:166`); нужен список `ack_for` — либо расширить до
`ack_for_all: Option<Vec<String>>` (адреса релеев, от которых брать письмо),
либо просто слать ack на все известные релеи контакта. Второе проще и не хуже:
`ack` идёт внутри ratchet-сессии, лишний ack на релей, который не прислал
письмо, релей отбросит — у него нет такого `id`.

## 7. Тесты

`dht/tests/sim.rs` — симуляция сети релеев в памяти, единственное место, где
это проверяется быстро:

- `open_address_records` отдаёт все адреса, а не один, и дедуплицирует;
- подделанная запись (чужая подпись) отбрасывается, как и раньше;
- список ограничен `MAX_PUBLISHED_RELAYS`;
- письмо, разложенное на N релеев, собирается с любого одного из них;
- **переписан** `mail_outlives_every_node_it_was_first_stored_on`: он проверяет
  single-relay модель («письмо живёт, пока жив релей»), и после этого изменения
  смысл меняется на «письмо живёт, пока жив **любой** из N». Старое имя больше
  не соответствует тому, что проверяет, поэтому переименовывается.

`tests/e2e-*` — живой прогон: два клиента, релей между ними, `DHT_RELAYS=2`,
письмо доходит при убитом одном из них.

## 8. Порядок работ

1. `dht/src/items.rs`: `open_address_records` + дедуп + лимит. Тест в `sim.rs`.
2. `libcore/src/session.rs` + `db.rs`: `relay_addresses` в payload и в контакте,
   старое поле живёт.
3. `libcore/src/dht_client.rs`: публикация всех адресов, не больше лимита.
4. `core/src/core.rs`: `route_for` → `Vec<Route>`, раскладка по всем, успех при
   любом одном, DHT только если не взял никто.
5. `core/src/core.rs`: отдельное шифрование каждой копии (самое тонкое место).
6. `core/src/core.rs`: `ack` на все релеи, с которых пришло.
7. Переписать `mail_outlives_every_node_it_was_first_stored_on`.
8. `E2E_RELAYS` в живом прогоне.
