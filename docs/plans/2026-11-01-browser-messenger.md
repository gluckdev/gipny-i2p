# Браузерный мессенджер после WASM router spike

Владелец поручил готовить весь браузерный мессенджер после слияния #143.
Рабочая ветка — `feat/browser-messenger`, база — `318b2d5`.
Все сборки и исполнение тестов выполняются только в GitHub Actions.
Изменённый пользователем `third_party/i2pd-android` сохраняется.

Результат: существующий интерфейс Gipny работает с ядром в Web Worker,
создаёт собственную личность и зашифрованный профиль в OPFS, открывает
клиентскую I2P destination и обменивается сообщениями между двумя браузерами.
X3DH/Double Ratchet и wire format должны переиспользовать исходники Gipny.
Браузерное хранение ключей имеет отдельную реализацию памяти: в браузере
нет mlock/mprotect и гарантий защищённых страниц нативного клиента.

Порядок реализации:

1. Прямой in-process client API emissary и bounded memory streams.
   Используется существующий destination/streaming engine; SAM/I2CP TCP/UDP
   listener не создаётся. Его внутренние подтверждения остаются в памяти
   адаптера, приложение получает типизированные потоки.
2. Перенос общего crypto/wire в WASM, worker lifecycle и шифрованный OPFS
   vault с сохранением состояния ratchet до сетевой отправки/подтверждения.
3. Client pools, совместимый relay protocol и два браузера в живой I2P.
4. Подключение к существующим API/экранам UI, passkey PRF, установка PWA,
   offline shell, блокировка/восстановление и доставка outbox после перезапуска.
5. GitHub CI для криптографии, хранилища, реального обмена и lifecycle;
   отдельная проверка мобильного браузера. Эмуляция не означает проверку
   физического устройства.

Публичное размещение snapshot/forwarder требует доступного сервера и домена.
Сначала готовятся код, артефакты и проверяемый сценарий развёртывания.
Произвольное открытое TCP-проксирование не допускается: сохраняются
проверенные RouterInfo, allowlist, Origin/capability и ресурсные лимиты.
До подтверждённого обмена/восстановления и реального мобильного прогона
продукт не объявляется полностью готовым.
