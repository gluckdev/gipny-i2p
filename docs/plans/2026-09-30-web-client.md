# Веб-обвязка: мессенджер в браузере поверх headless-агента

## Context

Вопрос владельца (2026-09-30): «насколько сложно сделать веб-обвязку, чтобы
мессенджер запускался на JavaScript». Ответ — средняя сложность, и не там, где
кажется. Транспорт из браузера не поднять, но это не проблема портирования, а
граница архитектуры: сеть — C++ i2pd внутри процесса, и после #103 у неё нет
портов вовсе. Портируется почти всё остальное.

Что уже есть и переиспользуется:

- **Почта не требует знать содержимого.** Релей хранит сообщение по публичному
  ключу получателя: `deposit(to: [u8;32], blob)` → `pending_above(pk, cursor)` →
  `ack(pk, id)` (`libcore/src/relay_server.rs:314-372`). Отправитель и релей не
  видят открытого текста — только шифротекст и ключ получателя. Это готовый
  мост: агент может ретранслировать почту, не имея к ней доступа.
- **Крипта — чистый Rust без натива.** `libcore/src/crypto.rs` (518 строк):
  `Identity`, `PreKeyBundle`, `x3dh_initiate`/`x3dh_respond`, Double Ratchet
  (`encrypt`/`decrypt`), покусочное шифрование файлов (`encrypt_chunk`/
  `decrypt_chunk`). Всё это — `ed25519-dalek`, `x25519-dalek`, `chacha20poly1305`,
  у которых есть WASM-сборки. Портируется почти без изменений.
- **UI — тонкая обёртка над Tauri.** `ui/src/api.ts` (778 строк) — это почти
  целиком `invoke('команда', {…})` и два `listen` (`core_event`,
  `boot_status`). Между UI и бэкендом — один файл, который можно заменить.
- **UI без фреймворка.** Ванильный TypeScript, 7777 строк в `ui/src/`, сборка
  `vite` + `tsc --noEmit`. Не нужно портировать React/Vue — меняется только
  транспортный слой.
- **Headless-агент уже есть.** `agent/src/main.rs` — `gipny-agent`: держит
  идентичность, регистрирует мастера, выполняет команды. Это шаблон для
  веб-моста: тот же `TorNode::start` + `Db::open` + `SessionManager::start` +
  цикл `SessionEvent`.
- **Сессии уже переживают смену адреса.** `SessionManager` не привязан к
  конкретному destination — адрес меняется, сессия остаётся. Для браузера это
  важно: соединение с агентом может рваться и восстанавливаться.

Чего нет и что придётся строить:

- **WebSocket-моста.** В проекте нет ни одного WebSocket-клиента или сервера
  (проверено: нет совпадений по `websocket`/`ws://` в Rust и TS). Это новое.
- **WASM-сборки крипты.** Нужен `wasm-pack` или `wasm-bindgen` поверх
  `libcore/src/crypto.rs`, плюс JS-обёртка.
- **Хранилище в браузере.** Сейчас vault — это `rusqlite` с
  `bundled-sqlcipher-vendored-openssl` и argon2 для ключа (`libcore/src/db.rs`,
  2270 строк). В браузере этого нет: нужен IndexedDB с шифрованием на уровне
  приложения.

### Развилка, которую надо решить до кода

**Вариант А — браузер держит ключи.** Крипта и идентичность в WASM, агент —
только труба для шифротекста. Агент не может прочитать переписку даже по
принуждению. Сложность: выше (WASM-крипта, хранилище, восстановление сессий
при обрыве). Безопасность: выше.

**Вариант Б — браузер только видит.** Агент держит ключи и крипту, браузер
получает открытый текст по WSS. Проще, но агент становится единой точкой
компрометации: его захват — это вся переписка. Для админского мессенджера это
неприемлемо.

**Рекомендация: А.** Мессенджер адмский, и вся его ценность в том, что ключи не
покидают устройство. Вариант Б переносит это свойство на агент, то есть теряет
его. План ниже — для А.

---

## 1. Граница: что где живёт

```
Браузер (WASM + UI)          Агинт (Rust, нативный)        Сеть релеев
─────────────────────        ──────────────────────        ─────────────
Identity (sign + dh)         TorNode (i2pd внутри)         deposit/claim
X3DH / Double Ratchet        SessionManager                 по публичному ключу
UI (ui/src/*)                Relay (handle_client)          получателя
IndexedDB (шифр.)           ↕ WSS ↕                         ← шифротекст
```

Агент знает: адреса, маршруты, чей это публичный ключ. Агент не знает: открытый
текст, ключи сессий, содержимое вложений. Это тот же уровень доверия, что у
любого релея в сети сейчас — и это правильно.

## 2. Крипта в WASM

Новый крейт `crypto-wasm` (или `libcore` с флагом `wasm32`), который экспортирует
в JS ровно то, что нужно:

- `identity_generate()` → `{ sign_pk, dh_pk }`
- `identity_from_bytes(bytes)` → то же (для восстановления из хранилища)
- `x3dh_initiate(our_identity, their_bundle)` → состояние сессии
- `x3dh_respond(our_identity, our_bundle, init)` → состояние сессии
- `ratchet_encrypt(state, plaintext)` → `{ header, ciphertext }`
- `ratchet_decrypt(state, header, ciphertext)` → plaintext
- `chunk_encrypt(key, idx, plaintext)` / `chunk_decrypt(key, idx, ciphertext)` —
  для файлов

Состояние сессии — это обычная структура с `to_bytes`/`from_bytes`
(`crypto.rs:418-419`), так что сериализация в WASM уже есть. JS-обёртка
хранит состояния в IndexedDB.

**Риск:** argon2id в WASM медленный. Но argon2 нужен только для ключа хранилища
(при разблокировке), а не для каждого сообщения. Приемлемо.

## 3. UI без Tauri

`ui/src/api.ts` заменяется на двух реализациях одного интерфейса:

- `TauriApi` — как сейчас (`invoke` + `listen`).
- `WebApi` — тот же интерфейс, но поверх WebSocket.

`CoreEvent` (`api.ts:247-277`) — это уже готовый union событий. Для веба он
приходит как JSON по WSS вместо Tauri-события. Формат не меняется: те же имена
полей, те же варианты.

Выбор реализации — одна строка в точке входа (`main.ts`), остальной UI не
знает, где он работает.

## 4. Агент как ретранслятор (WSS-мост)

Расширение `gipny-agent` (или новый бинарь `gipny-web`), который:

1. Поднимает `TorNode` + `SessionManager` как обычно.
2. Слушает WSS на локальном порту (например, `wss://127.0.0.1:7890`).
3. Принимает соединение от браузера, проверяет идентичность браузера
   (см. раздел 6).
4. Передаёт между браузером и сетью только шифротекст:
   - браузер → агент: «положи это на релей получателя X» → `deposit(X, blob)`.
   - агент → браузер: «пришло сообщение для твоего ключа» → `pending_above` +
     `ack`.
5. Не имеет доступа к открытому тексту и не должен его иметь.

**Почему не отдельный релей с HTTP:** релей уже умеет `handle_client` поверх
`DuplexStream` (`relay_server.rs:448`), но это бинарный протокол поверх i2p, а
не HTTP. Добавлять HTTP в релей — значит открывать порт в сеть, что после #103
недопустимо. WSS на локальном порту — это не сеть, это интерфейс между двумя
частями одного приложения.

## 5. Vault в браузере

Вместо `rusqlite` + SQLCipher — IndexedDB с шифрованием на уровне приложения:

- Ключ хранилища выводится из пароля через argon2id (в WASM).
- Каждая запись (контакт, сессия, настройки) шифруется `chunk_encrypt` перед
  записью в IndexedDB.
- При разблокировке кэшируется в памяти, при блокировке — затирается.

Это слабее, чем SQLCipher (нет шифрования на уровне файла), но для браузера
это нормально: браузер и так не даёт изолированного хранилища. Честная граница:
пароль защищает от того, кто прочитал файл базы, а не от того, кто получил
доступ к запущенному браузеру.

## 6. Протокол WSS

Поверх WSS — простой JSON-протокол, по одному сообщению в строку:

```json
// браузер → агент
{ "type": "deposit", "to": "<sign_pk получателя>", "blob": "<base64>" }
{ "type": "claim", "cursor": 0 }
{ "type": "ack", "id": 123 }

// агент → браузер
{ "type": "messages", "items": [{ "id": 123, "blob": "<base64>" }] }
{ "type": "event", "event": { "IncomingMessage": { … } } }
```

Аутентификация браузера: браузер подписывает каждое сообщение своим `sign_pk`,
агент проверяет, что это тот же ключ, который был зарегистрирован при первом
подключении. Это тот же принцип, что и в режиме агента (`identity_sign`), только
подпись идёт по WSS-сообщению, а не по сообщению Double Ratchet.

**Важно:** WSS-канал — это транспорт, а не граница безопасности. Сообщения уже
зашифрованы Double Ratchet, так что перехват WSS не даёт открытого текста. Но
подпись нужна, чтобы чужой не мог подключиться к агенту и читать чужую почту.

## 7. Порядок работ

1. **WASM-крипта** — крейт, экспорт, JS-обёртка, тест на совпадение с нативной
   (один и тот же `x3dh_initiate` в Rust и в WASM даёт одинаковый результат).
2. **Заглушка агента** — WSS-сервер, который принимает `deposit`/`claim`/`ack` и
   перекладывает их в `MemStore`. Без UI, только протокол. Проверяется с
   консольным клиентом.
3. **WebApi** — реализация интерфейса `api.ts` поверх WSS. UI пока не меняется.
4. **IndexedDB-хранилище** — замена `Db::open` для веба.
5. **Сборка вместе** — `main.ts` выбирает `WebApi`, остальное работает как есть.
6. **CI** — сборка WASM, тип-проверка UI, живой тест «браузер ↔ агент ↔ релей».

## Verification (только GitHub Actions)

- **WASM ≡ нативный:** тест, который прогоняет один и тот же сценарий (X3DH →
  N сообщений → проверка) в Rust и в WASM и сравнивает результаты байт в байт.
- **Протокол:** консольный клиент на Python или `curl`, который подключается к
  агенту, делает `deposit`/`claim`/`ack` и проверяет, что почта дошла.
- **UI в браузере:** `vite build` + `tsc --noEmit` — как сейчас, но с `WebApi`.
  Живой прогон в браузере — на машине владельца, не в CI.
- **Сквозной тест:** два браузерных клиента через одного агента — пишут друг
  другу, проверяют, что сообщения доходят и что агент не может их прочитать
  (проверяется тем, что в логах агента нет открытого текста).
