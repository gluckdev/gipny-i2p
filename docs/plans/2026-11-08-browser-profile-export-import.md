# Экспорт и импорт браузерного профиля

Дата: **2026-11-08**. Запись по просьбе владельца: «экспорт и импорты
браузерного профиля в планы». Статус: план, работы не начаты. Сегодня документация
честно говорит: «экспорт/импорт браузерного профиля пока не реализованы»
([browser-messenger.md](../browser-messenger.md)); очистка данных сайта или
вытеснение хранилища браузером уничтожают профиль без возможности восстановить.

## 1. Что есть у нативного клиента

- `export_identity(passphrase, path)`: полный бэкап профиля — настройки, контакты,
  группы с участниками, сообщения, вложения байтами, закреплённые сообщения,
  prekeys, состояние удалений — сериализуется bincode (`BackupV3`) и запечатывается
  `gipny_libcore::security::backup_seal` (Argon2id + XChaCha20-Poly1305, парольная
  фраза от 8 символов) в один файл.
- `import_identity_to_profile(profile, vault_pass, backup_path, backup_pass)`:
  открывает файл и восстанавливает его в **новый** профиль; сессии ratchet не
  переносятся, они устанавливаются заново.
- Схема бэкапа живёт в `core/src/lib.rs` (Tauri), а не в `libcore`, поэтому
  браузерное ядро её сейчас не видит.

## 2. Что есть у браузера

- Профиль: два слота OPFS с XChaCha20-Poly1305 (`storage.ts`), ключ из Argon2id
  (64 МиБ), состояние как JSON внутри `BrowserEngine` (Rust/WASM); вложения в
  OPFS отдельными файлами с ключом на файл; личность, prekeys и сессии в движке.
- Доставка файлов пользователю: потоковый download через service worker
  (`browser-download-sw.js`, `saveBrowserAttachment`) без ключей и без OPFS у
  воркера; на iOS файл уходит в «Файлы».
- Выбор файла пользователем: `<input type="file">`, объекты `File` живут в памяти
  до отправки (`browser-files.ts`).
- Shared-код: `gipny-libcore` уже компилируется в WASM (`browser-router` зависит от
  него), значит `backup_seal`/`backup_open` доступны без копий.

## 3. Два вида экспорта

1. **Снимок браузерного профиля (браузер → браузер).** Один запечатанный архив:
   оба слота vault, `profile.json`, все файлы вложений как есть (они уже
   зашифрованы ключами профиля). Восстановление побайтовое, включая сессии и
   очередь исходящих. Просто и точно, но читается только браузерным клиентом,
   и только при том же пароле профиля (слоты запечатаны им). Ключ архива —
   отдельная парольная фраза, как у нативного бэкапа.
2. **Переносимый бэкап (браузер ↔ натив).** Тот же `BackupV3`, что у нативного
   клиента: движок собирает его из состояния (контакты, группы, сообщения,
   вложения, prekeys, личность) и запечатывает `backup_seal`; импорт в браузер
   открывает `backup_open` и строит из него новый профиль. Сессии не переносятся
   (как у натива). Для этого схему бэкапа надо вынести из `core/src/lib.rs` в
   `libcore` и зафиксировать тестовыми векторами.

Рекомендация: делать оба, в порядке 2 → 1. Переносимый бэкап закрывает главный
риск (потеря профиля при очистке сайта) и даёт миграцию между телефоном,
десктопом и браузером; снимок — быстрый путь восстановления «как было».

## 4. Порядок работ

1. **Схема в libcore.** Перенести `BackupV3` и версии в `gipny_libcore`
   (модуль `backup`), оставить в Tauri только вызовы; тест: нативный экспорт из
   `main` открывается новым кодом байт в байт.
2. **Экспорт в браузере.** Команда воркера `export_backup(passphrase)` → движок
   собирает бэкап из `BrowserState` и OPFS-вложений, запечатывает, отдаёт поток
   через download-SW под именем `gipny-<профиль>-<дата>.gipnybak`. Лимит памяти:
   вложения читать частями, архив формировать потоково (до 2 ГиБ вложений).
3. **Импорт в браузере.** Экран «Импортировать бэкап» на старте: файл, парольная
   фраза бэкапа, пароль нового профиля; воркер открывает бэкап в памяти, создаёт
   профиль через существующий `vault_create`, пишет состояние и вложения, не
   трогая существующие профили; коллизия личности с существующим профилем —
   ошибка, не слияние.
4. **Снимок браузерного профиля** (вид 1): экспорт слотов и вложений как есть,
   импорт в новый каталог OPFS; проверка целостности по SHA-256 архива.
5. **Интерфейс и тексты.** Пункты в настройках и на экране выбора профиля,
   предупреждение, что файл содержит ключи, RU/EN (переводы — Codex), документация
   в browser-messenger.md и README вместо фразы «пока не реализованы».
6. **Проверки.** WASM-тесты round-trip (экспорт → импорт → те же контакты,
   сообщения, вложения, прежняя личность); сценарий в `run_messenger_ci.py`:
   браузер A экспортирует, свежий браузер B импортирует, история видна, новая
   сессия устанавливается и письмо доходит; перекрёстно: нативный бэкап из e2e
   импортируется в браузер. Safari: загрузка файла в «Файлы» и выбор его обратно
   проверяются WebKit-smoke.

## 5. Границы и риски

- Файл бэкапа содержит приватные ключи личности и prekeys; парольная фраза
  должна быть не короче пароля профиля, подбор ограничен только Argon2id.
- Импорт в тот же браузер поверх живого профиля запрещён: два клиента с одной
  личностью одновременно ломают ratchet у собеседников.
- Снимок (вид 1) содержит сессии: восстановление на второе устройство при живом
  первом даёт тот же конфликт; в интерфейсе — предупреждение и совет использовать
  вид 2 для миграции.
- Квоты: импорт проверяет `storage.estimate()` там, где он есть, и падает понятной
  ошибкой при нехватке места до записи первого байта.
