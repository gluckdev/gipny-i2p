# Сайт .i2p на воркере GitHub — план

Идея владельца (2026-09-17): держать сайт проекта внутри i2p, а «сервером» для
него сделать обычный воркер GitHub Actions — тем же приёмом, каким в фазе 5
поднимается сид-узел сети релеев. Пока не начато; это запись идеи и её цены.

## Что это даёт

- **Страница проекта, доступная из i2p** без clearnet: описание, карточка,
  адреса сид-узлов сети релеев, отпечатки сборок.
- **Зеркало релизов внутри i2p.** Сейчас обновления ходят на GitHub через
  *чужой* выходной узел (`exit.stormycloud.i2p`): он не видит содержимого, но
  видит факт обращения, может быть недоступен и делит лимит GitHub API со всеми,
  кто через него идёт. Свой eepsite с файлами релиза убирает выходной узел из
  пути обновления целиком — это единственный способ сделать обновления
  полностью внутрисетевыми. Хорошо сочетается со планом «свой HTTP-клиент поверх
  SAM» (`2026-09-17-borrowing-from-others.md`): с зеркалом внутри i2p клиенту
  вообще не нужен HTTP-прокси и CONNECT к clearnet.
- **Точка входа для новых людей:** ссылка `.b32.i2p`, которую можно дать, не
  раскрывая clearnet-инфраструктуру.

## Как это может работать

То же, что запланировано для сид-узла (`dht-seed.yml`), плюс статика:

1. Воркфлоу по расписанию поднимает i2pd и маленький HTTP-сервер со статикой
   (сгенерированной из `docs/` и со ссылками на файлы релиза).
2. **Постоянный адрес.** Ключи destination и состояние роутера шифруются `age`
   и кладутся в `actions/cache` перед выходом и раз в час; следующий запуск их
   расшифровывает, поэтому `.b32.i2p` не меняется. Публичный ключ — переменная
   репозитория, приватный — секрет (кэш доступен воркфлоу из форков, секреты —
   нет, поэтому украденный кэш бесполезен).
3. `concurrency` — строго один запуск: две копии одного destination означают
   конфликт LeaseSet.
4. Файлы релиза берутся из самого релиза (`gh release download`), чтобы сайт не
   хранил бинарей в репозитории.

## Чего это стоит и где честные оговорки

- **Пересменка.** Задание Actions живёт не больше шести часов, поэтому сайт
  недоступен несколько минут при каждой смене. Для страницы это терпимо; для
  обновлений — нужен запасной путь (сначала зеркало в i2p, при неудаче — старый
  путь через выходной узел).
- **Это нецелевое использование CI.** Держать сетевой сервис на раннерах
  GitHub — не то, для чего они даны; аккаунт за это могут ограничить. Перед
  включением нужно решение владельца с открытыми глазами, а в идеале — дешёвый
  VPS как основной хост и воркер как запас.
- **Первое построение туннелей** после каждой пересменки занимает минуты, даже
  когда состояние роутера восстановлено.
- **Один хост — одна точка отказа.** Сид-узел сети релеев и сайт лучше держать
  в разных запусках: падение сайта не должно уносить сид.

## Порядок

Сначала фаза 5 сети релеев (сид-узел): она отрабатывает шифрованное состояние,
пересменку и `concurrency`. Сайт — это тот же скелет с добавленной статикой,
поэтому делать его имеет смысл после, переиспользуя воркфлоу, а не параллельно.
