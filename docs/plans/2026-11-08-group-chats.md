# Групповые чаты: что есть, чего нет, порядок работ

Дата: **2026-11-08**. Запись по просьбе владельца: «надо записать в планы
поддержку групповых чатов». Статус: план, работы не начаты. Факты о текущем
состоянии взяты из кода `main` на `e911857`; сроков нет, оценки появятся после
первого этапа.

## 1. Что уже есть

- Создание группы с участниками из контактов и ботов (`Core::create_group`),
  добавление участника любым участником (`add_group_member`).
- Доставка: каждому участнику отдельный конверт, очередь `(msg_id, recipient)`
  держится до подтверждения этим получателем и переживает рестарт
  ([группа доставки](../group-delivery.md), PR #120, v0.4.19).
- В группах работают правки, закрепление, «печатает», кнопки ботов, ответы.
- Состав группы (имя, участники с ключами и адресом) едет с каждым сообщением;
  менять его может только участник, ключи участников закреплены; браузерное
  ядро принимает до 64 участников и имя до 128 символов.
- Отключение уведомлений (mute); «Покинуть (локально)» удаляет копию у себя.
- Браузерный клиент принимает и показывает группы тем же UI.

## 2. Чего нет

- Удаления участника и выхода, видимого остальным: «покинуть» сейчас только
  локальное удаление, остальные продолжают слать сообщения ушедшему.
- Согласия на вступление: участника добавляют без вопроса, он сразу получает
  переписку группы.
- Ролей: нет администратора, любой участник меняет состав.
- Переименования, описания и аватара группы после создания.
- Срока жизни сообщений в группах: `send_to_group` игнорирует TTL
  (`_ttl`, `expires_at = None`), хотя личные чаты его поддерживают.
- Истории для нового участника (по умолчанию и не нужна: он видит только то,
  что отправлено после добавления; это надо зафиксировать как решение).
- Групповых ключей: сообщение шифруется N раз, группа из N участников создаёт
  N×(N−1) конвертов на круг; предел масштаба не измерен.
- Описания передачи файлов частями в группах: [file-transfer.md](../file-transfer.md)
  о группах молчит; поведение надо проверить и записать.
- Сводного статуса доставки по участникам в интерфейсе (кому доставлено, кому
  ещё нет) — уточнить, что показывает UI сейчас.

## 3. Порядок работ

Каждый этап — код, интеграция в UI, отрицательные сценарии, CI на точном SHA,
документация RU/EN (правило проекта). Этапы независимы настолько, чтобы
выпускать их по одному.

1. **Журнал состава.** Изменение состава (добавить, удалить, выйти,
   переименовать) — подписанная запись «кто, что, когда», а не только текущий
   список. Правила: участник может удалить только себя (выход) или действовать
   по роли (этап 2); конфликт двух записей решается по времени и подписи;
   запись едет со следующим сообщением и отдельным служебным сообщением, чтобы
   ушедший перестал получать конверты. Тесты: core и libcore на принятие и
   отклонение записей, восстановление после рестарта; e2e: трое участников,
   выход одного, сообщения после выхода не доходят до ушедшего.
2. **Роли.** Создатель — администратор; администратор добавляет, удаляет,
   переименовывает и передаёт роль; остальные могут выйти. Один уровень, без
   иерархии. Тесты на отказ в праве.
3. **Приглашение с согласием.** Добавленный получает запрос «вас приглашает
   {имя} в группу {название}» через существующий механизм запросов контакта;
   до согласия не получает переписку и не числится участником у остальных.
4. **Срок жизни и статус.** Решить, разрешать ли TTL в группах (сейчас молча
   игнорируется — либо поддержать, либо честно отключить в UI); показать статус
   доставки по участникам в карточке сообщения.
5. **Файлы в группах.** Проверить и записать поведение частичной передачи для
   нескольких получателей (квоты, повторная отправка частей каждому); при
   необходимости — одна очередь частей на файл с рассылкой.
6. **Групповые ключи (исследование).** Измерить трафик и время на группу из 16
   при текущей схеме; оценить sender keys и их совместимость с ratchet и с
   очередью до подтверждения. Решение — по цифрам, не по умолчанию.
7. **Браузер.** Паритет этапов 1–4 в `ui/src/browser-core`; сценарий CI «два
   браузера и нативный клиент в одной группе» (есть основа в
   `browser-router/tests/run_messenger_ci.py`).
8. **Документация.** [group-delivery.md](../group-delivery.md) расширить до
   описания групп целиком или добавить `docs/groups.md`; строки в README и
   [current-state.md](../current-state.md); меню группы в интерфейсе и его RU/EN
   строки (переводы — Codex).

## 4. Вопросы владельцу

- Состав меняет только администратор или любой участник (как сейчас)?
- Нужен ли TTL в группах или его отключить в UI?
- Предел размера группы: оставить 64 или задать меньше до появления групповых ключей?
- Новый участник не видит прошлую переписку — зафиксировать как правило?
