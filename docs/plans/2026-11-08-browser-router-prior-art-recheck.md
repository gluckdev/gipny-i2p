# Браузерный роутер: оценка заметок и повторная проверка готовых проектов

Дата: **2026-11-08**. Предмет: корпус исследования `research_notes/I2P клиент в
браузере/` (2026-11-01), план [2026-11-01-browser-router-wasm.md](2026-11-01-browser-router-wasm.md)
и вопрос владельца: не сделал ли кто-то за это время I2P-роутер для браузера и
можно ли вынести роутер отдельно, например на Java. Поиск: GitHub (репозитории,
код, issues) и веб, 2026-11-08. Выводы — внизу, в разделе 4.

## 1. Что говорили заметки и что с ними стало

Корпус состоит из пяти заметок исследователя (prior art, toolchain, транспорты и
входные узлы, хранилище/ключи/PWA, модель угроз) и пяти заметок внешних воркеров.
Каждая заметка разбита на «Takeaway / Cited findings / Inferences / Gaps», каждый
факт датирован и снабжён URL, непроверенное помечено. Это редкое качество для
заметок такого объёма: их можно проверять по частям. Слабые места тоже названы в
самих заметках: zzz.i2p и Reddit не искались; быстро стареющие факты (версии
CheerpJ, Safari, Emscripten) привязаны к датам.

Главные выводы заметок:

1. Никто не запускал I2P-роутер в браузере и не собирал его в WASM; у i2pd есть
   закрытое issue #1817 (2022–2023) с отказом из-за pthreads.
2. Единственный путь с рабочим прецедентом — Rust-ядро с заменяемым runtime плюс
   мост на нативной стороне (Arti → tor-js). Для I2P такой хук — трейт `Runtime`
   в emissary-core.
3. i2pd → Emscripten несёт три независимых риска, которые никто не брал вместе:
   pthreads и COOP/COEP (GitHub Pages их не ставит), Boost.Asio поверх неполной
   эмуляции сокетов через WebSocket с открытым багом `select()`, отказ upstream.
   SSU2 (UDP) в браузере невозможен в принципе.
4. Java I2P → CheerpJ: прецедентов нет, сеть только через Tailscale-over-WebSocket
   с выходным узлом оператора, проприетарная лицензия (toolchain, KQ3).
5. При любом варианте у браузерного узла есть компонент на нативной стороне;
   архитектурное решение — это мост, а не язык роутера.

Что подтвердилось делом, а не рассуждением: спайк #143 (emissary-core на wasm32,
exploratory-туннели 3+3 по 2 хопа в Chrome CI), затем мессенджер в `main` и в
0.5.0-rc3; сценарий двух браузеров в CI и браузер ↔ телефон 2026-11-07 (туннели
64 с, доставка 32 с); 2026-11-08 тот же клиент прошёл в движке Safari (Playwright
WebKit 27.2: профиль за 0,3–0,5 с, вход в чаты за 0,7 с, PR #154). Устарели только
статусы: PR #144 объединён, а «мост не развёрнут» верно до сих пор.

Чего заметки предсказать не могли: что публичный клиент на Pages останется без
`browser-config.json` (вопрос развёртывания, не исследования) и что экран загрузки
спрячет это за «повторим в фоне». Обе проблемы закрыты в PR #154.

**Оценка:** заметки верны и подтверждены практикой; переписывать их не нужно,
дополнять — только датированными приписками (как сделано в prior art, см. ниже).

## 3. Оценка плана из заметок сессии: спайк A против спайка B

Заметки сессии 2026-11-07 предлагали два спайка: A — libi2pd в один поток под
Emscripten (`-sASYNCIFY` или `-pthread` + coi-serviceworker), B — довести emissary
до «туннелей как у i2pd».

**Спайк A: снять с повестки.** Три риска из заметок не изменились, и добавились
конкретные: (1) coi-serviceworker должен контролировать scope страницы, а у клиента
там уже стоит свой `browser-sw.js` (офлайн-оболочка); на один scope один service
worker, то есть инъекцию COOP/COEP пришлось бы встраивать в наш SW, Safari без
`credentialless` потребует CORS/CORP на каждом кросс-доменном ресурсе (снапшот
netDb), первый визит получит перезагрузку; (2) ASYNCIFY — около +50 % CPU и больший
бинарь, а JSPI лежит вне нашего порога (Safari 27+); (3) за неделю этого никто не
сделал и за три года тоже. Просьба владельца «адаптировать i2pd и его туннели» честно
читается как паритет поведения туннелей, а не как бинарь i2pd в браузере.

**Спайк B: это путь, и он уже дальше, чем записано.** Сценарий двух браузеров и
браузер ↔ телефон работают (CI, 2026-11-07), так что остаётся не «построить», а
«измерить и подтянуть»: параметры клиентского пула по умолчанию i2pd (длина,
количество, разброс из `tunnels.conf`), публикация LeaseSet через исходящий путь и
её повтор после рестарта, окна streaming, время до первого туннеля на телефоне.
Ориентир по форме ядра — axon-i2p (sans-I/O), по транспорту — слои webtor-rs.

**Java отдельно:** ответ дан в сессии 2026-11-08 и опирается на toolchain KQ3:
Java в Safari не исполняется, Java → WASM упирается в те же потоки/сокеты/размер,
а «отдельный роутер на Java» — это сервер, к которому браузер ходит по WSS, то
есть тонкий клиент, отвергнутый решением 2026-11-01. Язык роутера мост не убирает.

**Мост — пункт номер один.** Без развёрнутого форвардера публичный клиент
работает только офлайн (PR #154, чек-лист в
[browser-messenger.md](../browser-messenger.md#hosting-status)). Непроверенная
подсказка из FaunaTor: их relay живёт бесплатным Cloudflare Worker, а Workers
умеют исходящий TCP; можно ли собрать Rust-форвардер WSS → NTCP2 под Workers и что
при этом увидит Cloudflare (IP браузера, адреса пиров, объёмы) — вопрос для
владельца, не план.

## 4. Выводы и следующий шаг

1. Заметки 2026-11-01 верны, подтверждены спайком и рабочим клиентом; хранить как
   есть, дополнять датированными приписками.
2. Готового чужого решения нет; появившиеся проекты (webtor-rs, FaunaTor, nostra,
   axon-i2p) подтверждают наш путь и дают образцы, не замену.
3. Спайк A (i2pd/Emscripten) снять; спайк B (паритет туннелей emissary) вести как
   измерения с цифрами на телефоне.
4. Владелец: развернуть мост или решить вопрос про Workers; без этого любой
   прогресс по роутеру невидим пользователю.
