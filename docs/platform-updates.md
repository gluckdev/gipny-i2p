# Обновления приложения и агента

Состояние реализации: 2026-10-28, рабочая ветка `feat/today-integration-20261028`.
Матрица описывает поведение кода; проверка установки на реальном устройстве
отмечается отдельно от unit-тестов и компиляции.

## Проверка и политика

Приложение и агент проверяют стабильный GitHub Release через собственный I2P
stream к outproxy, затем TLS до GitHub. Обновлятор выбирает ровно один asset
с точным именем: компонент, версия релиза, архитектура и формат установки.
Повтор одинакового имени, неправильная версия и неизвестный target не выбираются
по похожему суффиксу. Поддерживаются стабильные версии `major.minor.patch`.

`SHA256SUMS.txt` обязателен. Его отсутствие, неоднозначные строки или неверный
SHA256 останавливают обновление; непроверенный исполняемый файл не публикуется.
Метаданные, manifest, архив и распакованный executable имеют ограничения размера.
SHA256 из того же релиза проверяет целостность, но не является независимой
подписью издателя.

Первая автоматическая проверка выполняется через 30 секунд, следующие успешные
проверки — через 6 часов. Ошибка загрузки или установки возвращается в цикл
повтора с задержками 60, 300, 1200 и 3600 секунд. Автоматическая установка по
умолчанию включена; сохранённый `auto_update=0` или `GIPNY_NO_AUTO_UPDATE`, равный
`1`, `true`, `yes`, `on` без учёта регистра, её отключает. Значение `0` переменной
её не отключает. Явная ручная команда установки остаётся доступна.

Явное отклонение версии сохраняется в `dismissed_update_version`. Подготовка
обновления и открытие системного установщика не записывают отклонение. Успешная
подготовка запоминается только до завершения текущего процесса; отменённый
системный запрос можно повторить. В приложении операции установки сериализованы.

## Приложение

| Сборка | Asset | Действие после проверки |
|---|---|---|
| Linux x86_64 AppImage | `gipny-i2p_<version>_amd64.AppImage` | Уникальный временный файл рядом с `$APPIMAGE`, sync и атомарная замена; новая версия при следующем запуске |
| Linux arm64 AppImage | `gipny-i2p_<version>_aarch64.AppImage` | Та же замена AppImage |
| Linux x86_64 / arm64 deb | `gipny-i2p_<version>_amd64.deb` / `_arm64.deb` | По нажатию пользователя `pkexec apt-get install`; отказ пароля возвращается как ошибка, старая программа продолжает работать |
| Windows x64 NSIS | `gipny-i2p_<version>_x64-setup.exe` | Публикуется полный `pending_update` с версией и SHA256; установщик запускается при следующем запуске профиля |
| macOS arm64 / x86_64 | `gipny-i2p_<version>_aarch64.dmg` / `_x64.dmg` | По нажатию пользователя `/usr/bin/open` открывает проверенный DMG; пользователь заменяет приложение обычным способом |
| Android arm64 / armv7 | `gipny-i2p_<version>_android-arm64.apk` / `_android-armv7.apk` | Проверенная cache-копия передаётся системному установщику через `FileProvider`; разрешение и подтверждение принадлежат Android |

Открытие DMG или Android installer означает передачу пакета системе, а не
подтверждённую установку. Программа не объявляет новую версию установленной и не
скрывает релиз навсегда. APK picker также выбирает точное имя версии и архитектуры
и требует SHA256. Неизвестные архитектуры автоматически не подменяются соседними.

На Windows запуск сначала атомарно переименовывает `installer.exe` в
`installer.claimed.exe`, затем повторно проверяет локальный SHA256 и запускает
NSIS. Ошибка запуска возвращает файл в pending; старое приложение продолжает
старт. Успешное создание процесса позволяет старому приложению выйти. Если после
передачи установщику снова запускается старая версия, сохранённый claimed-файл
вызывает понятную ошибку, сохраняя старое приложение и пакет для диагностики.
Когда запускается целевая или более новая версия, staging очищается по возможности.
Создание процесса не доказывает успешную установку NSIS.

При атомарной замене ошибка до публикации сохраняет старый исполняемый файл.
Уникальные временные файлы исключают общую `.new` между конкурентными попытками.
Это не обещание восстановления файловой системы после любого сбоя питания.

## Агент

Linux GNU использует `gipny-agent_<version>_linux-amd64.tar.gz` или
`_linux-arm64.tar.gz`, macOS — `_darwin-amd64.tar.gz` или `_darwin-arm64.tar.gz`.
Обновлятор извлекает один обычный `gipny-agent`, отклоняет дубликаты, ссылки,
небезопасные пути и превышение лимитов. Уникальный временный executable в каталоге
текущего binary публикуется атомарно после sync. Текущая сессия продолжает работать;
новый binary используется при следующем старте службы или процесса.

Сборки Linux musl выбирают только точное имя
`gipny-agent_<version>_<Rust target>.tar.gz` по target, записанному Cargo:

- `aarch64-unknown-linux-musl`;
- `x86_64-unknown-linux-musl`;
- `i686-unknown-linux-musl`;
- `armv7-unknown-linux-musleabi`.

GNU fallback для musl отсутствует. Этот список не означает поддержку любого
роутера OpenWrt: важны ABI, CPU, память, версия ядра и конкретная сборка релиза.
MIPS и ARMv6 в этот контракт не входят. Наличие selector не заменяет успешную
сборку и проверку конкретного release asset.

Windows использует `gipny-agent_<version>_windows-amd64.tar.gz`. Установщик должен
настроить Scheduled Task через `start-agent.ps1`; существующая старая установка
требует повторного запуска `install-agent.ps1`, чтобы сменить action задачи.
Отсутствующий bootstrap — ошибка с инструкцией переустановки, пакет сохраняется.
Агент публикует `<DataDir>/pending_agent/ready.json` с basename уникального `.exe`,
SHA256 и версией только после записи и sync executable. Более старая попытка не
заменяет уже ожидающую более новую версию. Bootstrap проверяет запись, заменяет
остановленный executable перед следующим запуском задачи и сохраняет backup для
rollback до подтверждения готовности дочернего агента. Сам `Process.Start`
не считается подтверждением: новый child может выйти с ошибкой OS credential
provider, SQLCipher или session initialization уже после успешного запуска ОС.

Bootstrap передаёт случайный 32-byte nonce и уникальный путь в приватном
`DataDir` только через `ProcessStartInfo.EnvironmentVariables`. В argv и
recovery journal их нет. Синхронный `main` агента забирает и удаляет эти env
до создания Tokio threads, чтобы ticket не наследовали shell-команды мастера.
После provider/SQLCipher, `SessionManager`, relay/master registration и worker
initialization агент пишет sync+atomic marker с nonce и собственным PID.
Bootstrap проверяет точный формат, nonce, PID своего Process handle, размер
и отсутствие reparse point. Private ACL — часть границы: nonce не защищает
от root, SYSTEM или атакующего с эквивалентным доступом к процессу/каталогу.

Ожидание ограничено десятью минутами для холодного I2P startup. Выход до marker,
неверный marker или timeout означают отказ: bootstrap завершает только child,
которого сам запустил, ждёт его выхода, восстанавливает старый binary и
запускает его без ticket. По имени процесса или PID из файла никого не убивают.
Rejected package остаётся для диагностики, а его прежний `ready.json` получает
имя `rejected-*.json`, чтобы следующий task start не повторял отказ автоматически.
Это относится к прежней staging-заявке: разрешённый auto-updater может позже
скачать и подготовить новую попытку той же версии; постоянный dismissal здесь
не записывается.
Более новая одновременно опубликованная заявка этим cleanup не удаляется.

До File.Replace фиксируется bounded recovery journal с допустимым basename
backup и SHA256 старого/нового image. После прерывания bootstrap следующий старт
восстанавливает незавершённую замену; после подтверждённой readiness journal
фиксирует acceptance до удаления backup. Неожиданный hash, path или занятый
чужим процессом image оставляют recovery state и дают явную ошибку. Произвольные
пути из journal не передаются File.Replace. Это подготовка к следующему старту
задачи, а не немедленный рестарт работающей сессии.

Rollback восстанавливает **binary**, а не предыдущий snapshot базы. Readiness
обозначает успешную границу startup, не долгосрочную исправность процесса или
доставку команды по живой I2P. Перед будущим релизом, меняющим формат vault/БД,
нужно отдельно доказать совместимость старого binary с уже выполненными
миграциями или спроектировать version-aware rollback. Возврат прежнего
исполняемого файла сам по себе не является откатом миграции данных.

Без явного `--name` агент выбирает английское или русское ASCII-имя кота и
сохраняет его как `agent_name` в своей БД. Перезапуск сохраняет имя. Явное
`--name` обновляет сохранённое имя; hostname не используется как default.

## Границы проверки

2026-10-28 в текущем рабочем дереве выполнены focused Rust-проверки:
`cargo test --locked -p gipny-libcore --lib update::tests` — 22 PASS;
`cargo test --locked -p gipny-agent` — 2 PASS, включая сохранение имени после
reopen БД. Они использовали `I2P_EMBED_STUB=1` и не запускали настоящий роутер.
`npm test` — 9 PASS, включая EN/RU DOM-проверку системного handoff без restart
или dismissal; `npm run build` — PASS. Это запись targeted-проверок, а не
подтверждение полного native release или всех последующих изменений ветки.

Unit-тесты проверяют выбор asset, неоднозначность manifest, повреждённые загрузки,
сохранение старого executable, конкурентные Unix replacement, Windows claim и
восстановление после ошибки запуска, version-aware Windows agent staging и
сохранение имени кота после reopen БД. Host-тесты Windows-функций с подставленным
launcher не выполняют NSIS или Scheduled Task.

Новые readiness/journal regressions подготовлены **после** этих исторических
прогонов. Первый Windows run checkpoint `d907307` **2026-10-28**
[обнаружил ошибку](https://github.com/gluckdev/gipny-i2p/actions/runs/40757760043/job/123061162221):
PowerShell передал `$null` backup в `File.Replace` как недопустимый пустой path.
Исходник исправлен на уникальный принадлежащий bootstrap временный backup
журнала. Повторный Windows run **2026-10-28**, source
`5d3500d388e2985d90c17cbf92fb1db7ed23172b`,
[прошёл](https://github.com/gluckdev/gipny-i2p/actions/runs/40758501807/job/123063747261)
все checksum/replacement/readiness/rollback/recovery fixtures. Это проверка
bootstrap на настоящем Windows runner с тестовыми дочерними executables,
не установка службы и не запуск настоящего I2P-агента.
`scripts/tests/windows-agent-update.ps1`
компилирует C# fixtures из исходников непосредственно в Windows GitHub Actions:
успешная readiness, отказ native loader, early exit, timeout, неверные nonce/PID,
непричастный процесс с тем же basename, interrupted journal recovery и отказ
на traversal/tampered backup. Timeout fixtures используют внутренний параметр
в секунды, production default остаётся 600 s. Два новых Rust tests проверяют
строгий ticket, atomic marker, directory/PID binding и сохранение чужого temp.
Локальная сборка или исполнение этих проверок не выполнялись.

Для обещания рабочей установки нужны отдельно: native Windows CI bootstrap,
запуск и обновление установленных NSIS/AppImage/deb/DMG/APK, системные разрешения,
подпись Android и Gatekeeper macOS, а также реальные OpenWrt устройства нужного
ABI. Компиляция Android arm64 сама по себе этого не подтверждает.
