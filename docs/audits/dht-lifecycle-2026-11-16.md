# DHT lifecycle: статический аудит 2026-11-16

Проверены текущие файлы рабочего дерева, независимо от прошлых отчётов.
Область: Core, SessionManager, durable inbox/seen, сбор почты, адресные lookup и
обновление prekeys. Ниже доказательства по коду и сценарии для регрессионных
тестов; сами тесты и исправления в этом шаге **не выполнялись**. Номера строк
относятся к состоянию на момент аудита. Общая безопасность DHT не подтверждена.


## Навигация после структурного переноса

Ниже сохранены номера строк исходного аудита. После декомпозиции 2026-11-16
те же реализации находятся в следующих модулях; поведение не исправлялось:

- Session DHT collect/lookup — `libcore/src/session/dht.rs`;
  prekey publication — `libcore/src/session/identity.rs`;
  decrypt/receive — `libcore/src/session/inbox.rs`;
  relay tasks — `libcore/src/session/relay.rs`.
- DB DHT storage/seen — `libcore/src/db/dht.rs`;
  contacts/address updates — `libcore/src/db/contacts.rs`.
- Core shutdown/track — `core/src/core/lifecycle.rs`;
  prekey selection — `core/src/core/identity.rs`;
  hosted relay/join — `core/src/core/hosted_relay.rs`;
  warm relay — `core/src/core/relay.rs`.
- `core/src/core/dht.rs`, `core/src/core/inbox.rs`, `libcore/src/db/inbox.rs`
  сохранили пути, но форматирование также могло изменить номера строк.


## 1. Seen сохраняется раньше письма: потеря DHT-копии при прерывании

**Высокий приоритет, Core и SessionManager, не исправлено.**

- `core/src/core/dht.rs:90` и `libcore/src/session.rs:2234` вызывают
  `dht_seen_mark` до входа в `handle_incoming_envelope`.
- Это самостоятельный `INSERT OR IGNORE`: `libcore/src/db.rs:2233`.
  Транзакция `commit_received` сохраняет prekey/session/inbox, но не seen:
  `libcore/src/db/inbox.rs:53`.
- До commit есть ожидания mutex, например `core/src/core/inbox.rs:100`;
  shutdown отменяет tracked tasks (`core/src/core.rs:672`,
  `libcore/src/session.rs:301`). Обработчик ошибок с `dht_seen_forget`
  при отмене future или аварийном завершении не выполняется.

Сценарий: получить envelope, сохранить seen, остановить collect до commit
inbox, открыть профиль повторно. Та же DHT-копия пропускается как обработанная,
хотя inbox пуст и ratchet не продвинут. Seen живёт 8 суток
(`core/src/core.rs:103`, `libcore/src/session.rs:137`), mail — 7 суток
(`dht/src/items.rs:12`), поэтому purge не спасает эту копию. Повторная отправка
нового envelope отправителем может восстановить доставку; offline fallback
этого не гарантирует.

Тест: барьер после mark и до commit, abort collect, закрытие/повторное открытие
DB, повторная выдача того же envelope. Ожидание: ровно одно сохранённое письмо.
Отдельно проверить две конкурентные collect и прерывание после commit. Простое
перемещение mark после handle без общей атомарности недостаточно: остаётся окно
между расходованием ratchet key и записью dedup.

## 2. Повторные проходы перестают искать ещё живую почту

**Высокий приоритет для offline delivery, оба пути, не исправлено.**

Core после первого прохода переключается с 7 на 2 дня
(`core/src/core/dht.rs:34`, `:47`); SessionManager — аналогично
(`libcore/src/session.rs:2158`, `:2166`, `:2193`). Генераторы ключей проверяют
только `0..days`, то есть сегодня/вчера при `days=2`
(`dht/src/items.rs:105`, `:110`). Временная ошибка получения или `SealedDrop`
не сохраняет старый day-key для последующего обхода.

Сценарий: клиент работает без перезапуска; письмо остаётся недоступным во время
трёхдневного сбоя DHT. После восстановления сети оно ещё укладывается в 7-суточный
TTL, но обычные collect его key уже не спрашивают. Отдельный startup/join/kick
может инициировать широкий обход, но это не часть гарантированного retry после
любой сетевой ошибки. Тест с управляемыми часами: восстановить доступ к письму
трёхдневной давности при работающем lifecycle и проверить получение до TTL.

Есть и граничный случай первого прохода: 7 календарных buckets не покрывают
полные 168 часов. Например, письмо дня D в 23:59 живо в D+7 в 00:01, а `days=7`
проверяет лишь D+7..D+1. Тест: граница суток, возраст чуть больше 6 суток.

## 3. Весь collect накапливается до обработки, общего бюджета нет

**Средний приоритет, оба пути, не исправлено.**

`core/src/core/dht.rs:63-87` и `libcore/src/session.rs:2206-2232` получают весь
список контактов, introductions и затем mail каждого контакта в общий `Vec`.
`Db::list_contacts` не ограничивает число строк (`libcore/src/db.rs:814`).
При C подходящих контактах выполняется до `days * (C + 1)` последовательных
вызовов `node.get`, прежде чем обрабатывается первая introduction. Core исключает
Incoming-запросы; SessionManager исключает только Blocked.

В lifecycle нет общего ограничения bytes/items, времени обхода или количества
одновременных collect. Startup join может пересекаться с периодическим collect:
`core/src/core.rs:911-918`, `libcore/src/session.rs:335-342`. Атомарный seen-mark
исключает повторную обработку одинакового hash в нормальном исполнении, но не
дублирующие сетевые запросы и удержание результатов. Один медленный поздний
контакт задерживает уже собранные introductions всех остальных.

Тест: fake collector выдаёт первые письма немедленно, последний контакт ждёт
барьера; проверить, что первые письма обрабатываются в заданный срок и пиковый
объём удержанных данных ограничен. Отдельный тест на два одновременных запуска.
Лимиты внутри node/client требуют отдельной проверки; per-response лимит сам
по себе не ограничивает сумму результатов этого lifecycle.

## 4. Core оставляет address lookup работающим после shutdown

**Средний приоритет, Core; SessionManager этот handle хранит. Не исправлено.**

`core/src/core/dht.rs:147` отбрасывает `JoinHandle`, сохраняя внутри задачи
`Arc<Core>`. Shutdown отменяет только handles в `tasks`
(`core/src/core.rs:672`). После ответа lookup может изменить DB, отправить событие
и вызвать `warm_relay_of` (`core/src/core/dht.rs:163-168`), который тоже запускает
detached task (`core/src/core.rs:1309-1317`). Это продолжение работы старого
экземпляра после закрытия/смены профиля; уничтожение его ресурсов откладывается.

В SessionManager lookup и warm task tracked
(`libcore/src/session.rs:2285`, `:2309`, `:430-439`); этот конкретный дефект
отбрасываемого handle к нему не относится. В обоих путях throttling — только
раз в 10 минут на contact ID, без общего semaphore/in-flight marker. Это не
задаёт глобального предела фоновых lookup и допускает перекрытие медленных
запросов. Верхняя граница времени node lookup проверяется отдельным аудитом.

Тест: задержать find_address, вызвать shutdown, освободить ответ; DB/события/
открытие relay не должны меняться. Нагрузочный тест: много контактов и медленные
ответы, проверить общий лимит одновременно активных запросов.

## 5. Поздний DHT-ответ может откатить более свежий адрес

**Средний приоритет, оба пути, не исправлено.**

Lookup запоминает `known` до await и после ответа сравнивает только с ним,
игнорируя `issued`: `core/src/core/dht.rs:146-164`,
`libcore/src/session.rs:2282-2300`. Затем безусловно обновляет строку по ID
(`libcore/src/db.rs:791`). За время запроса новое аутентифицированное сообщение
может сообщить другой relay (`core/src/core/inbox.rs:316-324`,
`libcore/src/session.rs:1452-1459`). Поздний корректно подписанный, но старый
DHT-record перезапишет более свежий адрес, уже известный приложению.

Сценарий/тест: исходный A; задержать lookup с ответом B; принять сообщение с C;
завершить lookup B. Ожидание: C сохраняется. Нужна проверка текущей identity,
существования и актуальности строки при применении результата; простой повторный
read не обеспечивает атомарность с конкурирующим update. Это ошибка свежести,
а не доказанный обход проверки подписи DHT-record.

## 6. Core не обновляет DHT bundle после расходования OPK

**Средний приоритет, Core; SessionManager обновляет. Не исправлено.**

После принятия X3DH вызывается `republish_bundle`
(`core/src/core/inbox.rs:56-57`, `:83-84`). В Core он пополняет prekeys и пишет
только на relay (`core/src/core/dht.rs:187-196`). DHT обновляется при join и
periodic maintain (`core/src/core.rs:914`, `core/src/core/dht.rs:43`), интервал
maintain 45 минут (`libcore/src/dht_client.rs:34`) плюс длительность работы.
SessionManager вызывает publish DHT в самом republish
(`libcore/src/session.rs:2323-2332`).

Сценарий: опубликовать bundle с OPK p, принять первую introduction и удалить p;
до следующего maintain другой отправитель получает прежний bundle. Его init
даёт StaleOpk (`core/src/core/inbox.rs:263`), а collect удаляет DHT-копию
(`core/src/core/dht.rs:98-101`). Тест на fake DHT: после расходования p запись
должна содержать следующий доступный prekey без ожидания maintain.

Отдельная архитектурная граница обоих путей: один публичный bundle содержит один
OPK (`core/src/core.rs:1224-1233`, `libcore/src/session.rs:723-729`). Два offline
отправителя могут одновременно выбрать его до любого republish; второй init
уже нельзя открыть после расходования первого. Немедленный refresh уменьшает
окно, но не решает эту коллизию. Нужен отдельный сценарий двух отправителей и
решение для DHT bootstrap, сохраняющее свойства X3DH, а не повторное использование
уже израсходованных ключей без анализа протокола.

## Что не установлено

Не проводились live I2P-прогоны, fault injection, межплатформенные проверки и
аудит всех сетевых/криптографических примитивов. Не утверждается, что любой из
описанных сценариев уже наблюдался у пользователей. Выводы опираются на конкретные
ветви кода и требуют регрессионных тестов до закрытия соответствующих задач.
