# Удаление личных сообщений у обоих участников

Состояние на **2026-10-28**: изменение подготовлено в рабочем дереве
`feat/today-integration-20261028` для кандидата `0.4.19`. Это ещё не
опубликованный релиз. Новые DB/wire и UI regression tests прошли в
**GitHub Actions** на `38892f6` и повторно на `a66d223`. Старые результаты updater/group outbox
не являются проверкой этого изменения.

## Поведение

В личном диалоге любой из двух участников может удалить своё сообщение или
сообщение собеседника. Удаляются текст, inline attachments и файлы, передаваемые
частями. Вместо сообщения остаётся постоянная отметка с его номером. Очередь
запроса хранится до аутентифицированного E2E ACK второго приложения; локальный
enqueue, transport ACK релея и успешная запись в DHT этого не заменяют.

Интерфейс различает ожидание подтверждения и полученный ACK. Отметка удаления
не является новым сообщением: она не увеличивает unread и не создаёт звук или
уведомление. Для неё недоступны reply/edit/forward/buttons и повторное удаление.
Удаление текста из истории также убирает доступные через приложение вложения
и ссылки на действующий transfer.

Команда в меню личного диалога очищает его у обоих участников; общая очистка
истории использует тот же протокол для всех DM. Явно установленный
таймер DM тоже создаёт отметку и запрос удаления, включая закреплённое
сообщение. Сообщение, пришедшее уже после своего срока, не показывается как
новый текст. Поведение групп этим протоколом не расширяется: их прежняя
локальная очистка и исключения для pinned records остаются отдельными.

## Идентификатор и постоянный номер

Wire reference содержит **public key автора + исходный `origin_msg_id` +
`sent_at`**. Это не чужой локальный DB ID. Для исходящего сообщения origin
фиксируется у автора; у получателя хранится переданный origin. Контекст
аутентифицированной сессии ограничивает запрос текущим личным диалогом,
а автором target может быть только один из двух его участников.

Проверка удаления не использует старый `resolve_contact_message` с
`id OR origin_msg_id`. Чужой контакт, другой автор, неправильный target и
попытка заранее удалить ещё не существующее сообщение этого устройства
не получают доступ к другой переписке. Автор может удалить своё сообщение
до прихода его содержимого на вторую сторону: tombstone заблокирует его позже.

`dm_seq` — отдельный неизменяемый локальный порядковый номер внутри диалога.
Он выделяется при приёме строки и не переиспользуется при удалении, очистке,
истечении срока или reopen. Например, живые сообщения №1, №3, №5, №10
сохраняют номера; остальные позиции остаются отметками удаления. Одновременные
offline-отправки могут дать разный порядок приёма на двух устройствах,
поэтому этот номер не используется в протоколе и не обещает общего глобального
порядка. Пагинация истории сохраняется.

## Транзакция, повторы и файлы

`libcore/src/db/dm.rs` реализует общую границу для `Core` и `SessionManager`:

1. Одна транзакция создаёт tombstone, при локальной операции добавляет
   `dm_delete_outbox`, очищает body, настройки buttons/sound/console и pinned,
   удаляет ключи/метаданные attachments, transfers и обычные pending.
2. Пути зашифрованных файлов попадают в durable `deleted_file_cleanup`.
   После commit выполняется unlink; неудачные удаления остаются для повторной
   очистки и после reopen. Это не гарантия физического стирания SSD, снимков
   файловой системы или уже созданных копий.
3. Синхронная блокировка file mutations охватывает чтение transfer state,
   запись части и публикацию результата в БД. Удаление использует ту же
   блокировку. `await` внутри этой границы отсутствует; chunk не может
   закончить запись после удаления и заново опубликовать ключ.
4. Новые DM chunks несут исходную reference. Части до offer дополнительно
   связываются с ней через `dm_early_files`: удаление очищает их, даже если
   offer никогда не придёт. Отвергнутые file IDs сохраняются без имён и ключей,
   чтобы поздние chunks не создали новый transfer.
5. Повторный delete снова подтверждается, но не создаёт новую строку или
   новое unread. Только точный ACK из той же сессии снимает соответствующее
   ожидание. После потери ACK запрос повторяется и подтверждается заново.

Backoff запроса растёт до пяти минут. В отличие от обычной семидневной
почтовой очереди запрос удаления сам не истекает: иначе долгий offline
незаметно превратил бы удаление у обоих в локальное. Доступность маршрута,
блокировка контакта и поддержка протокола второй стороной влияют на ожидание.

Replay исходного текста и offers проверяется до публикации содержимого.
Поздний edit не превращается в новое DM и не меняет tombstone. UI принимает
`MessageDeleted` отдельно от `IncomingMessage` и игнорирует поздние edit/file
events для уже удалённой строки. Обычные события публикуются в точке,
упорядоченной с транзакцией удаления.
Запоздавший list/pinned IPC response тоже проходит через tombstone overlay.
При удалении очищаются относящиеся к представлению previews, image URLs и
модальные копии; активные draft/pending/console history сбрасываются, чтобы
сохранявшаяся копия не осталась в редакторе. Граница WebView и отсутствие
гарантии GC-стирания описаны в [memory-security.md](memory-security.md).

## Совместимость и backup

`WireDm` добавлен в конец payload. Декодер сохраняет чтение старых форматов,
включая прежний полный file payload (`WireV10`). Старый клиент читает обычное
сообщение по прежнему префиксу, а пустой delete control игнорирует. Он не
присылает ACK нового протокола: интерфейс остаётся в ожидании, без ложного
«удаление подтверждено». Для удаления у обоих нужны поддерживающие его клиенты.

Новые encrypted backups содержат metadata-only sidecar `dm_state_v1` в
существующем settings vector; layout backup V2/V3 не меняется. Public keys
сопоставляют контакты при восстановлении, даже если локальные contact IDs
различаются. После восстановления attachments применяются origins, номера,
tombstones и очередь запросов; отмеченное удаление снова убирает тело и ключи,
если более ранний snapshot ещё содержал их. Sidecar не дублирует сообщения,
имена файлов, file keys или ciphertext. Он не заставляет старые сохранённые
копии или экспортированные файлы исчезнуть вне приложения.

Старые backup не сохраняли incoming origin. Для такого сообщения нельзя
доказуемо определить запись на второй стороне по локальному ID. Операция
возвращает явную ошибку и оставляет сообщение без изменений, вместо тихого
локального удаления под видом удаления у обоих. Исторически удалённые до этого
изменения строки и номера не восстанавливаются. Автоматический таймер такой
старой записи тоже не может доказать удаление на второй стороне и оставляет
её; при этом таймеры остальных сообщений выполняются. Общая ручная очистка
с таким legacy record возвращает ошибку целиком, без частичного удаления.
Перенос профиля не добавляет
multi-device protocol: одна identity по-прежнему имеет одно активное устройство.

Удаление — действие сотрудничающих приложений. Оно не отзывает прочитанное,
скриншоты, OS notifications, старые backups или данные модифицированного клиента.
SQLCipher/SQLite и файловая система не объединены в power-loss transaction;
прежний `WAL`/`synchronous=NORMAL` не расширяет гарантии при потере питания.
