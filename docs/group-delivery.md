# Групповая доставка: очередь до подтверждения получателем

Состояние на **2026-10-28**: очередь до ACK реализована в
`0460e2fe7a57c47140515d4ee42b0c7adf1adb4e`
([PR #120](https://github.com/gluckdev/gipny-i2p/pull/120)), ещё не выпущено.
Ветка `fix/atomic-group-outbox` от этой ревизии дополнительно закрывает окно
между сохранением сообщения и готовностью очереди. База исходного дефекта —
`main` `26487a5ca213c4ccbbd372038d14a71e17ca6314`.

## Исправляемый сбой

В базовой версии `Core::send_to_group` и `SessionManager::send_to_group`
удаляют запись `pending_outbound` после успешной постановки зашифрованного
конверта в канал отправки. Такое же удаление есть при повторе. Если соединение
оборвётся до передачи конверта или релей потеряет письмо до получения клиентом,
отправитель больше не повторит сообщение этому участнику. Успех локального
канала ещё не подтверждает доставку получателю.

Исправление сохраняет отдельную запись `(msg_id, recipient_contact_id)` до
подтверждения этим получателем. Один и тот же контракт действует в приложении
(`core/src/core.rs`) и у агента и ботов (`libcore/src/session.rs`).

## Публикация очереди и подтверждение

1. Отправитель определяет снимок получателей: известные контакты участников
   группы, кроме себя и заблокированных контактов. Ошибка чтения контакта из БД
   прерывает подготовку.
2. `StagedGroupAttachments` заранее шифрует файлы на диске, завершает запись
   через `sync_all` и готовит стабильные file ID и SHA256 для offers. В памяти
   готовятся доступные этому API метаданные: ответ, сериализованные кнопки и звук,
   описание группы и первоначальный payload. В истории сообщения ещё нет.
3. `Db::commit_outgoing_group` принимает `NewOutgoingGroup` и подготовленные
   `NewGroupAttachment`. Одна синхронная транзакция сохраняет сообщение,
   `reply_to`, метаданные вложений, настройки `buttons_<id>`/`sound_<id>`,
   `file_out`, `file_out_peer` и **весь** снимок `pending_outbound`.
   Фоновая отправка видит всё это только после commit. Внутри транзакции нет
   `await` или вызова другого метода `Db`, повторно захватывающего mutex.
4. `attempt_group_delivery` записывает попытку перед отправкой. Успех или ошибка
   отправки сохраняют запись получателя в очереди.
5. `acknowledge_delivery` принимает `contact_id` из аутентифицированной сессии,
   проверяет исходящее направление сообщения и совпадение группы в ACK.
   `Db::acknowledge_group_delivery` атомарно удаляет только пару этого сообщения
   и этого получателя.

Commit этой транзакции означает приём сообщения в локальный outbox. До него
сбой подготовки или SQL не оставляет видимого сообщения, offers или части
получателей. После commit сбой процесса до первой отправки оставляет полный
outbox для повтора после открытия БД. Ошибка маршрута или последующего чтения
контакта сохраняет принятую очередь; отправка возвращает её message ID.

Оба `send_to_group` используют один DB API и общий guard файлов. `Core`
передаёт `reply_to`, `SessionManager` — кнопки и звук. Offers первоначального
payload строятся из тех же file ID и hashes, которые записывает транзакция;
регистрация файлов после публикации очереди больше не нужна.

Результат ACK задаёт дальнейшее поведение:

| `GroupDeliveryAck` | Состояние |
|---|---|
| `NotPending` | Такой пары в очереди нет; состояние доставки не меняется |
| `PendingRecipients` | Этот получатель подтвердил, остальные ещё ожидаются |
| `Complete` | Ожидаемых получателей больше нет; `sent = 1` и `delivered = 1` фиксируются в той же транзакции |

`MessageDelivered` и замер RTT для группового сообщения появляются только при
`Complete`. ACK другого контакта, неправильной группы, несуществующего сообщения и
повторный ACK не снимают чужое ожидание и не создают повторного события
завершения. Обработка ACK не применяет переданный в нём состав группы.

## Повторы и срок хранения

Очередь переживает перезапуск БД и сброс сессии шифрования. Повтор создаёт новый
зашифрованный конверт с прежним `origin_msg_id`. Существующий приёмник ищет
дубликат по группе, аутентифицированному отправителю и `origin_msg_id`, повторно
отправляя ACK уже сохранённого сообщения.

Пауза между попытками —
`min(300000, 5000 * 2^min(send_attempts, 16))` миллисекунд. Начальная попытка
тоже учитывается, поэтому после неё расчётная пауза — 10 секунд; верхняя
граница — 5 минут. Фактическая отправка зависит также от цикла отправки,
наличия маршрута и сессии.

`RETRY_TTL_MS` ограничивает повторы семью днями. Новые записи получателей имеют
одинаковый `created_at`, равный `sent_at` сообщения. В начале `flush_all_pending`
вызывается `purge_expired_group_outbound`: если просрочена хотя бы одна запись
получателя, удаляются **все оставшиеся записи очереди этого сообщения**. Это
учитывает старые записи с разным временем создания и не позволяет превратить
частичное истечение срока в полную доставку. История сообщения сохраняется;
истечение срока не выставляет `delivered`. После очистки поздний ACK больше
не может завершить эту доставку. Очередь личных сообщений эта очистка не меняет.

Перед начальной отправкой очередному получателю повторно проверяется наличие
контакта и блокировка. Если контакт заблокирован уже после публикации снимка,
его ожидание сохраняется до разблокировки или истечения срока. Удаление контакта
сохраняет существующее поведение БД: триггер удаляет его записи очереди. Поэтому
последующее завершение относится к оставшимся ожиданиям.

## Границы исправления

- Доставка допускает повторные сетевые копии (`at-least-once`): потеря ACK
  вызывает повтор даже уже сохранённого сообщения. Это не обещание `exactly-once`.
- История, метаданные и полный fan-out приняты вместе либо отсутствуют вместе.
  Запись encrypted файлов на диск предшествует транзакции БД. При обычной
  ошибке или раскрутке стека guard пытается удалить только созданные этой попыткой файлы;
  незавершённый входной поток помечает staging как непригодный для публикации.
  При ошибке самой очистки или принудительном завершении процесса до commit
  могут остаться зашифрованные файлы без ссылок в БД; они не являются принятым сообщением. Автоматический
  скан/GC этих crash-orphans здесь не добавлен, чтобы не удалять файлы активного
  writer. Их ограниченная безопасная очистка остаётся отдельной задачей.
- Атомарность относится к локальным данным исходящего группового сообщения.
  Транзакции ratchet и входящих сообщений, файловая система и SQLite не
  объединяются в общий протокол. Настройки SQLite `WAL`/`synchronous=NORMAL`
  не менялись; гарантии при потере питания устройства здесь не расширяются.
- Ранее потерянные записи `pending_outbound` не восстанавливаются. Старая
  отметка `delivered`, выставленная по первому ACK, также не пересчитывается.
- Формат сообщений и кадров, криптография и нативный транспорт I2P не меняются.
  ACK подтверждает приём сообщения; завершение передачи файлов частями имеет
  собственные подтверждения и прогресс.
- Локальные проверки SQLite и каналов не доказывают доставку в живой сети I2P.

## Проверка

Регрессионные тесты находятся в `db.rs::group_delivery_tests`,
`session.rs::delivery_tests` и `core.rs::group_delivery_tests`, а граница срока
для старой очереди — в `db.rs::group_expiry_boundary_tests`.
Они проверяют потерю принятого в канал
конверта, сохранение после ошибки и перезапуска, повторы, изоляцию получателей,
неверные и повторные ACK, полное завершение и очистку без удаления истории.

Новая граница подготовки проверяется в `db.rs::atomic_group_outbox_tests`:
инъекции SQL `RAISE(ABORT)` во время settings, attachment, file offer,
file peer и частично записанного fan-out после reopen не оставляют ни одной
части нового сообщения. Успешный commit после reopen содержит исходные
`sent_at`, ответ, кнопки, звук, оба вида вложений, стабильный offer и всех
получателей. `files.rs::group_staging_tests` проверяет очистку собственных файлов
при SQL/stream ошибке, отказ публикации после неполной записи и чтение
принятых inline/chunked файлов после reopen. Эти проверки исполняют DB API и
файловый guard, используемые обоими callers; полный runtime двух клиентов и
реальный kill процесса они не запускают.

```bash
env -u CC -u CXX I2P_EMBED_STUB=1 cargo test --locked -p gipny-libcore -p gipny --lib
```

Команда запускает полные наборы библиотечных тестов обоих крейтов. Этим тестам
не нужен запущенный роутер: `I2P_EMBED_STUB=1` заменяет нативный роутер заглушкой
и проверяет локальную логику. Для сборки с настоящим i2pd эту переменную нужно
убрать; такой запуск тоже не равен проверке доставки в живой сети.
`I2P_EMBED_SKIP_NATIVE=1` предназначен для `cargo check` и не заменяет линковку
тестов.

Для ревизии PR #120 проверено **2026-10-28**, Rust `1.93.1`, `I2P_EMBED_STUB=1`: наборы
`gipny-libcore` — **119/119**, `gipny` — **23/23**. Включён тест конкурентных
ACK; проверки используют настоящую SQLite и каналы `mpsc`. Также проходит
`cargo check --locked -p gipny-agent -p gipny-bot -p e2e-harness --all-targets`
в том же режиме заглушки. Отрицательная проверка с временным возвратом удаления
pending после успешного enqueue в `session.rs::attempt_group_delivery` падает:
очередь пуста вместо ожидаемого сообщения. После восстановления исправления
полный набор проходит. Доставка по живой I2P этим не проверялась.

Для ветки `fix/atomic-group-outbox` тем же способом проверено **125/125**
`gipny-libcore --lib`, включая три новых теста атомарной публикации и три теста
staging, и **23/23** `gipny --lib`. Отдельные целевые прогоны двух новых модулей
также прошли **3/3** каждый.
Инъекции моделируют SQL/stream отказ и reopen БД; они не имитируют физическое
отключение питания и не запускают транспорт I2P.
